# 試行用の道具

工程([docs/](../docs/README.md))を実際に試すための、最小限の道具。草案の段階の実装であり、docs の定義が変われば直す。

| ファイル | 内容 |
|---|---|
| `check.py` | 機械の検査。検査の台帳のIDごとに成果物を検査し、検査の記録を書く。記録の書式も確かめる |
| `status.py` | 状態の記録(`status.yaml`)を書く機械の命令。検査の記録からの更新、承認の記録、無効になった成果物の洗い出し |
| `selftest.py` | 道具の自己確認。見本が検査に通り、壊した版が、その検査のIDで不合格になることを確かめる |
| `fixtures/mini/` | 見本の資料。2章、4節、本編9枚と付録3枚。工程0から7の成果物が、今の定義の書式で揃う |
| `fixtures/breaks.yaml` | 見本を壊す差分の一覧。検査のIDごとに1つある |
| `build.py` | 確認用の資料(目次と章扉、骨組み、仮置き)のビルドの最小版。古い書式(`headline`)のままである |
| `render.py` | スライド仕様から、型ごとの描画の関数でスライドを描く。古い書式のままである。書式と収容量は [patterns-data.md](patterns-data.md) |
| `render_shot.js` | `render.py` の補助。Playwright の Chromium で診断を取り、PNG を撮る |
| `checks_table.py` | 検査の台帳(`docs/checks.yaml`)から、文書の合格条件を作る。使い方は [docs/README.md](../docs/README.md) |
| `tasks_table.py` | 工程表(`docs/tasks.yaml`)を確かめ、作業の一覧を文書に書き出す。使い方は [docs/README.md](../docs/README.md) |
| `build_skills.py` | 工程表、工程の文書、検査の台帳から、スキル(`.claude/skills/`)を作る。使い方は [docs/README.md](../docs/README.md) |
| `work_order.py` | 工程表から、作業1件の作業票を出す。入力を限る作業の写しを作り、起こす側の手順を出す。使い方は [docs/README.md](../docs/README.md) |

依存: Python 3、PyYAML。`build.py` は python-pptx も使う(`pip install python-pptx`)。`render.py` の依存は [patterns-data.md](patterns-data.md) にある。

## check.py

```
python3 tools/check.py <資料のディレクトリ> --stage N          工程Nの機械の検査
python3 tools/check.py <資料のディレクトリ> --task <作業のid>   工程表の機械の作業の検査
python3 tools/check.py <資料のディレクトリ> --id K04-03        検査1件
python3 tools/check.py <資料のディレクトリ>                    工程0から8の全て
python3 tools/check.py --coverage                             台帳の機械の検査の、実装の状況
python3 tools/check.py --records <資料のディレクトリ>           検査の記録と実行の記録の書式の確かめ
```

| 指定 | 内容 |
|---|---|
| `--stage N` | 台帳の `stage` が N で、判定者に機械を含む検査。複数の工程で使う検査(`KX`)は、その工程の文に当てる |
| `--task <id>` | 工程表の機械の作業の `checks` のうち、判定者に機械を含むもの |
| `--id <ID>` | 検査1件。束ねる項目(`K02-25` など)を指定すると、指す検査を実行する。`--stage` を添えると、`KX` をその工程の文だけに当てる |
| `--chapter <章のID>` | 工程7の検査を、その章のスライドに限る。付録は `appendix` |
| `--write` | 結果を検査の記録に書き、状態の記録を更新する。`--task` か `--stage` と使う |
| `--json` | 結果をJSONで出す |
| `-v` | 合格の行も出す |

終了コードは、不合格か書式の誤りがあれば1。警告だけなら0。引数の誤りは2。

### 結果

検査の条件は、台帳の `check` の文と、`defined_in` が指す文書の定めだけから実装している。結果は、台帳のIDごとに出す。1件の行は、検査のID、成果物、対象(`item`)、合否、該当箇所の引用、理由を持つ。

| 結果 | 意味 |
|---|---|
| 合格 | 条件を満たす。対象がない検査は、「対象がない」として合格にする |
| 不合格 | 条件を満たさない。満たすと言い切れない場合も、不合格とする |
| 警告 | 台帳の `level` が `warning` の検査で、条件を満たさない。終了コードは0 |

実装していない検査は、実行せず、IDを末尾に並べる。

台帳にない確かめを、「書式」として別に出す。YAMLとして読めること、必須の項目、定めた値、IDの重複、IDの参照先である。検査の実行を執筆の誤りから守るためのもので、誤りがあれば終了コードは1になり、`--write` は記録を書かない。合否にする検査として台帳にIDがあるもの(`axis` の有無など)は、書式では見ない。

### 検査の記録を書く

`--write` は、[不合格と修正の手順](../docs/rework.md)の書式で、`checks/<作業のid>--<対象>--<回>.yaml` を書く。

- 対象は、工程7の章ごとの検査では章のID、ほかは `all` とする。`--chapter` がなければ、スライド仕様がある全ての章の記録を、章ごとに書く。
- 回は、同じ作業と対象の記録の数から決める。前の回の記録は書き換えない。
- `commit` は、資料のディレクトリの `git rev-parse --short HEAD` である。コミットしていない変更が成果物にあると、書かずに終了コード2で終わる。`--allow-uncommitted` を付けると、`commit: null` で書く。Gitで管理していないディレクトリでも、`commit: null` で書く。
- 書いた後に、`status.py record-check` と同じ処理で、状態の記録を更新する。

執筆のセッションは、`--write` を付けずに実行する。検査の記録と状態の記録は、受け入れる側が書く([不合格と修正の手順](../docs/rework.md)の「検査と記録を守る」)。

### 記録の書式を確かめる

`--records` は、検査セッションと読み手の役のセッションが書いた記録を、機械が受け取る前に確かめる。

| 記録 | 確かめること |
|---|---|
| 検査の記録(`checks/`) | ファイル名が「作業のid--対象--回.yaml」である。作業が工程表にある。`task`、`target`、`commit`、`round`、`results` がある。`task` と `round` がファイル名と合う。機械の作業の記録は `model` を持たず、ほかの記録は持つ。行の `check` が台帳にあり、その作業の `checks` にある。`verdict` が `pass` か `fail` である。全ての行に `quote` がある。不合格の行に `reason` がある |
| 実行の記録(`runs/`) | ファイル名が「場面の識別子--回.yaml」である。場面が[工程8](../docs/stages/08-integration.md)の識別子である。`scenario`、`commit`、`round`、`steps` がある。`steps` の行に `slide` と `understood` がある。`findings` の行に `slide`、`note` があり、`kind` がエラーの種類の識別子である |

| 分類 | 内容 |
|---|---|
| 描画の結果が要る | ビルドした実物、描画上の診断、最終の出力が要る。描画の道具を直すときに実装する |
| 書式や置き場が未定義 | 判定に要る項目の名前、ファイル名、書式が docs にない |
| 上限や辞書が未確定 | 上限の値、辞書、収容量の値が決まっていない |
| 形態素解析が要る | 語の切り分けや品詞の見分けが要る。標準ライブラリだけではできない |
| 条件が機械で1つに決まらない | 条件の文から、判定の方法が1つに決まらない |
| GitやIssueの状態が要る | ブランチの差分やIssueが要る |

### 判定のやり方

**数値の照合**(`K01-09`、`K02-05`、`K02-12`、`K02-21`、`K03-06`、`K04-16`、`K07-12`)。文の中の数値を、値と単位の組で抜き出して比べる。

- 全角と半角、桁区切り、桁の語(兆、億、万、千)を正規化する。「1兆2,000億円」は、`value: 1.2`、`unit: 兆円` と同じ値になる。
- 単位は、道具が持つ一覧(%、ポイント、倍、円、年度、年、件、人など)に、素材台帳の `unit` を足したものから、数値の直後で最も長く合うものを取る。
- 事実の値は、`value` と `unit` の組と、`statement`、`quote`、`qualifiers` に書かれた数値とする。年や期間は、`value` ではなく `statement` にあるためである。
- 値と単位の両方が同じ場合だけ、一致とする。丸めと「約」は見ない。「2つ」のような数え方も数値として扱う。漢数字は拾わない。

**語彙の検査**(`KX-17`、`KX-18`、`KX-19`)。形態素解析をしない。

- 語彙表の語、仕組みの定義の要素の名前、`allowed` の語を、長いものから順に文から消す。ひらがなで終わる語(「増える」など)は、ひらがなの前まで(「増」)も、後ろにひらがなが続く箇所で消す。活用した形に合わせるためである。
- 数値と、その直後の単位を消す。
- 残った漢字、カタカナ、英字の並びを、登録のない語とする。ひらがなだけの語は拾えない。
- 当てるのは、要約の文、主張(`answer` を含む)、章と節とスライドの題と要点である。説明、表のセル、ノートは、一般語の辞書がないため見ない。図のラベルと表の見出しは、型のデータの中で見分けられないため見ない。
- `banned` の語は、登録した語を消した後の文に、そのまま含まれるかを見る。
- 表記の揺れは、長音の有無、全角と半角、漢字の間の送り仮名を正規化して、語彙表の語と比べる。

**内部のID**(`KX-15`)。資料にあるIDと、定義の例の形(`F001`、`Q1.1`、`T-xxx`、`ch1-s1` など)に合う文字列を、`{}` の参照のほかで探す。スライド仕様の中身(`body`)で、値がIDだけの項目は、参照として扱い、文としては見ない。

### ブリーフの書式

docs に書き方の定めがないため、道具が次の書式で読む。

```markdown
# ブリーフ

## 資料の型
- 状態: 確定

調査報告(research-report)

## 読み手の立場と懸念
- 状態: 確定
- 立場: 中立
- 懸念: つながりにくいのは一部の時間帯だけではないか
- 懸念: 原因は担当者の人数ではないか

## 制約
- 状態: 確定
- 枚数の目安: 10
- 期限: 2026-12-15

## 型ごとの追加の項目
- 状態: 未定
- 決める人と時期: 管理部の部長が、工程1の承認までに決める
```

- 項目は、`## ` で始まる行にする。項目の名前は、[工程0](../docs/stages/00-brief.md)の表の通りに書く。15個の全てが要る。
- 項目の下に、`- 名前: 値` の行で属性を書く。コロンは全角でもよい。`- 状態: ` は必須で、値は 確定、推定、未定 のいずれかにする。
- 状態が未定の項目には、`- 決める人と時期: ` を書く。
- 「資料の型」の本文に、資料の型の定義の名前か `id` を1つだけ書く。[資料の型](../docs/deck-types.md)の「付属する定義」から引く。資料用の定義を作った場合は、`definitions/deck-type.yaml` に置く。
- 「制約」には、`- 枚数の目安: 数` を書く。`K03-13` が読む。
- 「読み手の立場と懸念」には、懸念を1つずつ `- 懸念: 文` で書く。`K04-28` が、`04-chapter-states.yaml` の `concerns_answered` と、文字列の完全一致で照合する。
- 属性の行のほかは、項目の本文として扱う。最初の `## ` より前の行は読まない。

### docs に書式がなく、道具が決めたもの

| 対象 | 決めたこと |
|---|---|
| `style.yaml` の上限 | `limits` の下に置く。`max_claims`(主張の数)、`summary_max_chars`(要約の文の字数)、`title_max_chars`(題の字数)、`point_max_chars`(要点の字数)、`section_max_slides`、`section_summary_min_slides`、`max_commas`(1文の読点の数)、`max_kanji_run`(漢字の連なり)。ない値を使う検査は、不合格になる |
| `style.yaml` の要点の位置 | [工程6](../docs/stages/06-patterns.md)の例の通り、最上位の `point_position` に置く |
| 資料の型の定義 | 付属する定義は docs/deck-types.md から読む。資料用の定義は `definitions/deck-type.yaml`(定義1件) |
| 型の定義 | 付属する型の候補の表(識別子、区分、土台、含意)を docs/patterns.md から読む。`expresses` などは表にないため、資料の定義 `definitions/patterns.yaml`(定義の並び)に書く。同じ `id` は、資料の定義が上書きする |
| `05-proof.yaml` | 「言い切り」「並列の列挙」を選んだ理由を、`relation_reason` に書く。`view` は、`scenario`、`elements`、`relations` を読む |
| `04-scenarios.yaml` | 並びで書く。1件は `scenario`(工程8の場面の識別子)と `expected`。該当しない場面は `applicable: false` と `reason` |
| `06-samples/` | 中の YAML を、スライド仕様の並びとして読む。`body.type` がその型の見本である。見本では、型の識別子をファイル名にした |
| `07-slides/` | 中の YAML を全て読む。スライドの章は、ストーリーラインの `chapter` で決める。見本では、付録を `appendix.yaml` にした |
| スライド仕様の保留 | `status: blocked` のスライドは、Issueの番号を `issue` に書く |
| 検査の記録の `target` | 機械の作業が複数の成果物を検査した場合は、ファイル名を並べる |
| 答えが「分からない」 | `answer` が「分からない」または「分からない。」と一致する場合とする |
| 検査の対象の成果物 | 検査の行がどの成果物についてのものかは、台帳の `target` の先頭の名前(「主張の骨子」など)から決める |

## status.py

```
python3 tools/status.py record-check <資料のディレクトリ> [--strict]
python3 tools/status.py record-approval <資料のディレクトリ> <成果物>... --by user|pm [--on 日付]
python3 tools/status.py invalidate <資料のディレクトリ> [--old <前の版のディレクトリ>] [--dry-run]
python3 tools/status.py show <資料のディレクトリ> [--invalid]
```

書式と決まりは、[不合格と修正の手順](../docs/rework.md)の「状態の記録」「承認の記録」「上流が変わったとき」による。状態の記録は、この道具と `check.py --write` だけが書く。

| 命令 | 内容 |
|---|---|
| `record-check` | `checks/` の、作業と対象ごとの最後の回の記録を読む。成果物ごとに、合否にする検査の不合格がなければ `checked` にし、`commit`、`rounds`、`checks` を書く。不合格があれば `draft` にして、終了コード1で終わる。警告の検査の `fail` は、不合格に数えない |
| `record-approval` | 成果物の状態を `approved` にし、`approved_by` と `approved_on` を書く。`commit` は、検査した版のままにする。状態が `checked` でない成果物、状態の記録にない成果物、検査した版の後に内容が変わった成果物は、拒む。1つでも拒めば、どれも記録しない |
| `invalidate` | 状態の記録の版(または `--old` のディレクトリ)と、今の成果物を比べる。変わった成果物そのものと、変わった項目を前提にする成果物とスライドを `invalid` にし、理由を書く |
| `show` | 状態の記録を表で出す |

`record-check` の決まり:

- 記録の書式に誤りがあれば、何も書かない(`check.py --records` と同じ確かめ)。
- 記録ごとに対象の版が違う場合は、その成果物が版の間で変わっていないことをGitで確かめる。確かめられなければ `draft` にする。
- その成果物を対象にする、工程0から7の検査が1件も記録にない場合は、状態を変えない。
- `invalid` の成果物は、無効になる前の記録が1つでも残っていれば、`invalid` のままにする。全ての作業で検査し直すと、解ける。
- 承認した版が検査に通っている場合は、`approved` のままにする。
- 記録にない合否にする検査を、知らせとして出す。`--strict` を付けると、実装していない機械の検査を除いて、記録にない検査がある成果物を `checked` にしない。
- スライドの `invalid` は、ストーリーライン、立証の設計、そのスライドの仕様のファイルが全て `checked` か `approved` になったときに消す。

`invalidate` が導く範囲は、[不合格と修正の手順](../docs/rework.md)の「直す成果物と、無効になる範囲」の表のうち、成果物の中の参照から機械で導けるものである。

| 変わったもの | invalid にするもの |
|---|---|
| 素材台帳の事実(値、記述、限定、画像の位置) | その事実を `evidence`、`facts`、`sources` に持つ、問いごとの答え、主張の骨子、ストーリーライン、立証の設計、仕組みの定義、スライド |
| 仕組みの定義の要素、つながり、場面 | それを `view` に持つ立証の設計と、そのスライド |
| 仮説の一覧 | 素材台帳、主張の骨子 |
| 探索の計画の問い | 問いごとの答え |
| 問いごとの答え | それを `from` や `question` に持つ、問いごとの答え、主張の骨子、章構成、ストーリーラインのスライド |
| 主張の骨子の `answer` | 章構成以降の全て |
| 主張の文言 | 章構成、その主張を割り当てた章のスライド |
| 章構成の章と節 | ストーリーライン、章の前提と到達点、その章以降のスライド |
| ストーリーラインのスライド | 立証の設計、章の前提と到達点、そのスライド、そのスライドへの言及を持つスライド |
| 章の前提と到達点 | その章以降のスライド |
| 立証の設計 | そのスライド、表現の対応表 |
| 表現の対応表、型の定義 | その型を使うスライドと、型の見本 |
| 語彙表の語 | その語を含むスライド |
| ブリーフの問い、読み手、目的 | 探索の計画以降の全て |
| ブリーフの「外に出せない情報」 | 素材台帳 |

`invalid` にするのは、状態が `checked` か `approved` の成果物だけである。ブリーフのほかの項目、資料の表現規約、テストの場面、要約の文、スライドの順序の変更は、機械で範囲を導けないため、知らせだけを出す。

## selftest.py

```
python3 tools/selftest.py                          全てを確かめる
python3 tools/selftest.py --break K04-03 <出力先>   その検査が不合格になる、壊した版を作る
python3 tools/selftest.py --list                   壊し方の一覧を出す
```

- 見本が、工程0から7の実装済みの検査の全てに通る。警告も、書式の誤りもない。
- `fixtures/breaks.yaml` の差分を見本の写しに当て、検査ごとに、その検査のIDで不合格(警告の検査は警告)になる。
- 書式と参照の確かめ、記録の書式の確かめが、壊した版で誤りを出す。
- 実装した検査と未実装の理由の表が、台帳と合う。実装した検査のうち、壊した版がないものを一覧で出す。
- `status.py` の4つの命令が、決まりの通りに書き、拒む。

検査を足すときは、`check.py` に `@check("ID")` の関数を足し、未実装の表(`TODO`)から消し、`fixtures/breaks.yaml` に壊し方を足す。

`fixtures/mini/` は、社内の問い合わせ窓口の電話がつながりにくい原因を調べた、架空の調査報告である。道具の自己確認と、描画の道具の入力に使う。

## build.py

```
python tools/build.py <資料のディレクトリ> --level toc|skeleton|placeholder [--font フォント名]
```

| `--level` | 読む成果物 | 載るもの |
|---|---|---|
| `toc` | `03-chapters.yaml` | 目次と、章扉(章の題と `message`) |
| `skeleton` | 加えて `04-storyline.yaml`、`01-sources.yaml` | 章扉と、各スライドの見出し、根拠の事実の `statement` |
| `placeholder` | 加えて `05-proof.yaml` | 各スライドに、主張の種類、見せるもの、注目させる点を仮置きとして足す |

`<資料のディレクトリ>/build/` に、次の2つを出す。前の出力は上書きする。

- `deck.pptx`: 白地のスライド。見出しが上、本文がその下。左下に、通し番号、スライドのID、区分を小さく出す。
- `deck.html`: 同じ内容を、1スライド1区画で縦に並べた1ファイル。PowerPointなしで読むためのもの。

付録のスライドは、最後に「付録」の扉を置いて並べる。章扉のIDは `<章のID>-cover` とする。章のまとめと要約のスライドは作らない。

フォントは、`fc-list` でこの環境にある日本語のフォントを探して指定する。見つからなければ `Yu Gothic` とする。開く側の環境に合わせる場合は、`--font` で指定する(例: `--font "Yu Gothic"`)。pptx では、日本語の文字に使うフォント(`a:ea`)にも同じ名前を指定している。

次は実装していない。

- 型ごとの描画。
- 人の手直しを守る仕組み(出力の要約値の記録と照合。[不合格と修正の手順](../docs/rework.md))。
- 成果物の検査。ビルドの前に `check.py` を実行する。参照先のない事実は、「(素材台帳にない)」と表示する。
