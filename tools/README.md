# 試行用の道具

工程([docs/](../docs/README.md))を実際に試すための、最小限の道具。草案の段階の実装であり、docs の定義が変われば直す。

| ファイル | 内容 |
|---|---|
| `check.py` | 工程0から6の機械的な検査の最小版 |
| `build.py` | 確認用の資料(目次と章扉、骨組み、仮置き)のビルドの最小版 |
| `render.py` | スライド仕様(`06-samples/`、`07-slides/`)から、型ごとの描画の関数でスライドを描く。HTML、PNG、`deck.html`、診断(`diagnostics.json`)を出す。書式と収容量は [patterns-data.md](patterns-data.md) |
| `render_shot.js` | `render.py` の補助。Playwright の Chromium で診断を取り、PNG を撮る |
| `checks_table.py` | 検査の台帳(`docs/checks.yaml`)から、文書の合格条件を作る。使い方は [docs/README.md](../docs/README.md) |
| `tasks_table.py` | 工程表(`docs/tasks.yaml`)を確かめ、作業の一覧を文書に書き出す。使い方は [docs/README.md](../docs/README.md) |
| `build_skills.py` | 工程表、工程の文書、検査の台帳から、スキル(`.claude/skills/`)を作る。使い方は [docs/README.md](../docs/README.md) |
| `work_order.py` | 工程表から、作業1件の作業票を出す。入力を限る作業の写しを作り、起こす側の手順を出す。使い方は [docs/README.md](../docs/README.md) |
| `selftest.py` | `check.py` の確かめ。見本が合格し、壊した写しが不合格になることを確かめる |
| `fixtures/mini/` | 3章、スライド9枚の見本の成果物一式(工程0から5) |

依存: Python 3、PyYAML。`build.py` だけが python-pptx も使う(`pip install python-pptx`)。

## check.py

```
python tools/check.py <資料のディレクトリ> [--stage N] [--json]
```

- `--stage N`(0から6)を省くと、全ての工程を検査する。
- 条件、結果、該当箇所の一覧を標準出力に出す。`--json` で同じ内容をJSONで出す。
- 不合格が1件でもあれば、終了コードを1にする。それ以外は0。引数の誤りは2。

結果の種類:

| 結果 | 意味 | 終了コード |
|---|---|---|
| 合格 | 条件を満たす | 0 |
| 不合格 | 条件を満たさない。該当箇所を出す | 1 |
| 警告 | docs が警告とする条件、機械が挙げて人が決める条件、判定の材料が docs に足りない条件 | 0 |
| 判定不能 | 判定に要る成果物や値がない、または壊れている | 0 |
| 未実装 | 「(機械)」の条件だが、実装していない | 0 |
| 成果物なし | その工程の成果物がない | 0 |

YAMLが壊れている成果物は、ファイル名と位置(行、列)を出して不合格にする。その成果物を使う条件は、判定不能になる。

検査セッションとユーザーが判定する条件は、対象にしていない。一覧にも出さない。

### ブリーフの書式

`00-brief.md` は、次の書式で書く。

```markdown
# ブリーフ

## 主な読み手
- 状態: 確定

管理部の部長

## 読み手の立場と懸念
- 状態: 確定
- 立場: 中立
- 懸念: 費用が見合うのか
- 懸念: 回答の誤りで混乱しないか

## 制約
- 状態: 確定
- 枚数の上限: 16
- 期限: 2026-12-15

## 型ごとの追加の項目
- 状態: 未定
- 決める人と時期: 管理部の部長が、工程1の承認までに決める
```

- 項目は、`## ` で始まる行にする。項目の名前は、[工程0](../docs/stages/00-brief.md)の表の通りに書く。15個の全てが要る。
  資料の型、伝え方、主な読み手、副次的な読み手、読み手が既に知っていること、読み手の立場と懸念、目的、答えるべき問い、扱わない範囲、使われる場面、書き手の立場、制約、外に出せない情報、手元の資料、型ごとの追加の項目。
- 項目の下に、`- 名前: 値` の行で属性を書く。コロンは全角でもよい。
- `- 状態: ` は必須で、値は 確定、推定、未定 のいずれかにする。
- 状態が未定の項目には、`- 決める人と時期: ` を書く。
- 「制約」には、`- 枚数の上限: 数` を書く。工程3の枚数の合計の検査が、この数を読む。
- 「読み手の立場と懸念」には、懸念を1つずつ `- 懸念: 文` で書く。工程4で、`04-chapter-states.yaml` の `concerns_answered` と、文字列の完全一致で照合する。
- 属性の行のほかは、項目の本文として扱う。検査は本文を読まない。
- 最初の `## ` より前の行は読まない。

### docs に書式がなく、実装で決めたもの

| 対象 | 決めたこと |
|---|---|
| `style.yaml` | 主張の数の上限を `limits.max_claims`(整数)に書く。ほかの項目は読まない |
| `05-proof.yaml` | 「言い切り」「並列の列挙」を選んだ理由を、`relation_reason` に書く |
| `04-scenarios.yaml` | 一覧で書く。1件は `scenario`(工程8の表の場面の名前)と `expected`。該当しない場面は `applicable: false` と `reason` |
| `06-samples/` | 型の見本は、型の識別子を名前にしたファイルまたはディレクトリとする(`pie-chart.yaml`、`pie-chart/` など) |
| 章ごとの枚数 | ストーリーラインの枚数に、章扉と章のまとめの2枚を、全ての章で足す |
| 型の定義 | `docs/patterns.md` の「付属する型の候補」の表の含意を、`check.py` の中に写した。資料ごとの型の定義は読まない |
| 答えが「分からない」 | `answer` が「分からない」または「分からない。」と一致する場合とする |
| 根拠に使える事実 | `verified: true` で、`kind` が `fact`、`derived`、`testimony`、`image` のいずれか |

### 実装した条件

工程0:

- ブリーフに全ての項目があり、各項目に状態がある。
- 推定のまま残る項目がない。
- 主な読み手、目的、答えるべき問いが確定である。
- 未定の項目に、誰がいつ決めるかが添えてある。
- 「外に出せない情報」が確定である。素材台帳に画像の素材があれば不合格、なければ警告とする。
- `style.yaml` がある。

工程1:

- 仮説、問い、事実のIDが重複していない。
- 仮説に `statement` と `proposed_by` がある。対立する仮説が1つ以上ある。
- 問いに `question` があり、`parent` が探索の計画にある。
- 全ての枝分かれに `axis` がある。全ての末端の問いに `evidence_type`、`priority`、`result` がある。
- 事実に `statement`、定めた種類の `kind`、`verified` がある。
- 全ての `fact` に `source`、`locator`、`quote` がある。
- 全ての `derived` に `formula` がある。
- 数値を持つ全ての事実に `metric` がある。`metric` が語彙表のIDまたは語である。
- 同じ `metric` で、`as_of` と `qualifiers` が同じなのに値が違う事実を挙げる(警告)。
- 全ての `testimony` に `source` がある。
- 画像の素材に `source` と、`version` または `captured_at` がある。`file` が実在する。
- 事実の `answers`、`superseded_by` の参照先がある。
- 画像の素材を除く全ての事実に、全ての仮説に対する `stance` がある。
- 終了の判断。重要度が `high` の問いの全てが `answered` または `disputed` なら合格。そうでなければ警告とする(残りの2つの条件は、記録の置き場が docs にない)。
- `01-model.yaml` がある場合: IDが重複していない。つながりと場面の参照先がある。全ての要素、つながり、場面に `verified: true` の事実が紐づく。`summarizes` が、元のつながりを順にたどっている。画像の素材の `regions` の `element` が定義にある。

工程2:

- 探索の計画の全ての問いに答えがある。`question` と `from` の参照先がある。
- 末端の問いの答えに、`verified: true` の事実が紐づく(「分からない」を除く)。
- 主張の骨子に `answer`、`summary`、`hypothesis`、`axis`、`claims` がある。主張に `statement` と `question` がある。反論に `objection` と `response` がある。`handling` が定めた値である。
- `hypothesis`、`question`、`evidence`、`contradictions` の参照先がある。
- 全ての主張が、問いの木の同じ階層の問いに対応する。
- 主張の数が、`style.yaml` の `limits.max_claims` 以下である。
- 全ての主張に、`verified: true` の事実が1件以上紐づく。
- 1つの `origin` だけに頼る主張を挙げる(警告)。`testimony` だけに頼る主張を挙げる(警告)。
- 採った仮説を否定する事実の全てが、`contradictions` にある。

工程3:

- `order`、章の `kind`、`title`、`message`、`slides` があり、定めた値である。章のIDが重複していない。
- `claims`、`contradictions`、`objections`、`omitted` の参照先がある。
- 全ての主張が、いずれかの本論の章に割り当てられている。
- 本論の章の全てに `claims` がある。導入と結びの章には `claims` がない。
- `omitted` の全てに、行き先と理由がある。
- 主張の骨子の `contradictions` のうち、扱いが `rebut` または `qualify` のものの全てに、触れる章が決まっている。
- 主張の骨子の全ての反論が、`objections` にある。
- 枚数の合計が、ブリーフの「枚数の上限」以下である。
- 全ての章に `slides_reason` がある。

工程4:

- スライドのIDが重複していない。問いと見出しが1つずつある。
- `chapter`、`from`、`evidence`、`contradiction`、`objection` の参照先がある。
- 本論の章の全てのスライドに、`from` と `evidence` がある。
- 章ごとの枚数が、章扉と章のまとめを合算して、章構成の配分以下である。
- 付録の全てのスライドに `appendix_of` があり、本編のスライドを指す。
- 付録に回した答えの全てに、`from` で参照する付録のスライドがある。章構成の `objections` の全てに、参照するスライドが決めた置き場にある。
- 章構成の `contradictions` の全てに、参照するスライドが決めた章にあり、`evidence` がその事実を含む。
- 全ての章に `entry` と `exit` がある。入口の `terms`、`accepted`、`open_questions` が、それより前の章の出口にある。
- 最後の章の出口で、`open_questions` が空である。
- ブリーフの懸念の全てが、いずれかの章の `concerns_answered` にある。ない場合は警告とする(答えないと決めた記録の置き場が docs にない)。
- 工程8が定める6つの場面の全てに、`expected` か、該当しない理由がある。

工程5:

- ストーリーラインの全てのスライドに、立証の設計が1つずつある。
- `relation` が主張の種類の語彙にある。
- `facts` が全て素材台帳にあり、`verified: true` で、`superseded_by` が空である。
- `facts` が、ストーリーラインの `evidence` を全て含む。
- `real` が true のスライドに `view` があり、その要素、つながり、場面が全て仕組みの定義にある。
- `show` と `focus` が空でない。`base` が `none` または `image` である。
- 「言い切り」と「並列の列挙」のスライドに `relation_reason` がある。
- 同じ事実を複数のスライドが使う場合は、警告とする。
- やり取りや状態の遷移の図に出る要素が、構成または要素の関係の図に出ない場合は、警告とする。
- 全てのスライドに `holds` があり、含意の語彙で書かれている。「言い切り」と「並列の列挙」では空である。

工程6:

- 対応表の各行に、語彙にある `relation`、`size`、`base`、付属する型の候補にある `pattern` がある。
- 立証設計に現れる全ての主張の種類と土台の組が、対応表にある。
- 主な型が、同じ土台の中で、複数の主張の種類に使われていない。
- 全てのスライドについて、型の `implies` がスライドの `holds` に含まれる(`emphasized` を除く)。
- 型の `implies` に `grouped`、`partition` がある場合は、立証の設計の `axis` が空でない。
- 資料で使う全ての型に、見本がある。
- 対象を指す語の全てに、`defined_in` か `no_definition` がある。`defined_in` がストーリーラインのスライドを指す。

## build.py

```
python tools/build.py <資料のディレクトリ> --level toc|skeleton|placeholder [--font フォント名]
```

| `--level` | 読む成果物 | 載るもの |
|---|---|---|
| `toc` | `03-chapters.yaml` | 目次と、章扉(章の題と `message`) |
| `skeleton` | 加えて `04-storyline.yaml`、`01-sources.yaml` | 章扉と、各スライドの見出し、根拠の事実の `statement` |
| `placeholder` | 加えて `05-proof.yaml` | 各スライドに、主張の種類、見せるもの、注目させる点を仮置きとして足す |

`<資料のディレクトリ>/build/` に、次の2つを出す。前の出力は上書きする。

- `deck.pptx`: 白地のスライド。見出しが上、本文がその下。左下に、通し番号、スライドのID、区分を小さく出す。
- `deck.html`: 同じ内容を、1スライド1区画で縦に並べた1ファイル。PowerPointなしで読むためのもの。

付録のスライドは、最後に「付録」の扉を置いて並べる。章扉のIDは `<章のID>-cover` とする。章のまとめと要約のスライドは作らない。

フォントは、`fc-list` でこの環境にある日本語のフォントを探して指定する。見つからなければ `Yu Gothic` とする。開く側の環境に合わせる場合は、`--font` で指定する(例: `--font "Yu Gothic"`)。pptx では、日本語の文字に使うフォント(`a:ea`)にも同じ名前を指定している。

次は実装していない。

- 型ごとの描画。
- 人の手直しを守る仕組み(出力の要約値の記録と照合。[不合格と修正の手順](../docs/rework.md))。
- 成果物の検査。ビルドの前に `check.py` を実行する。参照先のない事実は、「(素材台帳にない)」と表示する。

## 確かめ

```
python tools/selftest.py
```

見本をそのまま検査して合格すること、見本の写しを壊して(参照先のないID、必須の項目の欠落、壊れたYAMLなど)不合格になることを確かめる。工程6と仕組みの定義は、写しに成果物を足して確かめる。
