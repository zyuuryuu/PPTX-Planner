## 守ること

### 設計セッション(`docs/organization.md`)

設計の時期を通して、ユーザーの相手をする1つのセッション。工程0から6の成果物のうち、素材台帳、画像の素材、仕組みの定義を除くものを書く。この3つは収集セッションが書く。事実の収集と検査は、別のセッションに任せる。

設計の途中の判断は、設計の判断の記録 `decisions.md` に残す。ソフトウェア開発の設計判断の記録(ADR)と同じ形をとる。

- 状況(何を決める必要があったか。関係する事実)
- 決めたこと
- 却下した案と、その理由
- 受け入れた影響(証拠との食い違い、残る危険など)
- 決めた人と日付

記録するのは、案を却下したとき、証拠と食い違う結論を維持したとき、表現規約の規則の矛盾をユーザーが裁いたとき、および各工程の定義が記録を求めるときである。

製造の時期に入っても終了させず、設計担当として残す。製造中に設計の疑問や見直しが出たら、PMとユーザーはこのセッションに戻る。発表の後の反応は、ユーザーが伝え、このセッションが記録する([工程9](../../../docs/stages/09-finish.md))。

### ユーザーとのやり取り(`docs/organization.md`)

ユーザーの負担を抑えるため、次を守る。

- 一度に求める判断は1つにする。
- 白紙の質問ではなく、推奨と代案を示して選んでもらう。
- 全体の流れを先に見せ、その後は章ごとに進める。
- 検査に通ったものは見せず、判断が要るものだけを出す。
- 承認済みのものを再び聞かない。上流の変更で見直しが要るときは、変わった箇所だけを見せる。

### 原則(`docs/principles.md`)

1. **正本は仕様で、PPTXは生成物である。** 修正は仕様に対して行い、PPTXは作り直す。LLMはPPTXの中身を読まない。PPTXから文字だけを機械的に抜き出して使うことは、これに含まない。
2. **全体で設計し、章ごとに書き、全体で検査する。** 1枚あたり数行で済む成果物は、資料全体を1つのセッションで扱う。分量の多いスライド仕様だけを章に分ける。
3. **下流の作業は、承認済みの成果物だけで進められるようにする。** 会話の履歴にしかない情報を残さない。
4. **収集、執筆、検査は別のセッションで行う。** 詳細は[体制とセッション](../../../docs/organization.md)。
5. **執筆は素材台帳にある事実だけを使う。** 台帳にない事実が必要になったら、書かずに調査依頼を出す。
6. **人はスライドの形で確認する。** 章立て設計以降は、未完成でもビルドして見られるようにする。
7. **合格条件を満たせないときは上流に戻る。** 合格条件のほうを書き換えて通すことはしない。
8. **機械で検査できるものは機械で検査する。**

### 原則(`docs/rework.md`)

1. 直すのは、その成果物を書いたセッションである。検査した側は直さない。
2. 原因が上流にある場合は、その場で辻褄を合わせない。上流に戻す。
3. 検査の指摘に、異を唱える経路を持つ。検査セッションの指摘には誤検出がある。
4. 検査し直すのは、落ちた条件と、直した箇所に依存する条件に限る。
5. 往復に上限を持つ。超えたら人が決める。
6. 合格も不合格も、記録に残す。記録は、検査した側が書く。

## 作業ごとの手順

### `design-proof` スライドごとの立証の設計を書く

担当は設計セッション、工程は5である。

#### 入力

- `01-sources.yaml`
- `01-model.yaml`
- `04-storyline.yaml`
- `style.yaml`

#### 読まないもの

この作業だけの制限はない。「守ること」に従う。

#### 手順

##### 工程5 立証設計の前文(`docs/stages/05-proof.md`)

[目次に戻る](../../../docs/README.md)

スライドごとに、要点を読み手に納得させるために何を見せるかを決める。要点のないスライドでは、役割を果たすために何を見せるかを決める。中身を書く前に行う。全体を1つのセッションで扱う。

##### 成果物(`docs/stages/05-proof.md`)

`05-proof.yaml`(スライドごとの立証の設計):

```yaml
- id: ch2-s1
  relation: trend                 # 主張の種類
  show: 全体と△△領域の売上を5年分並べる   # 見せるもの
  focus: 2023年以降の差の広がり          # 注目させる点
  facts: [F015, F016, F040]       # 使う事実
  axis: null                      # 項目をまとめるスライドでは、分類の軸を書く
  base: none                      # 土台。none(なし) / image(画像の素材の上に描く)
  holds: [ordered, proportional]  # 項目の間に実際に成り立つ関係。含意の語彙で書く。先頭を、主な関係とする
- id: ch4-s3
  relation: interaction
  show: 購入の処理での、部品の間のやり取り
  focus: 在庫の確認で処理が待たされる箇所
  real: true                      # 実在の仕組み、業務、組織、画面を写す場合に true とする
  view:                           # real が true のスライドでは、仕組みの定義から選ぶ
    scenario: S-purchase
    elements: [E-web, E-order, E-stock, E-db]
  facts: [F110]
  holds: [ordered, connected]
```

##### 1. 主張の種類を判定する(`docs/stages/05-proof.md`)

担当: 設計セッション。

要点が何を述べているかで判定する。要点のないスライドは、見せる中身の項目の間の関係で判定する。種類の一覧は[語彙と区分](../../../docs/vocabulary.md)にある。

| 要点が述べていること | 主張の種類 |
|---|---|
| 時間とともに増えた、減った、変わった | 推移 |
| AはBより大きい、最も多いのはA | 項目の比較 |
| 全体のうちAが何割を占める | 構成比 |
| AするとBになる、Aが原因でB | 因果 |
| まずA、次にB | 手順 |
| AとBのどちらを選ぶか | 2案の対比 |
| 前はAだったが、後はBになる | 前後の対比 |
| AはBとCに分かれる、AはBの一部である | 構造・階層 |
| AはBとCの部品からなり、BはCにつながる | 構成 |
| AがBに頼み、BがCに問い合わせる | やり取り |
| Aの状態からBの状態に移る | 状態の遷移 |

この表は主な種類だけを挙げている。全ての種類は[語彙と区分](../../../docs/vocabulary.md)にある。

判定が割れる要点は、主張が2つ混じっているか、曖昧である。ストーリーラインに戻す。

「言い切り」と「並列の列挙」は、どの要点にも当てはめられる。この2つを選ぶ場合は、ほかの種類に当てはまらない理由を書く。

##### 2. 見せるものを決める(`docs/stages/05-proof.md`)

担当: 設計セッション。

見せ方の候補を2つか3つ出し、「要点を読まなくても、要点の内容が伝わるか」で1つに絞る。最初に思いついた見せ方をそのまま採らない。選ばなかった候補は記録しない。

使う事実を `facts` に書く。`facts` が足りなければ、調査依頼を出して工程1に戻る。

##### 3. 注目させる点を決める(`docs/stages/05-proof.md`)

担当: 設計セッション。

読み手に、図や表のどこを見てほしいかを1つ書く。複雑な図ほど必要になる。要点は図の説明(「注文処理の流れを示す」)ではなく、図から読み取ってほしいこと(「在庫の確認で処理が待たされる」)になっているかを、ここで確かめる。なっていなければ、ストーリーラインに戻す。

##### 4. 実在の仕組みを写す図では、仕組みの定義から選ぶ(`docs/stages/05-proof.md`)

担当: 設計セッション。

実在の仕組み、業務、組織、画面を写すスライドでは、`real` を true とし、[仕組みの定義](../../../docs/model.md)から、図に使う要素とつながり、または場面を選び、`view` に書く。主張の種類の区分は問わない。画面の操作の手順のように、区分が「仕組みの記述」でないスライドも含む。定義にないものが必要になったら、描かずに調査依頼を出す。

##### 5. 成り立つ関係を申告する(`docs/stages/05-proof.md`)

担当: 設計セッション。

スライドに載せる項目の間に実際に成り立つ関係を、[形が伝える意味](../../../docs/visual-grammar.md)の含意の語彙で `holds` に書く。工程6で、型が伝える含意と照合する。成り立たない関係を書かない。型に合わせて後から書き足さない。

##### 6. 表現の偏りを見る(`docs/stages/05-proof.md`)

担当: 設計セッション。

全スライドの主張の種類を集計する。同じ種類が続く箇所、特定の種類への偏り、「言い切り」と「並列の列挙」が占める割合を、ユーザーが仮置きの資料を見るときに示す。偏りは違反としない。割合が資料の表現規約の目安を超える場合は警告とし、理由を添えて示す。

#### 検査

##### 満たす合格条件

成果物は、次の条件を満たす。括弧の中は、判定者である。「警告」とある条件は、合否にしない。

- `K05-01` `relation` が[主張の種類の語彙](../../../docs/vocabulary.md)にある(機械)。
- `K05-02` `facts` が全て素材台帳にあり、`verified: true` で、`superseded_by` が空である。画像の素材も `facts` に含める(機械)。
- `K05-03` `facts` が、ストーリーラインの `evidence` を全て含む(機械)。
- `K05-04` `real` が true のスライドに `view` があり、その要素、つながり、場面が全て仕組みの定義にある(機械)。主張の種類の区分は問わない。
- `K05-05` `real` の申告が正しい。図が実在のものを写しているのに、false としていない(検査セッション。重大な検査)。
- `K05-06` 題または要点が「全体」を述べるスライドの `view` が、該当する種類の要素を全て含む(機械)。
- `K05-07` 全てのスライドの `show` が空でない。役割が演習の問題であるスライドを除き、`focus` が空でない(機械)。
- `K05-08` 「言い切り」と「並列の列挙」のスライドに、ほかの種類に当てはまらない理由がある(機械)。
- `K05-09` 同じ事実を複数のスライドが使う場合は、警告とする(機械。警告)。意図した再掲かどうかは、工程5の承認のときに、警告の扱いとして決める。
- `K05-10` やり取りや状態の遷移の図に出る要素が、構成または要素の関係の図のいずれかにも出る。出ない場合は警告とする(機械。警告)。
- `K05-11` 全てのスライドに `holds` の項目がある。項目の間に関係がないスライド(並列の列挙、言い切り)では、空とする(機械)。
- `K05-12` `holds` の申告が正しい。[形が伝える意味](../../../docs/visual-grammar.md)が含意ごとに定める問いで確かめる(検査セッション)。 [定義](../../../docs/visual-grammar.md#a-と-b-含意の照合)
- `K05-13` 主張の種類が、要点の述べていることと合う。要点のないスライドでは、見せる中身と合う(検査セッション)。
- `K05-14` スライド内の要素が除去の検査を通る。`show` が、`focus` に関係しない要素を含まない(検査セッション)。 [定義](../../../docs/checks.md#意味の検査)
- `K05-15` 項目をまとめるスライドが、分類の軸の検査を通る(検査セッション)。 [定義](../../../docs/checks.md#意味の検査)
- `K05-16` 要点の復元: 検査セッションに要点を隠して `show`、`focus`、`facts`、`view` だけを見せ、要点を書かせる。元の要点と意味が一致する。対象は、要点を持つスライドとする(検査セッション)。
