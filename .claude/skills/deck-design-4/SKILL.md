## 守ること

### 設計セッション(`docs/organization.md`)

設計の時期を通して、ユーザーの相手をする1つのセッション。工程0から6の成果物のうち、素材台帳、画像の素材、仕組みの定義を除くものを書く。この3つは収集セッションが書く。事実の収集と検査は、別のセッションに任せる。

設計の途中の判断は、設計の判断の記録 `decisions.md` に残す。ソフトウェア開発の設計判断の記録(ADR)と同じ形をとる。

- 状況(何を決める必要があったか。関係する事実)
- 決めたこと
- 却下した案と、その理由
- 受け入れた影響(証拠との食い違い、残る危険など)
- 決めた人と日付

記録するのは、案を却下したとき、証拠と食い違う結論を維持したとき、表現規約の規則の矛盾をユーザーが裁いたとき、および各工程の定義が記録を求めるときである。

製造の時期に入っても終了させず、設計担当として残す。製造中に設計の疑問や見直しが出たら、PMとユーザーはこのセッションに戻る。発表の後の反応は、ユーザーが伝え、このセッションが記録する([工程9](../../../docs/stages/09-finish.md))。

### ユーザーとのやり取り(`docs/organization.md`)

ユーザーの負担を抑えるため、次を守る。

- 一度に求める判断は1つにする。
- 白紙の質問ではなく、推奨と代案を示して選んでもらう。
- 全体の流れを先に見せ、その後は章ごとに進める。
- 検査に通ったものは見せず、判断が要るものだけを出す。
- 承認済みのものを再び聞かない。上流の変更で見直しが要るときは、変わった箇所だけを見せる。

### 原則(`docs/principles.md`)

1. **正本は仕様で、PPTXは生成物である。** 修正は仕様に対して行い、PPTXは作り直す。LLMはPPTXの中身を読まない。PPTXから文字だけを機械的に抜き出して使うことは、これに含まない。
2. **全体で設計し、章ごとに書き、全体で検査する。** 1枚あたり数行で済む成果物は、資料全体を1つのセッションで扱う。分量の多いスライド仕様だけを章に分ける。
3. **下流の作業は、承認済みの成果物だけで進められるようにする。** 会話の履歴にしかない情報を残さない。
4. **収集、執筆、検査は別のセッションで行う。** 詳細は[体制とセッション](../../../docs/organization.md)。
5. **執筆は素材台帳にある事実だけを使う。** 台帳にない事実が必要になったら、書かずに調査依頼を出す。
6. **人はスライドの形で確認する。** 章立て設計以降は、未完成でもビルドして見られるようにする。
7. **合格条件を満たせないときは上流に戻る。** 合格条件のほうを書き換えて通すことはしない。
8. **機械で検査できるものは機械で検査する。**

### 原則(`docs/rework.md`)

1. 直すのは、その成果物を書いたセッションである。検査した側は直さない。
2. 原因が上流にある場合は、その場で辻褄を合わせない。上流に戻す。
3. 検査の指摘に、異を唱える経路を持つ。検査セッションの指摘には誤検出がある。
4. 検査し直すのは、落ちた条件と、直した箇所に依存する条件に限る。
5. 往復に上限を持つ。超えたら人が決める。
6. 合格も不合格も、記録に残す。記録は、検査した側が書く。

#### 手順

##### 工程4 ストーリーラインの前文(`docs/stages/04-storyline.md`)

[目次に戻る](../../../docs/README.md)

全ての章のスライドの題と要点を、1つのセッションで決める。題は話題を示し、要点は読み手に理解してほしいことを述べる。2つを別の項目として持つ。全体を一度に扱うことで、章をまたぐ要点の重複と矛盾をこの段階で防ぐ。

題と要点の書き方は[文章の書き方](../../../docs/writing.md)に、要点のないスライド、節の要点を載せるスライド、スライドの区分は[語彙と区分](../../../docs/vocabulary.md)に定める。

##### スライドの題と要点の一覧 `04-storyline.yaml`(`docs/stages/04-storyline.md`)

```yaml
- id: ch2-s1
  chapter: ch2
  section: ch2-2               # 章構成で決めた節
  question: 伸びは続いているのか                 # 読み手が抱く問い
  title: △△領域の年ごとの市場規模               # 題
  point: △△の領域の市場規模は、5年続けて前の年を上回った   # 要点。問いへの答え
  qualifiers: [国内]           # 要点の文に入れきれない限定
  provenance: cited            # 出どころ。資料の型の定義が区別を求める資料だけに書く。cited(出典のある事実) / proposal(案) / practice(今の運用)
  from: [Q1.1]                 # 要点の素材にした、問いごとの答え
  evidence: [F015]
- id: ch2-s2
  chapter: ch2
  section: ch2-2
  title: △△領域の範囲と集計の方法
  point: null                  # 要点のないスライド
  role: detail                 # 役割。detail(詳しい説明) / exercise(演習の問題) / reference(参照用)
- id: ch2-s3
  chapter: ch2
  section: ch2-2
  question: 5年間でどれだけ大きくなったか
  title: 5年間の規模の変化
  point_from: section          # 節の要点を引く。自分の要点は書かない
  from: [Q1.1]
  evidence: [F015, F016]
- id: ch2-s4
  chapter: ch2
  section: ch2-3
  question: 伸びはどの地域でも同じか
  title: 地域ごとの伸び
  point_from: section          # スライドが1枚だけの節
  from: [Q1.3]
  evidence: [F033]
  contradiction: F033          # 結論を否定する事実に触れるスライドでは、その事実
- id: ap-s1
  chapter: appendix
  appendix_of: ch2-s1          # 付録のスライドでは、本編のどのスライドを補うか
  question: 伸びているのは大手だけではないか
  title: 新規参入の件数
  point: 新規参入の件数も3年で2倍に増えている
  from: [Q1.2]
  evidence: [F021]
  objection: {claim: C1, index: 0}   # 主張の骨子の反論に答えるスライドでは、その反論
```

以下では、`point` を書いたスライドと、節の要点を引くスライドを、要点を持つスライドと呼ぶ。

資料の型の定義が必ず置くと定めるスライド(`required_slides`)には、`required` にその `id` を書く。

この一覧に書くのは、本編と付録の、中身のあるスライドである。自動で作るスライドは書かない。

章の中は、次の順になる。

1. 章扉。
2. 節ごとに、本編のスライド。節のまとめを置く節では、節の最後に置く。
3. 章のまとめ。

##### 1. 読み手の問いを書き出す(`docs/stages/04-storyline.md`)

担当: 設計セッション。

節ごとに、節の要点を読んだ読み手が抱く問いを、抱く順に書き出す。ブリーフの「読み手が既に知っていること」に答えがある問いは、書かない。ブリーフの「読み手の立場と懸念」にある懸念は、問いとして含める。

##### 2. 問いに、題と要点で答える(`docs/stages/04-storyline.md`)

担当: 設計セッション。

1つの問いに、1枚のスライドで答える。要点は、その問いへの答えの文とする。題は、そのスライドの話題とする。

要点の素材は、工程2の問いごとの答えから取る。節の要点の素材にした答えと、その下にある答えが候補になる。白紙から要点を考えない。素材にした答えを `from` に書く。

該当する答えがない問いは、探索が足りていない。調査依頼を出して工程1に戻るか、その問いを外す。

要点の文に入れきれない限定は、`qualifiers` に書く。

資料の型の定義の `annotation` が出どころの区別を求める資料では、スライドごとに、出どころを `provenance` に書く。値は機械で導かない。設計セッションが書く。

##### 3. 要点のないスライドを足す(`docs/stages/04-storyline.md`)

担当: 設計セッション。

節の要点を理解するために要る説明、演習の問題、参照用の一覧は、要点のないスライドとして足し、役割を書く。

##### 4. 節の要点を載せるスライドを決める(`docs/stages/04-storyline.md`)

担当: 設計セッション。

[語彙と区分](../../../docs/vocabulary.md)の表に当てはめる。節の最後のスライドが載せる節では、そのスライドに `point_from: section` を書く。

##### 5. 必ず置くスライドを入れる(`docs/stages/04-storyline.md`)

担当: 設計セッション。

資料の型の定義の `required_slides` のスライドを、合う節に入れる。

##### 6. 枚数を章構成の配分に合わせる(`docs/stages/04-storyline.md`)

担当: 設計セッション。

章の枚数が章構成の配分を超えたら、除去の検査で残す根拠の弱いスライドから、付録に回すか捨てる。配分を増やす場合と、節を足す、分ける、まとめる場合は、工程3に戻ってユーザーの承認を取り直す。

##### 満たす合格条件

成果物は、次の条件を満たす。括弧の中は、判定者である。「警告」とある条件は、合否にしない。

- `K04-02` 資料の型の定義の `annotation` が出どころの区別を求める資料では、全てのスライドに `provenance` がある。`cited` とした、要点を持つスライドに、`evidence` がある(機械)。
- `K04-03` 全てのスライドが、要点を書く、節の要点を引く、要点を持たずに役割を書く、のいずれか1つの形である(機械)。
- `K04-04` 本編の全てのスライドが、章構成にある節に入っている。章構成の全ての節に、スライドが1枚以上ある(機械)。

- `K04-07` 資料の型の定義の `required_slides` の全てに、`required` でそれを参照するスライドがある(機械)。
- `K04-08` 書き方(`form`)の定めがあるスライドは、その通りに書かれている(検査セッション)。
- `K04-09` 章ごとの枚数が、章構成の配分以下である。自動で作るスライドの枚数は、別に数えてユーザーに示す(機械)。

- `K04-12` 章構成の `contradictions` の全てに、`contradiction` でそれを参照するスライドが、章構成が決めた章にある。そのスライドの `evidence` が、その事実を含む(機械)。

### `write-chapter-states` 章の前提と到達点を書く

##### 7. 章の前提と到達点を書く(`docs/stages/04-storyline.md`)

担当: 設計セッション。

要点の並びから、章ごとに、入る時点で読み手が得ているもの(語、納得した主張、抱いている疑問)と、出る時点で得ているもの(新しい語、納得した主張、答えを得た疑問、残る疑問)を書き出す。

ブリーフの読み手の懸念の1つ1つを、どの章で答えるかを決め、その章の到達点に書く。答えない懸念は、答えないと決めた理由とあわせて、設計の判断の記録に残す。

##### 章の前提と到達点(`docs/stages/08-integration.md`)

章と章のつなぎ目の仕様として、章ごとに、読み手が何を知った状態で入り、何を知った状態で出るかを定める。[工程4](../../../docs/stages/04-storyline.md)で、ストーリーラインとあわせて書く。

```yaml
- chapter: ch3
  entry:                       # この章に入る時点で、読み手が既に得ているもの
    terms: [契約企業, 利用者]
    accepted: [C1]             # 納得している主張
    open_questions: [なぜ△△の領域だけが伸びるのか]
  exit:                        # この章を出る時点で、読み手が得ているもの
    terms: [継続率]
    accepted: [C2]
    answered: [なぜ△△の領域だけが伸びるのか]
    open_questions: [自社はその領域で勝てるのか]
    concerns_answered: [費用が見合うのか]   # ブリーフの読み手の懸念のうち、この章で答えるもの
```

ある章の入口の状態は、それより前の章の出口の状態で満たされていなければならない。これは設計の時点で機械的に確かめられる。結合テストでは、実際に読んだ結果の状態が、定めた通りになっているかを確かめる。

章の執筆のセッションには、その章の前提と到達点を渡す。章は別々のセッションが並行して書くため、ほかの章の中身を読まなくても、どの語や主張を説明済みとして使ってよいかが、これで決まる。

##### 場面と読み方(`docs/stages/08-integration.md`)

| 場面 | 読み方 |
|---|---|
| 主な読み手の通読 | ブリーフの主な読み手として、最初から最後まで読む |
| 反対の立場の通読 | 結論に懐疑的な読み手として読む |
| 要約だけ | 要約のスライドだけを読む |
| 題と要点だけ | 機械が抜き出した、章、節、スライドの題と要点の一覧を、[題と要点の通読](../../../docs/checks.md)の3段で読む |
| 途中から | 配布する資料で、指定した章から読み始める |
| 発表の通し | 口頭の資料で、ノートを話として順に読む |
| 過去の指摘 | 過去に受けた指摘が再発していないかを、該当の箇所で確かめる |

##### 期待する結果(`docs/stages/08-integration.md`)

| 場面 | 期待する結果 |
|---|---|
| 主な読み手の通読 | 各章の出口で、定めた到達点の通りの状態になる。最後に、結論と、求められている行動を述べられる。未回答の疑問がない |
| 反対の立場の通読 | 主張の骨子に書いた反論の全てに、本編か付録で答えを得る |
| 要約だけ | 結論と、その理由を述べられる |
| 題と要点だけ | 章の要点から結論を、節の要点から章の要点を、スライドの要点から節の要点を述べられる。題に重複がなく、話題の順が自然である |
| 途中から | その章の入口の状態を、章扉と、前の章の要点を載せるスライドから得られる。章のまとめがこれに当たる。節が1つだけの章では、節の要点を載せるスライドが当たる |
| 発表の通し | 話が切れずにつながる。全体の時間が、ブリーフの制約に収まる |
| 過去の指摘 | 再発していない |
