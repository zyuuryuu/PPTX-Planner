### 成果物(`docs/stages/07-slide-spec.md`)

`07-slides/ch2.yaml`(章ごとのスライド仕様):

```yaml
- id: ch2-s1
  status: done               # done(書き終えた) / blocked(保留。Issueの番号を添える)
  title: △△領域の年ごとの市場規模               # 題
  point: △△の領域の市場規模は、5年続けて前の年を上回った   # 要点
  qualifiers: [国内]         # 限定
  provenance: cited          # 出どころ。ストーリーラインにある場合
  body:
    type: line-chart
    data: {...}
    highlight: series-target  # 強調する要素。立証設計の注目させる点に対応する
  text: 国内市場の{F040}を占めるまでに拡大した。集計の方法は「{ch2-s2}」に示す   # 数値は事実のID、別のスライドはスライドのIDで参照する
  sources: [F015, F016, F040]
  notes: 口頭で補う説明
```

`title`、`point`、`point_from`、`role`、`qualifiers`、`provenance` は、ストーリーラインの通りに写す。

`text`、`body.data`、`notes` の数値は直接書かず、事実のIDで参照する。ビルドの際に台帳の値に置き換える。`point` は、ストーリーラインを人が読めるように数値を直接書いてよい。その数値は、そのスライドの `sources` の事実と一致させる。別のスライドへの言及は、スライドのIDで書く。ビルドの際に、そのスライドの題に置き換える(文章の書き方)。

要点は、ビルドが、資料の表現規約が型ごとに定める位置に1回だけ描く。`qualifiers` と `provenance` は、ビルドが、資料の型の定義の `annotation` が定める場所に描く。執筆のセッションは、これらを `text` や `body` に書き写さない。

画像の型のスライドでは、画像の素材と、注釈を付ける `regions` を参照する。位置は書かない。

```yaml
- id: ch5-s2
  status: done

  point: 納期が空のまま保存すると、発注が止まる
  body:
    type: annotated-image-steps
    asset: A003
    crop: [due-date-field, save-button]   # この範囲が入るように切り抜く
    scenario: S-order-entry               # 番号は、場面の順から決まる
    captions:                             # 注釈の説明。スライドのノート(`notes`)とは別の項目
      due-date-field: 納期を入力する
      save-button: 保存を押す
  sources: [A003, F120]
```

### 2. スライド仕様を書く(`docs/stages/07-slide-spec.md`)

4. 上流の成果物の問題に気づいたら、推測で埋めない。体制とセッションの「上流の問題の戻し方」に従う。
5. 書き終えたら、検査のコマンドを実行し、完了の報告を返す。

### 項目ごとの書き方(`docs/writing.md`)

| 項目 | 書き方 |
|---|---|
| 題 | 話題を短く示す。名詞で終える。句点を付けない。1行に収める。字数の上限は、資料の表現規約に置く。章、節、スライドの題に共通する |
| 要点 | 読み手に理解してほしいことを、1文で述べる。言い切る。「〜がわかる」「〜について」「〜すべき」で止めない。最大2行。題の言い換えを書かない。章、節、スライドの要点に共通する |
| 説明 | 1文。題と要点の言い換えを書かない |
| ラベル、表のセル | 短い語句。同じ列や同じ並びの中で、形を揃える(全て名詞、または全て文) |
| 図の注記 | 注目させる点に対応するものだけ |
| 脚注 | 限定、出どころ、出典。置き場は下の「限定と出どころ」による |
| ノート | 伝え方による(下の節) |

要点を持たないスライドの扱いは、語彙と区分に定める。

要点を置く位置は、型ごとに資料の表現規約で決める(工程6)。要点は、決めた位置に1回だけ置く。同じことを、1枚の中で2回書かない。

### 限定と出どころ(`docs/writing.md`)

限定と出どころを、題と要点に詰め込まない。要点の文に入れきれない限定は、要点と同じ成果物の `qualifiers` に書く。出どころ(出典のある事実、案、今の運用のどれか)は、区別を求める資料に限り、`provenance` に書く。出どころを、要点の書き出し(「案として」など)で示さない。

`qualifiers` と `provenance` の置き場は、脚注、ノート、印のいずれかである。どれを使うか、出どころを区別するかは、資料の型の定義による。

限定を落としていないかの検査は、要点と `qualifiers` を合わせたものを対象とする。

### 内部のID(`docs/writing.md`)

読み手に見せる文(題、要点、説明、ラベル、表のセル、図の注記、脚注、ノート)に、内部のID(スライド、事実、主張、問い、語、仕組みの定義の要素などのID)を出さない。

別のスライドは、題で指す。スライド仕様には `{ch2-s1}` の形でIDを書き、ビルドの際にそのスライドの題に置き換える。

### 表記(`docs/writing.md`)

- 箇条書きの項目と、図や表の中の文は、名詞で終わる場合と、1文だけの場合は、句点を付けない。複数の文になる場合は、全ての文に句点を付ける。
- 数字と英字は、半角で書く。括弧と句読点は、全角で書く。
- 単位、日付の書式、文末の形は、資料の表現規約で決める(表現規約)。

文の長さ、語調、密度は、工程6で承認した型の見本に合わせる。

### ノート(`docs/writing.md`)

| 伝え方 | スライド | ノート |
|---|---|---|
| 口頭で説明する | 疎にする。題、要点、図で伝わる | 話す内容を書く。図の読み方、強調する点、次のスライドへのつなぎ、想定される質問 |
| 配布して読ませる | 必要なことを全てスライドに載せる | 使わない |

- ノートも、素材台帳にある事実だけを使う。
- スライドは、ノートなしで要点が伝わるようにする。
- ノートは、発表する人が書き手と別の場合を想定して書く。

### 削ってよいものと、削ってはいけないもの(`docs/writing.md`)

| 区分 | 例 | 扱い |
|---|---|---|
| 飾り | 非常に、様々な、重要な、まず前提として | 消す |
| 冗長な形 | することができる、という形になっている | 同じ意味の短い形にする |
| 限定 | 下の表 | 消さない |

限定にあたるもの:

| 種類 | 例 |
|---|---|
| 条件 | 〜の場合に限り、既定では、〜を有効にしたとき |
| 範囲 | 国内の、v2以降の、検証環境では |
| 数量の幅 | 最大で、少なくとも、約、平均で |
| 主体と対象 | 誰が、何が、何に対して |
| 例外 | ただし、〜を除く、原則として |
| 不確かさ | 〜のおそれがある、〜と見られる |
| 因果と順序を示すつなぎ | 〜のため、〜の後に |

限定を消すと、文は元の事実より強い主張、広い主張、または曖昧な主張に変わる。

素材台帳の事実には、その事実に付いている限定を `qualifiers` として記録する(工程1)。

### 技術的な内容の規則(`docs/writing.md`)

- 仕組みを述べる文では、動作の主体を省かない。「これ」「それ」が指すものを、同じ文の中で分かるようにする。
- 名詞をつなげて圧縮しない。語の間の関係を示す助詞を残す。
- 語彙表にある語を、平易な言い方に置き換えない。読み手が知らない語は、初出で補う。

### 収まらないときの順序(`docs/writing.md`)

字数の上限に収まらないときは、次の順で対処する。

1. 飾りを消す。
2. 冗長な形を短くする。
3. 文を分ける。または、条件を表の列にするなど、形を変える。
4. 詳細をノートか付録に移し、スライドからは参照する。
5. スライドを分ける。工程4に戻る。

限定を消すことは、どの段階でも行わない。要点の文から外す限定は、`qualifiers` に移す。

- `KX-16` 全角の数字と英字、半角の括弧と句読点、「表記」の決まりに合わない句点がない(機械)。 定義は、写してある「表記」にある。
- `KX-17` 全ての文から、名詞と動作を指す語を機械的に抜き出し、語彙表、`allowed` と照合する。扱いは、上の「厳しさの段階」の表による(機械)。 定義は、写してある「厳しさの段階」にある。
- `KX-18` `banned` の語を含まない(機械)。 定義は、写してある「厳しさの段階」にある。
- `KX-19` 表記の揺れ(長音の有無、送り仮名、全角と半角)を、正規化して語彙表と照合する(機械)。

### 図での使い方(`docs/model.md`)

工程5で、スライドごとに、図に使う要素とつながり、または場面を選ぶ。工程7のスライド仕様は、立証の設計の `view` をそのまま参照する。

- 図は、定義にある要素とつながりだけを含む。
- 「全体」を題または要点で述べる図は、該当する種類の要素を全て含む。
- 要素とつながりの数が型の上限を超える図は、警告とする。全体像を示すために意図して密にする場合は、表現規約の例外として理由を添える。全体図と詳細図に分ける場合は、詳細図で、全体図での要素の位置と名前を保つ。
- 文字が読める大きさであることは、例外を認めない。

これらは、工程5と工程7の合格条件で確かめる。

図をまたぐ整合は、工程5で、全てのスライドの `view` がそろった時点で検査する。図の中の名前は定義から引くため、名前の不一致は起きない。

### 画面の操作の手順(`docs/model.md`)

スクリーンショットに操作の順を書き足すスライドも、この定義から作る。

- 画面上の要素(ボタン、入力欄など)を、要素として登録する。画像の素材の `regions` が、要素と画像の中の位置を結びつける。
- 操作の手順を、場面として登録する。順序の出典は、手順書、実際の操作の記録、ユーザーの証言のいずれかとする。
- スライドに付ける番号は、場面の `steps` の順から機械的に決まる。

### 画像と注釈(`docs/visual-grammar.md`)

| 手がかり | 読み手が受け取る意味 | 規則 |
|---|---|---|
| 画像を載せる | 実物である(強) | 実物を写した画像だけを載せる。作り物の画面を実物として見せない |
| 画像の上に番号の印を置く | `ordered`(強) | 順序がある場合に限る。番号の並びを、目の動き(左上から右下)にできるだけ合わせる |
| 画像の一部を枠や色で示す | `emphasized`(強) | 注目させる点に対応する箇所に限る |
| 画像の一部から線を引き出して説明を置く | 説明がその箇所を指す(強) | 線の先が、指す箇所に届いている。線どうしを交差させない |
| 画像の周りを暗くする | 明るい部分が `emphasized`(強) | 注目させる範囲が1か所の場合に使う |

- 画像は、注目させる範囲に切り抜く。画面全体を縮めて、文字が読めない大きさにしない。位置関係を示す必要がある場合は、全体と拡大を組にする。
- 印と説明で、指す対象を隠さない。
- 1枚の画像に付ける注釈の数は、型の収容量以下とする。
- 同じ画面を複数のスライドで使う場合は、切り抜く範囲と大きさを揃える。
- 注釈の印の形と色を、資料の中で1通りに決める。

### E: 注目(`docs/visual-grammar.md`)

- 強調の色は、描画の実装が、スライド仕様で指定した要素にだけ付ける。構造で守る。
- 強調の数は、スライド仕様の強調する要素(`highlight`)の指定を数える。
- 最初に目が行く場所は、型ごとに1回、見本の画像で確かめる。

### F: 量の歪み(`docs/visual-grammar.md`)

- 立体のグラフは、型の定義に置かない。
- 構成比を円で表す場合の項目の数の上限は、型の収容量で定める。
- 複数のグラフの軸の範囲を揃えるのは、並べて比べる場合に限る。

### 不合格のときの手順(`docs/rework.md`)

1. **検査が不合格を返す。** 落ちた条件、該当する箇所、理由を添える。検査セッションの指摘には、根拠にした箇所の引用を必須とする。
2. **書いたセッションが、直すか、異議を唱えるかを選ぶ。**
3. **異議を唱える場合は、理由を添えて裁定を求める。** 裁く者は上の表による。裁定の結果は、検査の記録に残す。
4. **直す場合は、原因のある成果物を直す。** 原因が自分の成果物にあれば直す。上流にあれば、Issueを立てて上流に戻し、自分の成果物は保留にする。
5. **検査し直す。**
   - 機械的な検査は、全て再実行する。
   - 検査セッションの検査は、落ちた条件と、直した箇所に依存する条件に限る。新しく起こした検査セッションに、前回の指摘を渡す。確かめるのは、指摘が解消したかと、直したことで新しい問題が生じていないかである。直していない箇所に、新しい指摘を出さない。
6. **往復を数える。** 1つの成果物(スライド仕様は章または節)について、不合格、修正、再検査の1巡を1回と数える。資料の表現規約が定める上限を超えたら、上の表の者に上げる。

上げられた者は、次のいずれかを選ぶ。

| 選択 | 内容 |
|---|---|
| 直し方を指示する | 具体的な直し方を示す |
| 受け入れる | 指摘を残したまま進める。検査の記録に残し、工程9の検査の報告に載せる |
| 上流に戻す | 原因が上流にあると判断し、上流の成果物を直す |
| 例外を認める | 合格条件から外す。資料の表現規約の例外として、理由とともに記録する |

合格条件そのものを、その場で書き換えることはしない。

### 語の登録の手順(`docs/terms.md`)

使いたい語が出てきたときに、その1語について、似た語がないか、誤用でないかを確かめてから登録する。資料の全体から揺れを探すより、1語を文脈つきで判定するほうが、確かに判定できる。

### 管理の方法(`docs/git.md`)

資料ごとの成果物を、Gitのリポジトリで管理する。

| ソフトウェア開発 | スライド作成 |
|---|---|
| コミット前の自動検査 | 機械的な検査 |
| コードレビュー | 検査セッションによる検査 |
| 変更の受け入れ | PMによる受け入れ、ユーザーの承認 |
| Issue | 指摘、調査依頼、検査で残った問題、描画の実装への要望 |
| 機能ごとのブランチ | 章や節ごとの執筆 |
| 変更の差分 | 上流を直したとき、下流のどれが古くなったかの判定 |
| ビルドの生成物は管理しない | PPTXは管理の対象から外す |

- ユーザーの承認は、タグまたは状態の記録として残す。
- ユーザーにはYAMLの差分を読ませない。直す前と後のスライドを見せる。
- プルリクエストとCIは必須としない。複数人で1つの資料を作る場合の選択肢とする。

### 検査の実行(`docs/checks.md`)

機械的な検査は、1つのコマンドにまとめる。

| 検査 | 実行する時点 |
|---|---|
| 書式、IDの参照先、使う語彙、文の機械的な検査、数値の参照、分量の上限、担当外のファイルの変更 | コミット前 |
| ビルド、描画上の診断 | 工程の合格判定のとき |
| 検査セッションによる検査 | 工程の合格判定のとき |

工程の合格判定では、機械の検査を先に行い、通ったものを検査セッションが検査する。

コミット前の検査は飛ばすことができる。そのため、工程の合格判定とPMによる受け入れの際に、同じコマンドをもう一度実行する。

### C: 一貫性(`docs/visual-grammar.md`)

- 同じ主張の種類で同じ量の区分のスライドが同じ型を使うことは、表現の対応表と、スライド仕様の型との照合で確かめる。
- 同じ対象が全ての図で同じ色と同じ名前になることは、資料の表現規約の色の割り当てと、図や表のデータとの照合で確かめる。
- 矢印と図形の形の意味が資料の中で1通りであることは、型の定義と表現規約から決まる。

### 検査セッションが判断するもの(`docs/writing.md`)

| 検査 | 方法 |
|---|---|
| 裏付けのない文 | スライド仕様と、そのスライドが使う事実だけを渡す。文を1つずつ、事実に裏付けられているかを判定する。「多くの企業が」「近年」のような根拠のない一般化も対象とする |
| 限定の残存 | スライドが使う事実の `qualifiers` が、全て、文かスライドの `qualifiers` に残っているかを照合する |
| 削る検査 | 文ごとに、消しても意味が変わらない語を全て挙げる。挙がった語のそれぞれについて、消すと主張が事実より強く、広く、または曖昧になるかを確かめる。ならないものだけを消す。消した後も、文として読めること |
| 重複の検査 | 同じスライドの中で、題、要点、説明、中身が同じことを繰り返していないか |
| 言い直しの検査 | 中身(型のデータと説明)が、題と要点の言い直しだけで、新しい情報を足していないスライドを挙げる。挙がったスライドは、前後のスライドに統合する候補として、設計セッションに渡す |
| 主体の検査 | 仕組みを述べる文で、動作の主体が書かれているか |
| 読み戻し | 経緯を知らない検査セッションにスライドの文だけを読ませ、意味を完全な文で書き直させる。素材台帳の事実と比べ、条件の脱落や主体の違いがないかを確かめる。対象は、仕組みの記述のスライドと、`qualifiers` を持つ事実を使うスライドとする |

検査に落ちた後の手順と、往復の上限は、不合格と修正の手順による。

### D: 知覚の限界(`docs/visual-grammar.md`)

- 文字の大きさ、文字と背景の色の差、隣り合う色の差、1枚で使う色相の数は、描画の実装が報告する。文字の大きさの下限には、例外を認めない。
- 型の項目ごとの字数が収容量を超える場合は、不合格とする。
- 項目の数が型の収容量を超える場合は、工程6で、中身を見直すか、収容量を超えた場合の型に切り替える。
- 図の要素とつながりの数が型の収容量を超える場合は、警告とする。
- 注釈の印と説明が、指す対象に重なっていないかは、`regions` の位置から判定する。

### G: 飾り(`docs/visual-grammar.md`)

- 情報を運ばない要素は、型の定義に置かない(型の定義)。
- 消しても情報が失われない要素がないかは、型ごとに1回、見本の画像で確かめる。

### 機械で測るもの(`docs/writing.md`)

- 1文の字数が、項目の種類ごとに定める上限以下である(機械)。 `KX-01`
- 1文の読点の数が、上限以下である(機械)。 `KX-02`
- 「の」の連続と、同じ助詞の重なりが、連続する回数の上限以下である(機械)。 `KX-03`
- 漢字の連なりが、連続する字数の上限以下である(機械)。 `KX-04`
- 辞書にある冗長な言い回しを含まない(機械)。 `KX-05`
- 辞書にある、中身のない形容と強調を含まない(機械)。 `KX-06`
- 辞書にある書き出しの決まり文句(「一言で言うと」「結論から言うと」「要するに」「端的に言えば」など)を含まない(機械)。 `KX-07`
- 辞書にある、LLMに多い語を含まない(機械)。 `KX-08`
- ぼかし(「など」「等」「といった」)の数が、上限以下である(機械)。 `KX-09`
- 「また」「さらに」「加えて」で始まる文の割合が、上限以下である(機械)。 `KX-10`
- 近い位置での同じ語の繰り返しの回数が、上限以下である(機械)。 `KX-11`
- です・ます調と、である調が混在していない(機械)。 `KX-12`
- 題が名詞で終わる。句点がない。字数が上限以下である(機械)。 `KX-13`
- 要点が1文である。文末が「がわかる」「について」「すべき」でない。字数が、2行に収まる上限以下である(機械)。 `KX-14`
- 読み手に見せる文に、内部のIDがない。IDの書式に合う文字列が、`{}` で囲んだ参照のほかにない(機械)。 `KX-15`
- 全角の数字と英字、半角の括弧と句読点、「表記」の決まりに合わない句点がない(機械)。 `KX-16`


使う語彙の検査も、機械で測る。

日本語の文章を機械的に検査する道具(textlintと、その技術文書向けの規則集)を土台にする。上限をスライド向けに厳しくし、辞書を足す。辞書は個人の表現規約に置き、フィードバックで足す。

上限の値は未確定である。口頭の資料のノートでは、字数と読点の上限を緩める。技術的な資料では、1文の字数の上限を緩める。値は資料の型の定義の `limits` に置く。

### 厳しさの段階(`docs/terms.md`)

語彙の検査は、文の種類によって厳しさを変える。

| 文の種類 | 登録も許可もされていない名詞と動作の語 |
|---|---|
| 要約の文、主張、章と節とスライドの題と要点、図のラベル、表の見出し、仕組みの定義の要素の名前 | 不合格とする。一般語の辞書は使わない。語彙表にも `allowed` にもない語は、全て止める |
| 説明、表のセル、図の注記、ノート | 語彙表、`allowed`、一般語の辞書のいずれにもない語を、警告とする。試作で誤検出の程度を見て、不合格に上げるかを決める |

`banned` の語は、文の種類によらず不合格とする。
