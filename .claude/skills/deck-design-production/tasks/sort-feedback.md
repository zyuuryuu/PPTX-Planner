## 手順

### フィードバック(`docs/feedback.md`)

ビルドした資料への指摘を受け、仕様に反映する。生成後にPowerPointで人が直した内容は、データとして仕様に同期しない。「こうしたい」という意図を伝える見本として読む。

### 入口(`docs/feedback.md`)

- 言葉での指摘。
- スライドを指しての問題点の指定。
- 人が軽く直したPPTX。
- 発表や配布の後に得た、読み手の反応(質問されたこと、伝わらなかった箇所、読み手が実際にとった判断や行動)。

直したPPTXは次の方法で読む。PPTXの座標や書式は読まない。

| 知りたいこと | 方法 |
|---|---|
| どのスライドが変わったか | 機械的に検出する |
| 文字の変更 | PPTXから文字だけを抜き出して差分をとる |
| 配置や見た目の変更 | 直す前と後の画像を並べて読む。変わったスライドだけを対象にする |

### 反映先の範囲(`docs/feedback.md`)

担当: 設計セッション。

設計セッションは指摘を整理し、反映先の範囲を提案する。「そのスライドだけ」より広い反映は、ユーザーの承認を経る。LLMは1件の指摘を過度に一般化しがちなためである。

| 範囲 | 例 | 直す成果物 |
|---|---|---|
| そのスライドだけ | この言い回しを変える | スライド仕様 |
| 同じ型の全スライド | この種類の話は、別の型で見せたい | 表現の対応表、立証設計 |
| 同じ型の全スライド | 比較の図は左右を逆にしたい | 資料の表現規約の規則 |
| 資料全体 | 文字が全体に多い | 資料の表現規約 |
| 資料全体 | この語に統一 | 語彙表。[使う語彙](../../../../docs/terms.md)の「語を後から変える場合」の手順による |
| 今後の全ての資料 | 結論はいつも左上に置く | 個人の表現規約 |
| 道具の側 | この図の型が描けない | 描画の実装への要望 |

### 記録(`docs/feedback.md`)

指摘は1件ずつIssueとして記録する。項目は、指摘の内容、LLMの解釈、反映先の範囲、直した成果物、反映の結果である。作り直した後に、過去の指摘が守られているかは、[工程8](../../../../docs/stages/08-integration.md)の「過去の指摘」の場面で確かめる。

### 再現できない手直し(`docs/feedback.md`)

図形を少し動かすなど、仕様で表現できない手直しは、黙って捨てない。作り直すと消えることを理由つきで伝え、描画の実装への要望にするか、最終版の後の手直しに回す。

最終版の後の手直しは自由とする。その後に作り直す場合は、手直しが消えることを警告する。
