## 守ること

### 設計セッション(`docs/organization.md`)

設計の時期を通して、ユーザーの相手をする1つのセッション。工程0から6の成果物のうち、素材台帳、画像の素材、仕組みの定義を除くものを書く。この3つは収集セッションが書く。事実の収集と検査は、別のセッションに任せる。

設計の途中の判断は、設計の判断の記録 `decisions.md` に残す。ソフトウェア開発の設計判断の記録(ADR)と同じ形をとる。

- 状況(何を決める必要があったか。関係する事実)
- 決めたこと
- 却下した案と、その理由
- 受け入れた影響(証拠との食い違い、残る危険など)
- 決めた人と日付

記録するのは、案を却下したとき、証拠と食い違う結論を維持したとき、表現規約の規則の矛盾をユーザーが裁いたとき、および各工程の定義が記録を求めるときである。

製造の時期に入っても終了させず、設計担当として残す。製造中に設計の疑問や見直しが出たら、PMとユーザーはこのセッションに戻る。発表の後の反応は、ユーザーが伝え、このセッションが記録する([工程9](../../../docs/stages/09-finish.md))。

### ユーザーとのやり取り(`docs/organization.md`)

ユーザーの負担を抑えるため、次を守る。

- 一度に求める判断は1つにする。
- 白紙の質問ではなく、推奨と代案を示して選んでもらう。
- 全体の流れを先に見せ、その後は章ごとに進める。
- 検査に通ったものは見せず、判断が要るものだけを出す。
- 承認済みのものを再び聞かない。上流の変更で見直しが要るときは、変わった箇所だけを見せる。

### 原則(`docs/principles.md`)

1. **正本は仕様で、PPTXは生成物である。** 修正は仕様に対して行い、PPTXは作り直す。LLMはPPTXの中身を読まない。PPTXから文字だけを機械的に抜き出して使うことは、これに含まない。
2. **全体で設計し、章ごとに書き、全体で検査する。** 1枚あたり数行で済む成果物は、資料全体を1つのセッションで扱う。分量の多いスライド仕様だけを章に分ける。
3. **下流の作業は、承認済みの成果物だけで進められるようにする。** 会話の履歴にしかない情報を残さない。
4. **収集、執筆、検査は別のセッションで行う。** 詳細は[体制とセッション](../../../docs/organization.md)。
5. **執筆は素材台帳にある事実だけを使う。** 台帳にない事実が必要になったら、書かずに調査依頼を出す。
6. **人はスライドの形で確認する。** 章立て設計以降は、未完成でもビルドして見られるようにする。
7. **合格条件を満たせないときは上流に戻る。** 合格条件のほうを書き換えて通すことはしない。
8. **機械で検査できるものは機械で検査する。**

### 原則(`docs/rework.md`)

1. 直すのは、その成果物を書いたセッションである。検査した側は直さない。
2. 原因が上流にある場合は、その場で辻褄を合わせない。上流に戻す。
3. 検査の指摘に、異を唱える経路を持つ。検査セッションの指摘には誤検出がある。
4. 検査し直すのは、落ちた条件と、直した箇所に依存する条件に限る。
5. 往復に上限を持つ。超えたら人が決める。
6. 合格も不合格も、記録に残す。記録は、検査した側が書く。

##### 検査セッションが判断するもの(`docs/writing.md`)

| 検査 | 方法 |
|---|---|
| 裏付けのない文 | スライド仕様と、そのスライドが使う事実だけを渡す。文を1つずつ、事実に裏付けられているかを判定する。「多くの企業が」「近年」のような根拠のない一般化も対象とする |
| 限定の残存 | スライドが使う事実の `qualifiers` が、全て、文かスライドの `qualifiers` に残っているかを照合する |
| 削る検査 | 文ごとに、消しても意味が変わらない語を全て挙げる。挙がった語のそれぞれについて、消すと主張が事実より強く、広く、または曖昧になるかを確かめる。ならないものだけを消す。消した後も、文として読めること |
| 重複の検査 | 同じスライドの中で、題、要点、説明、中身が同じことを繰り返していないか |
| 言い直しの検査 | 中身(型のデータと説明)が、題と要点の言い直しだけで、新しい情報を足していないスライドを挙げる。挙がったスライドは、前後のスライドに統合する候補として、設計セッションに渡す |
| 主体の検査 | 仕組みを述べる文で、動作の主体が書かれているか |
| 読み戻し | 経緯を知らない検査セッションにスライドの文だけを読ませ、意味を完全な文で書き直させる。素材台帳の事実と比べ、条件の脱落や主体の違いがないかを確かめる。対象は、仕組みの記述のスライドと、`qualifiers` を持つ事実を使うスライドとする |

##### 要約を用意する(`docs/stages/08-integration.md`)

担当: 設計セッション。

要約は、結論と理由を1つの文にまとめたものとする。結論の下に根拠を箇条書きで並べる形は、主張を並べ直しただけで、要約にならない。

```yaml
- id: summary
  kind: summary
  text: 〇〇事業は、伸びている△△領域に絞れば、当社の継続率の高さを生かして2年で黒字に戻せる見込みである
  from: summary
  ask: 来月の経営会議で、△△領域への集中を決定いただきたい   # 結びの章の要点。載せるかどうかは表現規約で決める
  ask_from: ch7
```

要約に根拠を短く添えるかどうかは、[工程6](../../../docs/stages/06-patterns.md)の資料に共通の規則で決める。添える場合は、主張の骨子の主張を短くして並べ、元にした主張を記録する。元の主張より強い言い方にしない。

##### 規則の追加と整理(`docs/style-rules.md`)

担当: 設計セッション。

規則を足すたびに、既存の規則との整理と統合を行う。

1. **起案**: 指摘から規則の案を作る。
2. **照合**: 既存の全ての規則と比べ、次のいずれかを判定する。

   | 関係 | 対応 |
   |---|---|
   | 重複(同じことを言っている) | 1つにまとめる |
   | 矛盾(両立しない) | どちらを残すかをユーザーが決める |
   | 包含(一方が他方の特殊な場合) | 一般の規則と例外の形に組み直す |
   | 共通の原理がある(個別の規則が複数並ぶ) | 1つの規則に一般化する |

3. **影響の確認**: 整理後の規則を現在の資料に当て、違反になるスライドの一覧を出す。
4. **承認**: ユーザーが、整理後の規則と影響を見て承認する。
5. **反映**: 規則を更新し、違反になったスライドを直す。

整理は規則の数を減らす方向で行う。文章の規則より、表現の対応表や語彙表のような、機械で検査できる構造への組み込みを優先する。
