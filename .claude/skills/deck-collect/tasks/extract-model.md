### 考え方(`docs/model.md`)

LLMに、出典から図を直接描かせない。出典から図を直接描くと、どの線が出典にあり、どの線がLLMの補完なのかを後から区別できない。次の2段階に分ける。

1. 出典から、要素とつながりを1件ずつ抜き出し、仕組みの定義に登録する。
2. 図は、仕組みの定義から要素とつながりを選んで作る。図の記述は、選んだ内容から機械的に生成する。

| 確かめること | 方法 |
|---|---|
| 図が、仕組みの定義にないものを含まない | 機械。図は定義からの選択であり、構造上含められない |
| 仕組みの定義が、出典にないものを含まない | 検査セッション。1件ずつ引用箇所と突き合わせる |

図の中の名前は定義から機械的に引くため、図によって名前が変わることがない。

### 成果物(`docs/model.md`)

`01-model.yaml`。工程1で作る。

```yaml
elements:
  - id: E-order
    kind: component          # component(部品) / actor(主体) / data(データ) / state(状態) など
    name: 注文サービス
    evidence: [F101]         # 素材台帳の事実
relations:
  - id: R-order-stock
    kind: call               # call(呼び出し) / send(送信) / contain(包含) / depend(依存) / transition(遷移) など
    from: E-order
    to: E-stock
    label: 在庫の確認
    mode: unknown            # 出典に書かれていない属性は unknown とする
    evidence: [F102]
  - id: R-web-db
    kind: call
    from: E-web
    to: E-db
    summarizes: [R-web-order, R-order-db]   # 間を省略したつながり。元のつながりを記録する
scenarios:
  - id: S-purchase
    name: 購入の処理
    steps: [R-web-order, R-order-stock, R-order-db]   # つながりを順に並べる
    evidence: [F110]         # 順序の出典
  - id: S-order-entry
    name: 注文の入力
    steps: [R-user-due-date, R-user-save]   # 画面の操作の手順
    evidence: [F120]
```

要素、つながり、場面の1件ごとに、素材台帳の事実を紐づける。事実の種類と確認の条件は、工程1の定めに従う。

### 抜き出し(`docs/model.md`)

信頼の順位を次の通りとする。

| 順位 | 出どころ |
|---|---|
| 1 | 機械で読める出典(データベースの定義、APIの定義、構成の定義など)からの機械的な抜き出し |
| 2 | 文書からLLMが抜き出し、検査セッションが確認したもの |
| 3 | ユーザーの証言 |
| 不可 | LLMの推測 |

- 機械で読める出典がある場合は、LLMを使わずに抜き出す。
- 出典に書かれていないことは、`unknown` として登録する。よくある構成であることを理由に、書かれていない要素やつながりを足さない。`unknown` の項目は、ユーザーに聞くか、図の上で未確定と示す。
- 間の要素を省いたつながりは、実在しないつながりである。`summarizes` に元のつながりを記録したものだけを認める。
- 出典の日付または版を、素材台帳の事実の `as_of` に記録する。

### 画面の操作の手順(`docs/model.md`)

スクリーンショットに操作の順を書き足すスライドも、この定義から作る。

- 画面上の要素(ボタン、入力欄など)を、要素として登録する。画像の素材の `regions` が、要素と画像の中の位置を結びつける。
- 操作の手順を、場面として登録する。順序の出典は、手順書、実際の操作の記録、ユーザーの証言のいずれかとする。
- スライドに付ける番号は、場面の `steps` の順から機械的に決まる。

### 不合格のときの手順(`docs/rework.md`)

1. **検査が不合格を返す。** 落ちた条件、該当する箇所、理由を添える。検査セッションの指摘には、対象の該当する箇所の引用を付け、条件のどの部分に反するかを書く。
2. **書いたセッションが、直すか、異議を唱えるかを選ぶ。**
3. **異議を唱える場合は、理由を添えて裁定を求める。** 裁く者は上の表による。裁定の結果は、設計の判断の記録に残す。
4. **直す場合は、原因のある成果物を直す。** 原因が自分の成果物にあれば直す。上流にあれば、Issueを立てて上流に戻し、自分の成果物は保留にする。
5. **検査し直す。**
   - 機械的な検査は、全て再実行する。
   - 検査セッションの検査は、落ちた条件と、直した箇所に依存する条件に限る。新しく起こした検査セッションに、前回の指摘を渡す。確かめるのは、指摘が解消したかと、直したことで新しい問題が生じていないかである。直していない箇所に、新しい指摘を出さない。
6. **往復を数える。** 1つの成果物(スライド仕様は章または節)について、不合格、修正、再検査の1巡を1回と数える。資料の表現規約が定める上限を超えたら、上の表の者に上げる。

上げられた者は、次のいずれかを選ぶ。

| 選択 | 内容 |
|---|---|
| 直し方を指示する | 具体的な直し方を示す |
| 受け入れる | 指摘を残したまま進める。検査の記録に残し、工程9の検査の報告に載せる |
| 上流に戻す | 原因が上流にあると判断し、上流の成果物を直す |
| 例外を認める | 合格条件から外す。資料の表現規約の例外として、理由とともに記録する |

合格条件そのものを、その場で書き換えることはしない。

## 報告の書式

### 調査依頼(`docs/stages/01-exploration.md`)

担当: 設計セッション。

調査は設計セッションや執筆のセッションから直接行わず、調査依頼として収集セッションに渡す。調査依頼は、Issueとして出す(Gitでの管理)。調査依頼は、探索の計画の末端の問いをそのまま渡す。「Aを裏付ける事実を探せ」のような、結論を含む聞き方をしない。

調査依頼の項目:

- 知りたいこと(1文の問い)
- 探索の計画のどの問いに対応するか
- 返す形式(素材台帳の書式)
- 見つからなかった場合は「見つからない」と返すこと
