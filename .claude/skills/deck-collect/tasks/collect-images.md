### 画像の素材(`docs/stages/01-exploration.md`)

スクリーンショット、写真、文書の抜粋、他の資料から引用した図は、画像の素材として素材台帳に登録する。画像をLLMに生成させて、実物として載せることは認めない。

```yaml
- id: A003
  kind: image
  file: assets/order-screen.png
  statement: 注文の入力画面
  source: 受注管理システム          # 何を写したものか。引用した図では、引用元
  version: "4.2"                    # 対象の版
  captured_at: 2026-11-10           # 取得した日
  environment: 検証環境             # 取得した環境
  regions:                          # 画像の中の要素と、その位置
    - id: due-date-field
      element: E-ui-due-date
      label: 納期の欄
      box: [0.30, 0.42, 0.25, 0.05]
      box_origin: recorded
    - id: save-button
      element: E-ui-save            # 仕組みの定義の要素。対応するものがある場合
      label: 保存ボタン
      box: [0.82, 0.90, 0.10, 0.05] # 画像の幅と高さに対する割合(左、上、幅、高さ)
      box_origin: recorded          # recorded(取得と同時に機械的に記録) / user(ユーザーが指定) / estimated(LLMが推定)
  masked: [顧客名の列]               # 隠した箇所
  verified: true
```

隠す作業は、収集セッションが画像そのものを加工して行う。加工する前の画像は、資料のリポジトリに置かない。画像を差し替えた場合にやり直す検査は、不合格と修正の手順の表による。

画像の中の位置は、レイアウトではなく、画像に付属する事実として扱う。位置を書くのは画像の素材の `regions` だけである。スライド仕様は、位置ではなく `regions` の `id` を参照する。

位置の出どころの信頼の順位は、`recorded`、`user`、`estimated` の順とする。`estimated` の位置は、注釈を描いた後に確かめる(工程7)。

`verified: true` にする条件は、下の合格条件の「画像の素材」の全てである。

### 不合格のときの手順(`docs/rework.md`)

1. **検査が不合格を返す。** 落ちた条件、該当する箇所、理由を添える。検査セッションの指摘には、対象の該当する箇所の引用を付け、条件のどの部分に反するかを書く。
2. **書いたセッションが、直すか、異議を唱えるかを選ぶ。**
3. **異議を唱える場合は、理由を添えて裁定を求める。** 裁く者は上の表による。裁定の結果は、設計の判断の記録に残す。
4. **直す場合は、原因のある成果物を直す。** 原因が自分の成果物にあれば直す。上流にあれば、Issueを立てて上流に戻し、自分の成果物は保留にする。
5. **検査し直す。**
   - 機械的な検査は、全て再実行する。
   - 検査セッションの検査は、落ちた条件と、直した箇所に依存する条件に限る。新しく起こした検査セッションに、前回の指摘を渡す。確かめるのは、指摘が解消したかと、直したことで新しい問題が生じていないかである。直していない箇所に、新しい指摘を出さない。
6. **往復を数える。** 1つの成果物(スライド仕様は章または節)について、不合格、修正、再検査の1巡を1回と数える。資料の表現規約が定める上限を超えたら、上の表の者に上げる。

上げられた者は、次のいずれかを選ぶ。

| 選択 | 内容 |
|---|---|
| 直し方を指示する | 具体的な直し方を示す |
| 受け入れる | 指摘を残したまま進める。検査の記録に残し、工程9の検査の報告に載せる |
| 上流に戻す | 原因が上流にあると判断し、上流の成果物を直す |
| 例外を認める | 合格条件から外す。資料の表現規約の例外として、理由とともに記録する |

合格条件そのものを、その場で書き換えることはしない。

## 報告の書式

### 調査依頼(`docs/stages/01-exploration.md`)

担当: 設計セッション。

調査は設計セッションや執筆のセッションから直接行わず、調査依頼として収集セッションに渡す。調査依頼は、Issueとして出す(Gitでの管理)。調査依頼は、探索の計画の末端の問いをそのまま渡す。「Aを裏付ける事実を探せ」のような、結論を含む聞き方をしない。

調査依頼の項目:

- 知りたいこと(1文の問い)
- 探索の計画のどの問いに対応するか
- 返す形式(素材台帳の書式)
- 見つからなかった場合は「見つからない」と返すこと
