### 素材台帳 `01-sources.yaml`(`docs/stages/01-exploration.md`)

全工程を通じて唯一の事実の置き場とする。スライド上の数値と出典の表記は、台帳から生成する。

```yaml
- id: F012
  statement: 2025年の国内市場規模は1.2兆円
  value: 1.2            # 本文から参照する数値。数値でない事実では省く
  unit: 兆円
  kind: fact
  source: 〇〇白書 2025年版
  locator: p.34 図表2-1  # ページ、URL、節など
  as_of: 2025-03        # 出典の日付または版
  metric: T-domestic-market-size   # 何の指標か。数値を持つ事実で必須。語彙表の語で書く。同じ指標の事実を見つけるために使う
  superseded_by: null    # 同じ指標の別の事実を使うと決めた場合に、使う事実のID。値があるものは、根拠に使えない
  quote: "国内市場は1兆2,000億円に達した"
  qualifiers: [2025年, 国内]   # この事実に付いている限定(条件、範囲、数量の幅、不確かさなど)
  origin: 〇〇省の統計    # 元をたどった情報源。別の資料が同じ情報源を引いている場合に、同じ値になる
  answers: [Q1.1]        # 探索の計画のどの問いに答えるか
  stance: {H1: supports, H2: contradicts}   # 仮説ごとに、supports(支持) / contradicts(否定) / neutral(どちらでもない)
  verified: true
```

事実の種類(`kind`)は次の通り。

| 種類 | 内容 | `verified: true` にする条件 | 根拠に使えるか |
|---|---|---|---|
| `fact` | 出典のある事実。ユーザーが提出した社内の資料にある事実を含む | `quote` が出典に実在し、`statement`、`value`、`unit`、`qualifiers` が `quote` と合っている | 使える |
| `derived` | 合計や比率などの計算値。`formula` に元の事実と計算式を書く | 元の事実が全て `verified: true` で、再計算の結果が一致する | 使える |
| `testimony` | ユーザーの証言。現場での経験、聞いた話など。誰の、何に基づく証言かを `source` に書く | ユーザーが内容を確認した | 使える。証言だけに頼る主張は、工程2でユーザーに示す |
| `image` | 画像の素材。下の「画像の素材」の節に定める | 同じ節に定める | 使える |
| `inference` | 推測 | 対象外 | 使えない |
| `opinion` | 意見 | 対象外 | 使えない |

`inference` と `opinion` をスライドに載せる場合は、推測または意見であることを文面に明示する。

出典のない事実を台帳に入れられるのは、`testimony` だけである。「広く知られている」ことを理由に、LLMが出典なしで事実を加えることは認めない。

使われない事実が台帳に残ることは問題としない。

### 満たす合格条件

成果物は、次の条件を満たす。括弧の中は、判定者である。「警告」とある条件は、合否にしない。

- `K01-06` 全ての `fact` に `source`、`locator`、`quote` がある(機械)。
- `K01-07` 全ての `derived` の計算式が、元の事実の値から再計算して一致する(機械)。
- `K01-08` `fact` の `quote` が出典に実在する。`quote` の切り取り方が、出典の前後にある条件、範囲、主体を落としていない。落としている場合は、`quote` を広げる(検査セッション。重大な検査)。確認できないものは `verified: false` のまま残す。
- `K01-09` `fact` の `value` と `unit` が、`quote` の中の数値と単位に一致する(機械。表記を正規化して照合する)。
- `K01-10` `fact` の `statement` が、`quote` の述べていることと合う。`qualifiers` が、`quote` にある条件、範囲、数量の幅、不確かさを漏れなく挙げている(検査セッション。重大な検査)。
- `K01-11` 数値を持つ全ての事実に `metric` があり、語彙表の語である(機械)。
- `K01-12` 同じ `metric` を持つ事実どうしで、時点と範囲が同じなのに値が違うものを挙げる。使わない事実に `superseded_by` を書くか、該当する問いの結果を `disputed` とする(機械が挙げ、設計セッションが決める)。
- `K01-13` 全ての `testimony` に、誰の、何に基づく証言かの記録がある(機械)。

### 削ってよいものと、削ってはいけないもの(`docs/writing.md`)

| 区分 | 例 | 扱い |
|---|---|---|
| 飾り | 非常に、様々な、重要な、まず前提として | 消す |
| 冗長な形 | することができる、という形になっている | 同じ意味の短い形にする |
| 限定 | 下の表 | 消さない |

限定にあたるもの:

| 種類 | 例 |
|---|---|
| 条件 | 〜の場合に限り、既定では、〜を有効にしたとき |
| 範囲 | 国内の、v2以降の、検証環境では |
| 数量の幅 | 最大で、少なくとも、約、平均で |
| 主体と対象 | 誰が、何が、何に対して |
| 例外 | ただし、〜を除く、原則として |
| 不確かさ | 〜のおそれがある、〜と見られる |
| 因果と順序を示すつなぎ | 〜のため、〜の後に |

限定を消すと、文は元の事実より強い主張、広い主張、または曖昧な主張に変わる。

素材台帳の事実には、その事実に付いている限定を `qualifiers` として記録する(工程1)。

### 不合格のときの手順(`docs/rework.md`)

1. **検査が不合格を返す。** 落ちた条件、該当する箇所、理由を添える。検査セッションの指摘には、根拠にした箇所の引用を必須とする。
2. **書いたセッションが、直すか、異議を唱えるかを選ぶ。**
3. **異議を唱える場合は、理由を添えて裁定を求める。** 裁く者は上の表による。裁定の結果は、検査の記録に残す。
4. **直す場合は、原因のある成果物を直す。** 原因が自分の成果物にあれば直す。上流にあれば、Issueを立てて上流に戻し、自分の成果物は保留にする。
5. **検査し直す。**
   - 機械的な検査は、全て再実行する。
   - 検査セッションの検査は、落ちた条件と、直した箇所に依存する条件に限る。新しく起こした検査セッションに、前回の指摘を渡す。確かめるのは、指摘が解消したかと、直したことで新しい問題が生じていないかである。直していない箇所に、新しい指摘を出さない。
6. **往復を数える。** 1つの成果物(スライド仕様は章または節)について、不合格、修正、再検査の1巡を1回と数える。資料の表現規約が定める上限を超えたら、上の表の者に上げる。

上げられた者は、次のいずれかを選ぶ。

| 選択 | 内容 |
|---|---|
| 直し方を指示する | 具体的な直し方を示す |
| 受け入れる | 指摘を残したまま進める。検査の記録に残し、工程9の検査の報告に載せる |
| 上流に戻す | 原因が上流にあると判断し、上流の成果物を直す |
| 例外を認める | 合格条件から外す。資料の表現規約の例外として、理由とともに記録する |

合格条件そのものを、その場で書き換えることはしない。

### 画像の素材(`docs/stages/01-exploration.md`)

スクリーンショット、写真、文書の抜粋、他の資料から引用した図は、画像の素材として素材台帳に登録する。画像をLLMに生成させて、実物として載せることは認めない。

```yaml
- id: A003
  kind: image
  file: assets/order-screen.png
  statement: 注文の入力画面
  source: 受注管理システム          # 何を写したものか。引用した図では、引用元
  version: "4.2"                    # 対象の版
  captured_at: 2026-11-10           # 取得した日
  environment: 検証環境             # 取得した環境
  regions:                          # 画像の中の要素と、その位置
    - id: due-date-field
      element: E-ui-due-date
      label: 納期の欄
      box: [0.30, 0.42, 0.25, 0.05]
      box_origin: recorded
    - id: save-button
      element: E-ui-save            # 仕組みの定義の要素。対応するものがある場合
      label: 保存ボタン
      box: [0.82, 0.90, 0.10, 0.05] # 画像の幅と高さに対する割合(左、上、幅、高さ)
      box_origin: recorded          # recorded(取得と同時に機械的に記録) / user(ユーザーが指定) / estimated(LLMが推定)
  masked: [顧客名の列]               # 隠した箇所
  verified: true
```

隠す作業は、収集セッションが画像そのものを加工して行う。加工する前の画像は、資料のリポジトリに置かない。画像を差し替えた場合にやり直す検査は、不合格と修正の手順の表による。

画像の中の位置は、レイアウトではなく、画像に付属する事実として扱う。位置を書くのは画像の素材の `regions` だけである。スライド仕様は、位置ではなく `regions` の `id` を参照する。

位置の出どころの信頼の順位は、`recorded`、`user`、`estimated` の順とする。`estimated` の位置は、注釈を描いた後に確かめる(工程7)。

`verified: true` にする条件は、下の合格条件の「画像の素材」の全てである。

### 調査依頼(`docs/stages/01-exploration.md`)

担当: 設計セッション。

調査は設計セッションや執筆のセッションから直接行わず、調査依頼として収集セッションに渡す。調査依頼は、Issueとして出す(Gitでの管理)。調査依頼は、探索の計画の末端の問いをそのまま渡す。「Aを裏付ける事実を探せ」のような、結論を含む聞き方をしない。

調査依頼の項目:

- 知りたいこと(1文の問い)
- 探索の計画のどの問いに対応するか
- 返す形式(素材台帳の書式)
- 見つからなかった場合は「見つからない」と返すこと

### 管理の方法(`docs/git.md`)

資料ごとの成果物を、Gitのリポジトリで管理する。

| ソフトウェア開発 | スライド作成 |
|---|---|
| コミット前の自動検査 | 機械的な検査 |
| コードレビュー | 検査セッションによる検査 |
| 変更の受け入れ | PMによる受け入れ、ユーザーの承認 |
| Issue | 指摘、調査依頼、検査で残った問題、描画の実装への要望 |
| 機能ごとのブランチ | 章や節ごとの執筆 |
| 変更の差分 | 上流を直したとき、下流のどれが古くなったかの判定 |
| ビルドの生成物は管理しない | PPTXは管理の対象から外す |

- ユーザーの承認は、タグまたは状態の記録として残す。
- ユーザーにはYAMLの差分を読ませない。直す前と後のスライドを見せる。
- プルリクエストとCIは必須としない。複数人で1つの資料を作る場合の選択肢とする。
