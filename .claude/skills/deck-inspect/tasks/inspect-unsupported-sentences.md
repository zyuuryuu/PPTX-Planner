## 読まないもの

入力に挙げたもの以外を読まない。このファイルと、スキルの「守ること」は読む。正本の文書(`docs/`)は開かない。要る箇所は、このファイルに写してある。
`restricted/inspect-unsupported-sentences/views/` にある入力は、機械が元のファイルから作った写しである。元のファイルを開かない。
入力にないファイルを、Gitの履歴からも、スクリプトからも取り出さない。
読めないファイルに当たったら、回避しない。作業票の入力で足りないと報告して終える。
人の許可を待つ表示が出る命令を使わない。人が見ていないので、表示が出ると止まる。ファイルの読み書きには、シェルの命令ではなく、ファイルを読む道具と書く道具を使う。

ファイルをまるごと渡す入力は、次の定めによる。

### 検査セッションが判断するもの(`docs/writing.md`)

| 検査 | 方法 |
|---|---|
| 裏付けのない文 | スライド仕様と、そのスライドが使う事実だけを渡す。文を1つずつ、事実に裏付けられているかを判定する。「多くの企業が」「近年」のような根拠のない一般化も対象とする |
| 限定の残存 | スライドが使う事実の `qualifiers` が、全て、文かスライドの `qualifiers` に残っているかを照合する |
| 削る検査 | 文ごとに、消しても意味が変わらない語を全て挙げる。挙がった語のそれぞれについて、消すと主張が事実より強く、広く、または曖昧になるかを確かめる。ならないものだけを消す。消した後も、文として読めること |
| 重複の検査 | 同じスライドの中で、題、要点、説明、中身が同じことを繰り返していないか |
| 言い直しの検査 | 中身(型のデータと説明)が、題と要点の言い直しだけで、新しい情報を足していないスライドを挙げる。挙がったスライドは、前後のスライドに統合する候補として、設計セッションに渡す |
| 主体の検査 | 仕組みを述べる文で、動作の主体が書かれているか |
| 読み戻し | 経緯を知らない検査セッションにスライドの文だけを読ませ、意味を完全な文で書き直させる。別の検査セッションが、素材台帳の事実と比べ、条件の脱落や主体の違いがないかを確かめる。対象は、仕組みの記述のスライドと、`qualifiers` を持つ事実を使うスライドとする |

検査に落ちた後の手順と、往復の上限は、不合格と修正の手順による。

## 手順

この作業では、「守ること」の表より、入力の制限が優先する。

### 検査セッションの手順(`docs/checks.md`)

担当: 検査セッション。

全ての検査に共通の手順である。

1. 作業票が挙げる検査の条件の文を、対象に1件ずつ当てる。条件ごと、対象ごとに判定し、まとめて判定しない。
2. 条件を満たすと言い切れなければ、不合格とする。
3. 合格にも、判定の根拠にした箇所を引用する。不合格に添えるものは、不合格と修正の手順の「不合格のときの手順」の1による。
4. 直し方を提案しない。対象を直さないことは、体制とセッションの「セッションの分離」と、不合格と修正の手順の「原則」による。
5. 結果を、検査の記録に書く。書式は、不合格と修正の手順の「検査の記録」に定める。

### 重大な検査(`docs/checks.md`)

検査セッションの判定には見逃しがある。見逃したものが外に出ると実害が大きい検査を、重大な検査として指定し、2段で行う。

重大な検査は、台帳の `critical` で指定する。

- 重大な検査は、別のセッションで2回行う。2回目は、1回目と別のモデルで行う。モデルが違うと、見落とす箇所が違うためである。
- 2回の結果が食い違ったものは、設計の時期はユーザーが、製造の時期は設計セッションが見て決める。設計セッションが決められないものと、設計セッションが書いた成果物についてのものは、ユーザーに上げる。
- 工程9の抜き取りで誤りが見つかった場合は、その誤りを拾うはずだった重大な検査を、同じ章の全てのスライドでやり直す。見つかった割合が高い場合は、全ての章に広げる。割合の目安は、資料の表現規約に置く。

## 成果物

- `checks/`(書式は、このファイルの「検査の記録」に定める)

成果物は、`restricted/inspect-unsupported-sentences/results/` の下に、上の名前のまま書く。手順が示す置き場も、その下に読み替える。資料のディレクトリには書かない。
書いたら、作業のブランチにコミットして、プッシュする。ブランチが先に進んでいたら、取得してマージしてからプッシュする。強制のプッシュをしない。ほかのブランチに切り替えない。
章を対象にする作業票では、置き場が `restricted/inspect-unsupported-sentences-<章のID>/` になる。入力と成果物の置き場は、作業票に従う。

### 検査の記録(`docs/rework.md`)

検査1回につき、1つのファイルを `checks/` に置く。ファイル名は「作業のid--対象--回.yaml」とする。

- 対象は、章ごとに行う検査では章のID、そのほかでは `all` と書く。
- 回は、同じ作業と対象について検査した回数で、1から数える。再検査は新しいファイルに書く。前の回のファイルは書き換えない。

```yaml
# checks/inspect-sources--all--1.yaml
task: inspect-sources        # 工程表の作業
target: 01-sources.yaml      # 対象
commit: 3f2a9c1              # 対象の版
round: 1                     # 何回目か
model: claude-sonnet-5-5     # 判定したモデル
results:
  - check: K01-14            # 検査の台帳のID
    item: F015               # 対象の中のどれか
    verdict: fail            # pass / fail
    quote: "市場規模は約1.5倍"
    reason: 出典は「2019年比で1.4倍」とあり、値が合わない
  - check: K01-14
    item: F016
    verdict: pass
    quote: "継続率は業界平均より15ポイント高い"
```

- 条件ごと、対象の中の1件ごとに、1行を書く。対象の全体に当てる条件では、`item` を書かない。
- `quote` は、判定の根拠にした箇所の引用である。合格の行にも書く。
- `reason` は、不合格の行に書く。条件のどの部分に反するかを書く。
- 警告の検査(台帳の `level` が `warning`)も、同じ形で書く。条件を満たさなければ `fail` と書く。合否にしないことは、台帳が決める。
- 比べる作業は、`quote` に元の成果物の箇所を引用し、`reason` に、独立に書いた答えの箇所と、食い違いを書く。
- 機械的な検査の記録は、`model` を持たない。
