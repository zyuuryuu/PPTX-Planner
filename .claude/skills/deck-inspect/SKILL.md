# 検査セッション

作業票が指す作業のファイルを1つだけ読む。ほかの作業のファイルを読まない。

道具 `tools/build_skills.py` が作ったファイルである。直接は直さない。正本は、工程表 `docs/tasks.yaml`、検査の台帳 `docs/checks.yaml`、`docs/` の文書である。直すときは、正本を直して、道具を実行する。

## 守ること

### セッションの分離(`docs/organization.md`)

| セッション | 読むもの | してはいけないこと |
|---|---|---|
| 収集 | 調査依頼、外部の資料 | 主張、題、要点を書くこと、仮説の一覧を読むこと |
| 執筆 | 承認済みの上流の成果物 | Web検索や資料の直接の読み込み、台帳にない事実の記述 |
| 検査 | 検査対象の成果物と、その上流の成果物 | 検査対象を自分で直すこと |
| 読み手の役 | ブリーフの読み手の情報と、ビルドした実物 | 設計の成果物を読むこと、スライドを直すこと |

読み手の役のセッションは、工程7の章の受け入れと、工程8の結合テストで、PMが起こす。実行のたびに新しく起こす。

検査は、機械の検査を先に行う。検査セッションは、機械の検査に通ったものを検査する。

分ける理由:

- 執筆中のLLMは、文を完成させるために必要な事実を補ってしまう。事実を台帳のIDでしか参照できなくすれば、補う余地がなくなる。
- 生の資料が執筆の文脈に入らないため、読み込み量が抑えられる。
- 書いた本人による検査は、自分の誤りを見逃しやすい。

分離だけでは、収集セッション自身の捏造は防げない。そのため素材台帳に引用箇所を記録させ、検査セッションが出典と突き合わせる。

### 原則(`docs/rework.md`)

1. 直すのは、その成果物を書いたセッションである。検査した側は直さない。
2. 原因が上流にある場合は、その場で辻褄を合わせない。上流に戻す。
3. 検査の指摘に、異を唱える経路を持つ。検査セッションの指摘には誤検出がある。
4. 検査し直すのは、落ちた条件と、直した箇所に依存する条件に限る。
5. 往復に上限を持つ。超えたら人が決める。
6. 合格も不合格も、記録に残す。記録は、検査した側が書く。

### 検査と記録を守る(`docs/rework.md`)

検査で品質を守る以上、検査そのものと、その記録が書き換えられないことが前提になる。

- 検査のコマンド、辞書、検査の記録、状態の記録、上流の成果物は、執筆のセッションの作業の枝で変更できない。変更が含まれる場合は、受け入れを拒む。
- 受け入れる側は、執筆のセッションの作業の枝にある検査のコマンドを使わない。受け入れ済みの本流にある検査のコマンドと辞書で、自分で実行する。
- ユーザーが承認した成果物は、承認のときにタグを付ける。タグを付ける担当: PM。承認の後に内容が変わった成果物は、検査のコマンドがタグとの差分から機械的に挙げ、承認を取り直すまで、下流の工程の開始を止める。設計セッションが、検査を通すために承認済みの成果物を直すことを、これで拾う。
- 検査を通すための書き換えや、検査の回避が見つかった場合は、PMまたは設計セッションが、変更を取り消し、そのセッションを新しいセッションに替える。事実をIssueに記録する。

### 不合格のときの手順(`docs/rework.md`)

1. **検査が不合格を返す。** 落ちた条件、該当する箇所、理由を添える。検査セッションの指摘には、根拠にした箇所の引用を必須とする。
2. **書いたセッションが、直すか、異議を唱えるかを選ぶ。**
3. **異議を唱える場合は、理由を添えて裁定を求める。** 裁く者は上の表による。裁定の結果は、検査の記録に残す。
4. **直す場合は、原因のある成果物を直す。** 原因が自分の成果物にあれば直す。上流にあれば、Issueを立てて上流に戻し、自分の成果物は保留にする。
5. **検査し直す。**
   - 機械的な検査は、全て再実行する。
   - 検査セッションの検査は、落ちた条件と、直した箇所に依存する条件に限る。新しく起こした検査セッションに、前回の指摘を渡す。確かめるのは、指摘が解消したかと、直したことで新しい問題が生じていないかである。直していない箇所に、新しい指摘を出さない。
6. **往復を数える。** 1つの成果物(スライド仕様は章または節)について、不合格、修正、再検査の1巡を1回と数える。資料の表現規約が定める上限を超えたら、上の表の者に上げる。

上げられた者は、次のいずれかを選ぶ。

| 選択 | 内容 |
|---|---|
| 直し方を指示する | 具体的な直し方を示す |
| 受け入れる | 指摘を残したまま進める。検査の記録に残し、工程9の検査の報告に載せる |
| 上流に戻す | 原因が上流にあると判断し、上流の成果物を直す |
| 例外を認める | 合格条件から外す。資料の表現規約の例外として、理由とともに記録する |

合格条件そのものを、その場で書き換えることはしない。

### 警告(`docs/rework.md`)

合否にしない指摘を、警告と呼ぶ。警告は検査の記録に残す。発生した工程の最終の承認の際に、承認する者に示し、直すか、受け入れるかを記録する。受け入れた警告は、工程9の検査の報告に載せる。

### 記録(`docs/rework.md`)

| 記録 | 置き場 | 内容 | 書く者 |
|---|---|---|---|
| 状態の記録 | `status.yaml` | 成果物ごとの状態(作成中、保留、検査済み、承認済み、無効)、承認した版、往復の回数 | 検査のコマンド。ユーザーの承認は、Gitのタグとして残し、検査のコマンドがタグから写す。章の受け入れは、PMが書く |
| 検査の記録 | `checks/` | 検査ごとに、対象、条件、結果、判定者、指摘、裁定、前提にした上流の項目とその時点の内容 | 機械的な検査は、検査のコマンド。検査セッションの検査は、その検査セッション |
| 資料の表現規約 | `style.yaml` | [表現規約](../../../docs/style-rules.md)が定める内容。規則、上限と目安の値、例外 | 設計セッション |
| 結合テストの実行の記録 | `runs/` | 場面ごと、スライドごとの状態とエラー | 読み手の役のセッション |
| 集計の記録 | `metrics.yaml` | 工程9が定める集計 | 検査のコマンド |

資料の表現規約は、工程0で、資料の型の定義の `limits` と個人の表現規約を写して作る。工程6で、資料に共通の見た目の規則を加える。表現の対応表(`06-patterns.yaml`)と語彙表(`terms.yaml`)は別のファイルに置き、資料の表現規約から参照する。

成果物を書いたセッションは、その成果物についての検査の記録を書かない。

### 上流が変わったとき(`docs/rework.md`)

検査に通ったとき、その成果物が前提にした上流の項目と、その時点の内容を、検査の記録に残す。記録した項目のいずれかが後で変わった場合は、その合格を無効とする。判定の単位は、ファイルではなく項目とする。

- 機械的な検査は、再実行すれば上流の変化を拾える。
- 検査セッションによる合格は、上流が変わっても失敗しない。そのため、この記録で拾う。
- 無効になった成果物だけ、検査セッションの検査をやり直す。変わっていないものは再検査しない。
- ユーザーが承認したもの(`answer`、要約の文、主張、章と節とスライドの題と要点、見せ方、型の見本、語彙表)が変わる場合は、ユーザーの承認を取り直す。
- 設計の時期は設計セッションが、製造の時期はPMが、無効になった成果物を挙げる。挙げる元になるのは、検査の記録にある前提の項目である。前提の項目は、検査のコマンドが、成果物の中の参照(事実のID、主張のID、スライドのIDなど)から機械的に導く。検査セッションが書き足すことはできるが、機械が導いた項目を減らすことはできない。

スライド、事実、主張などのIDは、一度付けたら変えない。順序や章を変えても、IDは変えない。
