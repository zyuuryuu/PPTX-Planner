## 守ること

### 設計セッション(`docs/organization.md`)

設計の時期を通して、ユーザーの相手をする1つのセッション。工程0から6の成果物のうち、素材台帳、画像の素材、仕組みの定義を除くものを書く。この3つは収集セッションが書く。事実の収集と検査は、別のセッションに任せる。

設計の途中の判断は、設計の判断の記録 `decisions.md` に残す。ソフトウェア開発の設計判断の記録(ADR)と同じ形をとる。

- 状況(何を決める必要があったか。関係する事実)
- 決めたこと
- 却下した案と、その理由
- 受け入れた影響(証拠との食い違い、残る危険など)
- 決めた人と日付

記録するのは、案を却下したとき、証拠と食い違う結論を維持したとき、表現規約の規則の矛盾をユーザーが裁いたとき、および各工程の定義が記録を求めるときである。

製造の時期に入っても終了させず、設計担当として残す。製造中に設計の疑問や見直しが出たら、PMとユーザーはこのセッションに戻る。発表の後の反応は、ユーザーが伝え、このセッションが記録する([工程9](../../../docs/stages/09-finish.md))。

### ユーザーとのやり取り(`docs/organization.md`)

ユーザーの負担を抑えるため、次を守る。

- 一度に求める判断は1つにする。
- 白紙の質問ではなく、推奨と代案を示して選んでもらう。
- 全体の流れを先に見せ、その後は章ごとに進める。
- 検査に通ったものは見せず、判断が要るものだけを出す。
- 承認済みのものを再び聞かない。上流の変更で見直しが要るときは、変わった箇所だけを見せる。

### 原則(`docs/principles.md`)

1. **正本は仕様で、PPTXは生成物である。** 修正は仕様に対して行い、PPTXは作り直す。LLMはPPTXの中身を読まない。PPTXから文字だけを機械的に抜き出して使うことは、これに含まない。
2. **全体で設計し、章ごとに書き、全体で検査する。** 1枚あたり数行で済む成果物は、資料全体を1つのセッションで扱う。分量の多いスライド仕様だけを章に分ける。
3. **下流の作業は、承認済みの成果物だけで進められるようにする。** 会話の履歴にしかない情報を残さない。
4. **収集、執筆、検査は別のセッションで行う。** 詳細は[体制とセッション](../../../docs/organization.md)。
5. **執筆は素材台帳にある事実だけを使う。** 台帳にない事実が必要になったら、書かずに調査依頼を出す。
6. **人はスライドの形で確認する。** 章立て設計以降は、未完成でもビルドして見られるようにする。
7. **合格条件を満たせないときは上流に戻る。** 合格条件のほうを書き換えて通すことはしない。
8. **機械で検査できるものは機械で検査する。**

### 原則(`docs/rework.md`)

1. 直すのは、その成果物を書いたセッションである。検査した側は直さない。
2. 原因が上流にある場合は、その場で辻褄を合わせない。上流に戻す。
3. 検査の指摘に、異を唱える経路を持つ。検査セッションの指摘には誤検出がある。
4. 検査し直すのは、落ちた条件と、直した箇所に依存する条件に限る。
5. 往復に上限を持つ。超えたら人が決める。
6. 合格も不合格も、記録に残す。記録は、検査した側が書く。

##### 工程6 表現設計の前文(`docs/stages/06-patterns.md`)

[目次に戻る](../../../docs/README.md)

資料全体の見た目を、スライドを量産する前に確定する。主張の種類と型の対応、要点の位置、資料に共通の規則、型の見本を決める。同じ種類の主張には同じ型を、違う種類の主張には違う型を使う。

形の選び方の根拠は、[形が伝える意味](../../../docs/visual-grammar.md)に定める。型の定義は、[型の定義](../../../docs/patterns.md)に定める。

##### 表現の対応表 `06-patterns.yaml`(`docs/stages/06-patterns.md`)

```yaml
- relation: trend          # 推移
  size: any                # 量の区分。any(問わない) / within(型の収容量以内) / over(収容量を超える)
  base: none               # 土台。none(なし) / image(画像の素材の上に描く)
  pattern: line-chart
- relation: list           # 並列の列挙
  size: within
  base: none
  pattern: plain-list
- relation: list
  size: over
  base: none
  pattern: table
```

量の区分(`size`)は、立証の設計の中身と型の収容量から、機械が決める。土台(`base`)は、立証の設計に書く。

##### 1. 主張の種類を集計する(`docs/stages/06-patterns.md`)

担当: 設計セッション。

全スライドの立証設計から、主張の種類と、項目の数などの量を集計する。

##### 2. 種類ごとに主な型を選ぶ(`docs/stages/06-patterns.md`)

担当: 設計セッション。

型の定義から、次を満たす型を選ぶ。

- その主張の種類に対応する。
- 型の `implies` が、その種類のスライドの `holds` に全て含まれる。
- スライドの `holds` の主な関係(先頭の項目)が、型の `expresses` に含まれる。

候補が複数ある場合は、伝えたい含意が強く出て、伝えたくない含意が出ないものを選ぶ。

##### 3. 収容量を超えるスライドを扱う(`docs/stages/06-patterns.md`)

担当: 設計セッション。

型の収容量を超えるスライドは、すぐに別の型へ切り替えない。次の順で対処する。

1. 中身を見直す。項目を分類の軸でまとめられないか、除去の検査で減らせないかを確かめる。直す場合は、工程5またはそれより前に戻る。
2. それでも超える場合に限り、型の `overflow_to` の型を使い、対応表に `size: over` の行を加える。

収容量を超えた場合の型は、主な型と、配色、題と要点の位置を揃える。

##### 要点の位置(`docs/stages/06-patterns.md`)

要点を置く位置を、型ごとに1つ決め、資料の中で揃える。認める位置は、次の3つである。

| 位置 | 識別子 | 使う場合 |
|---|---|---|
| 題の直下 | `below-title` | 基本。下の2つに当たらない場合 |
| 中身の下 | `below-body` | 中身を追った結果として、結論に至る場合 |
| 中身そのもの | `body` | 要点を中身として描く場合。別の行に繰り返さない |

型ごとの既定は、[型の定義](../../../docs/patterns.md)にある。資料で使う型と位置の対応を、資料の表現規約に置く。

```yaml
point_position:
  default: below-title
  line-chart: below-body
  cause-chain: below-body
  statement: body
```

要点のないスライドには、要点を描かない。「中身の下」の位置を認めるかどうかは、未確定である([未検証の前提と未決定の事項](../../../docs/open-items.md))。

##### 資料に共通の規則(`docs/stages/06-patterns.md`)

資料の表現規約に、次を加える。

| 規則 | 内容 |
|---|---|
| 文字の大きさの下限 | 本文、図の中の文字、注のそれぞれについて定める |
| 色の割り当て | 同じ対象は、全ての図で同じ色にする。割り当てた色を、別の対象に使わない。対象と色の対応を表にする |
| 強調の方法 | 注目させる点を示す色と、その使い方を1通りに決める。強調は、1枚に1か所までとする([形が伝える意味](../../../docs/visual-grammar.md)) |
| 矢印と図形の意味 | 矢印の種類ごとの意味、図形の形ごとの意味を1通りに決める |
| 流れの向き | 時間と因果を流す向きを、左から右、または上から下のどちらかに決める |
| 定位置 | 題、凡例、単位、出典、限定と出どころの脚注、注を置く位置を決める。要点の位置は、上の「要点の位置」で決める |
| 色相の数の上限 | 1枚で使う色相の数の上限を決める |
| 要約の形 | 要約の文だけにするか、根拠を短く添えるかを決める。既定は要約の文だけとする。読み手に求めることを要約に載せるかどうかも決める |
| 付帯情報 | 出力するファイルの作成者などの付帯情報に、何を入れるかを決める |

##### 5. 型の見本のスライド仕様を書く(`docs/stages/06-patterns.md`)

担当: 設計セッション。

資料で使う型ごとに、見本のスライドを1枚作る。その型を使うスライドのうち、量が最も多いものを選ぶ。文字が小さくなる、詰まるといった問題を、最も厳しい条件で確かめるためである。

見本の分だけ、スライド仕様を先に書く。見本にしたスライドの仕様は、工程7でそのまま使う([体制とセッション](../../../docs/organization.md))。

##### 成果物(`docs/stages/07-slide-spec.md`)

`07-slides/ch2.yaml`(章ごとのスライド仕様):

```yaml
- id: ch2-s1
  status: done               # done(書き終えた) / blocked(保留。Issueの番号を添える)
  title: △△領域の年ごとの市場規模               # 題
  point: △△の領域の市場規模は、5年続けて前の年を上回った   # 要点
  qualifiers: [国内]         # 限定
  provenance: cited          # 出どころ。ストーリーラインにある場合
  body:
    type: line-chart
    data: {...}
    highlight: series-target  # 強調する要素。立証設計の注目させる点に対応する
  text: 国内市場の{F040}を占めるまでに拡大した。集計の方法は「{ch2-s2}」に示す   # 数値は事実のID、別のスライドはスライドのIDで参照する
  sources: [F015, F016, F040]
  notes: 口頭で補う説明
```

`title`、`point`、`point_from`、`role`、`qualifiers`、`provenance` は、ストーリーラインの通りに写す。

`text`、`body.data`、`notes` の数値は直接書かず、事実のIDで参照する。ビルドの際に台帳の値に置き換える。`point` は、ストーリーラインを人が読めるように数値を直接書いてよい。その数値は、そのスライドの `sources` の事実と一致させる。別のスライドへの言及は、スライドのIDで書く。ビルドの際に、そのスライドの題に置き換える([文章の書き方](../../../docs/writing.md))。

要点は、ビルドが、資料の表現規約が型ごとに定める位置に1回だけ描く。`qualifiers` と `provenance` は、ビルドが、資料の型の定義の `annotation` が定める場所に描く。執筆のセッションは、これらを `text` や `body` に書き写さない。

画像の型のスライドでは、画像の素材と、注釈を付ける `regions` を参照する。位置は書かない。

```yaml
- id: ch5-s2
  status: done
  title: 納期の入力と保存
  point: 納期が空のまま保存すると、発注が止まる
  body:
    type: annotated-image-steps
    asset: A003
    crop: [due-date-field, save-button]   # この範囲が入るように切り抜く
    scenario: S-order-entry               # 番号は、場面の順から決まる
    captions:                             # 注釈の説明。スライドのノート(`notes`)とは別の項目
      due-date-field: 納期を入力する
      save-button: 保存を押す
  sources: [A003, F120]
```

型の見本の承認とあわせて、ユーザーが語彙表を承認する。判断が要る候補だけを先に示し、残りは一覧で示す。承認の後は、語彙表を凍結する。凍結の後は、「語の登録の手順」を経ない限り、語を足すことも変えることもできない。
