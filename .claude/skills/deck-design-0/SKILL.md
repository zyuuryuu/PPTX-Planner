## 守ること

### 設計セッション(`docs/organization.md`)

設計の時期を通して、ユーザーの相手をする1つのセッション。工程0から6の成果物のうち、素材台帳、画像の素材、仕組みの定義を除くものを書く。この3つは収集セッションが書く。事実の収集と検査は、別のセッションに任せる。

設計の途中の判断は、設計の判断の記録 `decisions.md` に残す。ソフトウェア開発の設計判断の記録(ADR)と同じ形をとる。

- 状況(何を決める必要があったか。関係する事実)
- 決めたこと
- 却下した案と、その理由
- 受け入れた影響(証拠との食い違い、残る危険など)
- 決めた人と日付

記録するのは、案を却下したとき、証拠と食い違う結論を維持したとき、表現規約の規則の矛盾をユーザーが裁いたとき、および各工程の定義が記録を求めるときである。

製造の時期に入っても終了させず、設計担当として残す。製造中に設計の疑問や見直しが出たら、PMとユーザーはこのセッションに戻る。発表の後の反応は、ユーザーが伝え、このセッションが記録する([工程9](../../../docs/stages/09-finish.md))。

### ユーザーとのやり取り(`docs/organization.md`)

ユーザーの負担を抑えるため、次を守る。

- 一度に求める判断は1つにする。
- 白紙の質問ではなく、推奨と代案を示して選んでもらう。
- 全体の流れを先に見せ、その後は章ごとに進める。
- 検査に通ったものは見せず、判断が要るものだけを出す。
- 承認済みのものを再び聞かない。上流の変更で見直しが要るときは、変わった箇所だけを見せる。

### 原則(`docs/principles.md`)

1. **正本は仕様で、PPTXは生成物である。** 修正は仕様に対して行い、PPTXは作り直す。LLMはPPTXの中身を読まない。PPTXから文字だけを機械的に抜き出して使うことは、これに含まない。
2. **全体で設計し、章ごとに書き、全体で検査する。** 1枚あたり数行で済む成果物は、資料全体を1つのセッションで扱う。分量の多いスライド仕様だけを章に分ける。
3. **下流の作業は、承認済みの成果物だけで進められるようにする。** 会話の履歴にしかない情報を残さない。
4. **収集、執筆、検査は別のセッションで行う。** 詳細は[体制とセッション](../../../docs/organization.md)。
5. **執筆は素材台帳にある事実だけを使う。** 台帳にない事実が必要になったら、書かずに調査依頼を出す。
6. **人はスライドの形で確認する。** 章立て設計以降は、未完成でもビルドして見られるようにする。
7. **合格条件を満たせないときは上流に戻る。** 合格条件のほうを書き換えて通すことはしない。
8. **機械で検査できるものは機械で検査する。**

### 原則(`docs/rework.md`)

1. 直すのは、その成果物を書いたセッションである。検査した側は直さない。
2. 原因が上流にある場合は、その場で辻褄を合わせない。上流に戻す。
3. 検査の指摘に、異を唱える経路を持つ。検査セッションの指摘には誤検出がある。
4. 検査し直すのは、落ちた条件と、直した箇所に依存する条件に限る。
5. 往復に上限を持つ。超えたら人が決める。
6. 合格も不合格も、記録に残す。記録は、検査した側が書く。

資料が答える問いを固定する。問いが決まらないと、探索の範囲が決まらない。

##### 成果物(`docs/stages/00-brief.md`)

`00-brief.md`(ブリーフ)。項目は次の通り。

| 項目 | 内容 |
|---|---|
| 資料の型 | [資料の型](../../../docs/deck-types.md)の定義から選ぶ。合う型がなければ、この資料用の定義を作る |
| 伝え方 | 口頭で説明する、配布して読ませる、のいずれか |
| 主な読み手 | 立場。1人、または1つの立場に定める |
| 副次的な読み手 | 主な読み手のほかに読む人と、その立場 |
| 読み手が既に知っていること | 資料で説明しなくてよい内容 |
| 読み手の立場と懸念 | 賛成、反対、中立のいずれか。気にしそうな点、反対しそうな点 |
| 目的 | 読み手の今の状態と、読んだ後の状態。読んだ人に何を決めて、あるいは何をしてほしいか |
| 答えるべき問い | 1文 |
| 扱わない範囲 | この資料で答えないこと |
| 使われる場面 | 会議で映す、事前に配る、質疑がある、など |
| 書き手の立場 | 読み手から見た書き手(部下、外部の業者、専門家など) |
| 制約 | 枚数の目安、発表時間、テンプレート、言語、文体、期限。枚数の数え方は、[語彙と区分](../../../docs/vocabulary.md)による |
| 外に出せない情報 | 資料に載せてはいけない名前や情報(顧客の名前、個人の名前、社内だけの名称など)。写り込みの検査の材料にする |
| 手元の資料 | 一覧 |
| 型ごとの追加の項目 | 資料の型の定義が定める追加の質問(`brief_questions`)への答え |

各項目には、状態を付ける。

| 状態 | 意味 |
|---|---|
| 確定 | ユーザーが答えた、または推定をユーザーが確認した |
| 推定 | 設計セッションが依頼文や手元の資料から読み取った。ユーザーは未確認 |
| 未定 | まだ決まっていない。誰がいつ決めるかを添える |

この段階では結論を書かない。結論は工程2で決まる。ユーザーが既に持っている結論は、仮説として工程1の仮説の一覧に書く。

##### 受け入れの問い(`docs/stages/00-brief.md`)

ブリーフの項目は、工程9で、出来上がった資料を受け入れるかどうかを判断する基準になる。次の問いで、最後に判断する。

| ブリーフの項目 | 受け入れの問い |
|---|---|
| 目的 | 読み終えた読み手は、求めた判断や行動に進めるか |
| 答えるべき問い | 資料の結論は、問いへの答えになっているか |
| 読み手の懸念 | 懸念の1つ1つに、答えがあるか |
| 扱わない範囲 | 範囲の外の内容が入っていないか |
| 制約 | 枚数、時間、テンプレート、期限を守っているか |

##### 1. ブリーフを書く(`docs/stages/00-brief.md`)

担当: 設計セッション。

1. ユーザーの最初の依頼文と手元の資料から読み取れる項目を埋め、状態を推定とする。
2. 推定の項目を、ユーザーに確認する。
3. 残りの項目を、1つずつ聞く。選択肢があるものは選択肢を示す。
4. 答えるべき問いは、聞かずに案を出す。ほかの項目の答えをもとに問いの文を2つか3つ作り、ユーザーが選ぶか直す。
5. 資料の型の定義が定める追加の質問(`brief_questions`)を聞く。

分からない項目は、推測で確定にせず、未定として記録する。

##### 3. 受け入れの問いを示す(`docs/stages/00-brief.md`)

担当: 設計セッション。

ブリーフの承認を求めるときに、[受け入れの問い](../../../docs/stages/00-brief.md#受け入れの問い)で最後に判断することを、ユーザーに示す。この資料に固有の受け入れの条件があれば、受け入れの問いに加える。

##### 後から変える場合(`docs/stages/00-brief.md`)

探索や主張の整理の結果、問いの立て方が違っていたと分かることがある。その場合はブリーフを直し、ユーザーの承認を取り直す。波及する範囲は[不合格と修正の手順](../../../docs/rework.md)に定める。

#### 検査

##### 満たす合格条件

成果物は、次の条件を満たす。括弧の中は、判定者である。「警告」とある条件は、合否にしない。

- `K00-01` 全ての項目が、確定または未定である。推定のまま残る項目がない(機械)。
- `K00-02` 主な読み手、目的、答えるべき問いが確定である。この3つは未定を認めない(機械)。
- `K00-03` 答えるべき問いが1つである(検査セッション)。
- `K00-04` 答えるべき問いの、答えの形が決まっている。はいかいいえ、どれを選ぶか、どれだけか、どうやるか、のいずれかである(検査セッション)。
- `K00-05` 答えるべき問いの答えが、目的に書いた行動につながる(検査セッション)。
- `K00-06` 検査セッションがブリーフだけを読んで、「誰に、何のために、何の問いに答える資料か」を要約する。その要約が自分の意図と合っている(ユーザー)。
- `K00-08` 「外に出せない情報」が確定である。画像を使う資料では、未定を認めない(機械)。
- `K00-09` ブリーフの内容に同意する(ユーザー)。
