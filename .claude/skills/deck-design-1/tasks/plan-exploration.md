## 手順

### 工程1 探索の前文(`docs/stages/01-exploration.md`)

問いに答えるための事実を集める。収集の手段(Web検索、資料の読み込み、ユーザーへの聞き取り)は、この文書では定めない。定めるのは、何を調べるか、いつ終えるか、集めた結果が満たす条件である。

仮の結論に合う事実だけを集めることを防ぐため、次の3つを行う。

- 探索の範囲を、仮の結論ではなく問いから決める。
- 収集セッションに、仮説を見せない。
- 対立する仮説を置き、それぞれを支持する事実と否定する事実を記録する。

### 探索の計画 `01-plan.yaml`(`docs/stages/01-exploration.md`)

ブリーフの問いを、小さな問いの木に分解したもの。

```yaml
- id: Q1
  question: △△の領域の市場は今後も伸びるか
  parent: null
  axis: 市場、自社、採算       # この問いを子に分けた基準。末端の問いでは省く
- id: Q1.1
  question: △△の領域の市場規模は、過去5年でどう変わったか
  parent: Q1
  evidence_type: 統計          # 答えに必要な証拠の種類。末端の問いで必須
  priority: high               # high(答えによって結論が変わる) / low(結論を補う)
  perspective: null            # 資料の型の定義が定める観点に対応する場合は、その名前
  result: null                 # 収集の後に書く。answered / partial / not-found / disputed
```

### 問いの分解(`docs/stages/01-exploration.md`)

担当: 設計セッション。

1. [資料の型](../../../../docs/deck-types.md)の定義が定める問いの最初の分解(`decomposition`)を出発点にする。問いに合わなければ変えてよい。
2. 枝分かれのたびに、分けた基準を `axis` に書く。
3. 何を見れば答えが分かるかを言えるところまで分解する。言えたら、それを `evidence_type` に書いて末端とする。
4. 資料の型の定義が定める観点(`perspectives`)を、全て問いとして含める。
5. 末端の問いに重要度を付ける。対立する仮説の間で予想される答えが分かれる問いを `high` とする。どの仮説でも答えが同じになる問いは `low` とする。

## 検査

### 満たす合格条件

成果物は、次の条件を満たす。括弧の中は、判定者である。「警告」とある条件は、合否にしない。

- `K01-01` 全ての枝分かれに `axis` がある。全ての末端の問いに `evidence_type` と `priority` がある(機械)。
- `K01-02` 資料の型の定義が定める観点が、全て問いに含まれる(機械)。
- `K01-03` 枝分かれが、分類の軸の検査を通る(検査セッション)。 [定義](../../../../docs/checks.md#意味の検査)
- `K01-04` 末端の問いが全て答えられたら、ブリーフの問いに答えられる(検査セッション)。
- `K01-05` 計画の内容に同意する(ユーザー)。
