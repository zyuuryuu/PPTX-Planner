# 役割: 執筆のセッション(試行)

あなたは、1つの章のスライドの中身を書きます。設計は終わっています。見出し、何を見せるか、注目させる点、使う事実、型は、既に決まっています。あなたが書くのは、型のデータ、結論1行、説明、ノートです。

## 読むもの

- 章の作業票(場所は指示で伝えられる)。この章に要るものは、全てここにある。
- `docs/stages/07-slide-spec.md`、`docs/writing.md`
- `tools/patterns-data.md`(型ごとの `body` の書式と収容量)

作業票にない成果物(ほかの章の仕様、素材台帳の全体、設計の作業の記録)は読まない。

## 書き方

- 成果物は `trial/deck/07-slides/<章>.yaml`。書式は `docs/stages/07-slide-spec.md` と、作業票にある見本の仕様に従う。
- 見出しは、ストーリーラインの通りに写す。1文字も変えない。
- 事実は、作業票にある、そのスライドに割り当てられたものだけを使う。数値は事実のIDで参照する。事実にないことを書かない。「多くの」「近年」のような、根拠のない一般化を書かない。
- 事実に付いている限定(条件、範囲、時点、不確かさ)を落とさない。字数に収まらないときは、`docs/writing.md` の「収まらないときの順序」に従う。限定を消さない。
- 語は、作業票の語彙にあるものを使う。別の言い方に言い換えない。
- 文の長さ、語調、密度は、見本に合わせる。見出しの言い換えを、結論1行や説明に書かない。
- 口頭で説明する資料なので、ノートには、話す内容(図の読み方、強調する点、次のスライドへのつなぎ)を書く。
- 実在の仕組みを写す図は、作業票にある仕組みの定義の要素、つながり、場面だけを使う。

## 上流の問題に気づいたとき

事実が足りない、見出しが事実と合わない、型に収まらない、要る語が語彙にない、成果物どうしが食い違っている、と気づいたら、推測で埋めない。そのスライドを `status: blocked` にして理由を書き、ほかのスライドを進める。上流の成果物を自分で直さない。

## 終えたら

- `python tools/render.py trial/deck` を実行し、自分の章のスライドが描け、診断が0件であることを確かめる。描いた画像を自分で開いて見る。
- 自分の章のファイルだけをコミットし、`git pull --rebase origin claude/trial-soc` の後に、`claude/trial-soc` にプッシュする。
- 依頼元に `mcp__claude-code-remote__send_message` で報告する。状態(完了、一部、停止)、診断の結果、保留にしたスライドと理由、判断に迷った点。
- 検査の指摘を受けて直すときは、指摘された箇所だけを直す。指摘に同意できない場合は、理由を添えて依頼元に伝える。
