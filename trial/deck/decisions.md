# 設計の判断の記録

## D001 閉じる条件と上げる条件が公開資料で見つからないまま、探索を終える

- 状況: 探索の計画の high の問い Q3.1.1(誤検知として閉じてよい条件)と Q3.3.1(上に上げる条件)が、2回の収集(R3、R4、R6)で partial のまま。NIST SP 800-61 Rev.2/Rev.3 は、条件を組織の方針に委ねている(判断の材料としてリスク評価の要因を挙げる)。製品の公式文書は、閉じるときの分類を定めるが、製品ごとに定義が違う。終了の1つ目の条件(high が全て answered または disputed)を満たさない。
- 決めたこと: 「公開の標準は閉じる条件と上げる条件を定めておらず、組織が決める」ことを資料の前提として明記する。集まった判断の材料(リスク評価の要因、製品の分類など)から、閉じる・上げるの基準を組み立てる。組み立てた基準は、出典のある事実と分け、「案」であることが分かるように示す。依頼者の SOC の基準として使えるかは、依頼者が出来上がったものを見て決める。
- 却下した案: 依頼者の SOC の基準を聞き取って証言として加える(依頼者が選ばなかった)。調査を続ける(見つかる見込みが低い)。
- 受け入れた影響: 基準の部分は、出典で裏付けられた事実ではなく、設計の側が組み立てた案になる。立証の設計(工程5)で、案と事実を区別する見せ方が要る。
- 決めた人と日付: 依頼者、2026-11-23

## D002 資料の答えの流れとして、区別を3つにする案Aを採る

- 状況: 根の答えと仮説を比べた。依頼者の仮説 H1(まず誤検知かどうかの判定から入る。8割は誤検知)に対し、公開資料では、何から確かめるかの順序が出典で食い違い(NIST Rev.3 は起きたかの確認が先、民間の解説は優先順位付けが先)、8割に近い値はベンダーの調査の83%だけで誤検知と想定内の検知を分けていない。1つの実在のSOCの実測では侵害に至らなかった攻撃の試みが27%以上あり、誤検知でも想定内の検知でもない。誤検知に慣れることの危険を示す材料(Target の事案の推定、無視した経験の調査)がある。
- 決めたこと: 案A。アラートの根拠とログで、誤検知、想定内の検知、攻撃の疑い(侵害に至らなかった試みを含む)の3つに分け、次に影響の大きさで優先度を付ける。根拠をもって誤検知か想定内の検知と言えれば記録して閉じ、持ち時間の中で決められないとき、重要な資産や横展開の疑いがあるとき、迷うときは上げる。重大度が高いものは調べ終える前に上げる。条件: (1)上の割合と調査の数字は、スライドに出典(誰が、いつ、何を調べたか)を必ず載せる。(2)誤検知のパターンを教える部分は、3つの区分の1つとして残す。
- 却下した案: B(優先度付けを先にし、その後で区別する。民間の解説の順)。C(依頼者の仮説のまま、誤検知かどうかの2つで始める)。
- 受け入れた影響: どの仮説とも完全には一致しないため、主張の骨子の hypothesis は null とした。H1 の「区別から入る」は採り、「2つに分ける」と「8割は誤検知」は採らない。H1 を否定する事実(F404、F405、F501、F502、F503、F506、F312)は、3つの区分と、重大度の高いものを先に上げる手順に反映した。順序の根拠は出典で食い違うため、主張では「案」として示す。
- 決めた人と日付: 依頼者、2026-11-24
- 依頼者の発言(記録): 「攻撃だが失敗したもの」が27%以上というのは、自分の「8割」に混ざっていた気がする。誤検知と一緒に閉じていたものがあったかもしれない。

## D004 要約の文を、結論だけの短い2文にする

- 状況: `02-claims.md` は summary を「結論と理由を1文にまとめる」とし、1文であることを合格条件にする。結論、理由、上げる条件を1文に入れた案は、依頼者が「長すぎる。新人の頭に残らない」として差し戻した。研修資料で冒頭と最後に置く文は、新人に覚えさせる文である。
- 決めたこと: summary を「アラートは、誤検知、想定内の検知、攻撃の疑いの3つに分ける。根拠をもって誤検知か想定内と言えるものだけを記録して閉じ、迷ったら上げる。」とする。上げる条件、優先度の付け方、公開資料から組み立てた案であることは、中のスライドで示す。
- 却下した案: 結論と理由と条件を1文に入れた案(長すぎる)。2行に分けて見せる案(依頼者が「同じ」とした)。
- 受け入れた影響: 「1文である」の合格条件を満たさない(2文)。理由を含まない。資料の表現規約の例外として扱う。「迷ったら上げる」の根拠は標準ではない有志の手順書(F405)と、主張 C3 の案である。案であることは要約の文には書かず、中のスライドで示す。要約の文だけを読ませる検査と、summary の重大な検査は、この文では行っていない。
- 決めた人と日付: 依頼者、2026-11-24

## D005 章の message を、章扉に映せる1〜2行にする

- 状況: 依頼者が目次と章扉の資料を見て、第3章の扉の文が長すぎる(映しても誰も読まない)、「依頼者であるリーダーが同意し」は新人に見せる言葉ではない(新人から見ればリーダーなだけ)、第2章も少し長い、と指摘した。`03-chapters.md` の合格条件は、章の message が主張の限定を落とさないことを求め、限定を足した結果、文が長くなっていた。なお同文書は、完成形の章扉には message ではなく章の題と問いを載せるとしている。
- 決めたこと: ch2 と ch3 の message を1〜2行にする。数値や測定の対象、上げる条件、運用の中身は中のスライドで示す。限定を落とさないよう、短くするときは具体的な数値や条件を外し、言える範囲の広さを変えない書き方にする(例: 「27%以上、49%以上」を「多くを占めた」に、「1つのSOCの実測」は残す)。運用の出どころは「このSOCの運用」とする(新人に対しては講義を行うSOCの運用であり、依頼者の同意か既存の運用かの区別は台帳と主張に残る)。
- 却下した案: message は長いまま残し、章扉には別の短い文を載せる(章扉に載る文と章の主張が二重になり、`03-chapters.md` の確認用の章扉に合わない)。
- 受け入れた影響: message から具体的な数値が消え、「多くを占めた」は検査で広さを判定し直す必要がある。
