5 / 46 ・ ch2-s1 ・ 本編

アラートは、検知の仕組みが探すものを見つけたときの知らせで、本物の攻撃とは限らない

出典: Microsoft Learn(Microsoft Sentinel、Microsoft Defender for Endpoint の文書、2026年)、Yangら(USENIX Security 2024)。1つのSOCのネットワークの検知(Zeek)の2020年12月〜2022年7月のアラート約1,443万件を著者らが分類

  • F709: Microsoft Sentinel は、組織の全体からデータを集めた後、定期的に実行される脅威検知のルール(分析ルール)で、集めたデータに問い合わせて分析する。ルールは探しているものを見つけるとアラートを生成する。アラートは関わる実体(利用者、端末、アドレスなど)を含み、集約と相関によってインシデントにまとめられる
  • F619: Microsoft Defender for Endpoint では、脅威を検知するとアラートが作られ、同じ攻撃の手法や同じ攻撃者によるアラートはインシデントにまとめられる。検知の機能は端末の全ての操作を記録する監査やログの仕組みではなく、センサーには同じ事象の大量の繰り返しを間引く仕組みがある
  • F207: 実SOCの実測では、アラートのうち真の攻撃に関連するのは0.01%。攻撃の試み(侵害に至らなかった攻撃)が27%、正当な業務上の理由がある「良性のトリガー」が49%を占めた

仮置き

  • 主張の種類: entity-relation(要素の関係)
  • 見せるもの: 製品の例(Microsoft Sentinel)の3つのつながり: データソースがデータを集める、分析ルールが集めたデータに問い合わせる、ルールがアラートを生成する。図の下に1行で「1つのSOCのネットワークの検知の実測では、侵害に至った攻撃に関連するアラートは0.01%(ch2-s6で詳しく)」
  • 注目させる点: アラートは、ルールが探すものを見つけたときに出す知らせであること

6 / 46 ・ ch2-s2 ・ 本編

SIEMは、最も一般的にはルールで複数のログの記録値を照合し、重要なイベントを特定する

出典: NIST SP 800-92(2006年)。ルール以外の相関もある

  • F100: SIEMは、複数のログ源のデータを分析し、ログ項目間でイベントを相関させ、重要なイベントを特定して優先順位を付ける
  • F101: ログのイベント相関で最も一般的なのは、タイムスタンプ、IPアドレス、イベント種別などの記録値に基づいて複数のログ項目を照合するルールベース相関である

仮置き

  • 主張の種類: architecture(構成)
  • 見せるもの: ログの発生源がSIEMのサーバへログを送り(エージェントなしで発生源が送る場合の例)、サーバが全てのログ源のデータを分析して相関させ、重要と判断されたイベント(まだアラートではない)を特定する。サーバの中の注記に「相関で最も一般的なのはルール(ログ管理ソフトウェア一般の記述)」
  • 注目させる点: 複数のログをまとめて相関させるところ

7 / 46 ・ ch2-s3 ・ 本編

EDRは端末の振る舞いの記録を継続して集め、製品の例では脅威を検知するとアラートを作る

出典: 米国 OMB の覚書 M-22-01(2021年)、サウジアラビア国家サイバーセキュリティ庁(NCA)のEDR標準のひな形、Microsoft Learn(Microsoft Defender for Endpoint の文書、2026年)

  • F615: 米国 OMB の覚書 M-22-01 は、EDRを、端末のデータのリアルタイムで継続的な監視と収集に、ルールに基づく自動の対応と分析の機能を組み合わせたものと説明している
  • F618: Microsoft Defender for Endpoint は、プロセスの情報、ネットワークの活動、カーネルとメモリ管理の深い観測、利用者のログオンの活動、レジストリとファイルシステムの変更などの振る舞いのテレメトリを継続的に集め、6か月保存する
  • F619: Microsoft Defender for Endpoint では、脅威を検知するとアラートが作られ、同じ攻撃の手法や同じ攻撃者によるアラートはインシデントにまとめられる。検知の機能は端末の全ての操作を記録する監査やログの仕組みではなく、センサーには同じ事象の大量の繰り返しを間引く仕組みがある

仮置き

  • 主張の種類: architecture(構成)
  • 見せるもの: 2つの枠。左: EDRの要件の例(NCA)で、端末→エージェント→中央のデータベースと、記録を集める流れ。右: 製品の例(Microsoft Defender for Endpoint)で、製品がセンサーを持つことと、製品がアラートを作ること。右の枠の外に、製品が集める振る舞いのテレメトリの種類(プロセス、ネットワーク、ログオン、レジストリとファイルの変更)を一覧で添える。テレメトリと製品、アラートの間には矢印を描かず、「経路は出典にない」と注記する
  • 注目させる点: EDRは端末の振る舞いを継続して集め、製品は脅威を検知するとアラートを作ること(2つをつなぐ経路は示さない)

8 / 46 ・ ch2-s4 ・ 本編

アラートの詳細はOSのログで確かめることが多く、認証のログは通常、接続元と成否を残す

出典: NIST SP 800-92(2006年)。「しばしば」「通常は」の記述

  • F111: OSログは、特定のホストに関する不審な活動の特定と調査に最も役立つ。セキュリティソフトが不審な活動を見つけた後に、詳細を得るために参照されることが多い
  • F108: 認証サーバのログは、認証の試行ごとに、接続元、ユーザー名、成否、日時を記録する
  • F110: OSの監査記録は、認証の成功と失敗、ファイルアクセス、セキュリティポリシーの変更、アカウントの変更、権限の使用などのセキュリティ事象の情報を含む
  • F107: マルウェア対策ソフトの最も一般的な形であるウイルス対策ソフトは、通常、検出した全てのマルウェア、駆除の試み、隔離を記録する

仮置き

  • 主張の種類: list(並列の列挙)
  • 見せるもの: 2つのログと、そこから分かること: OSのログ(不審な活動の詳細。セキュリティソフトが見つけた後に参照されることが多い)、認証のログ(試行ごとの接続元、利用者、成否、日時を通常は記録する)
  • 注目させる点: アラートの詳細を確かめる先としてOSのログが多く使われること

9 / 46 ・ ch2-s5 ・ 本編

案として、ATT&CKの戦術で、アラートの活動が攻撃のどの段階かを表し、優先度の材料にする

出典: MITRE ATT&CK 公式サイト(v20.1、2026年)、NIST SP 800-61 Rev.3(2025年。インシデントのリスク評価の要因に「観測された活動の段階」)から組み立てた案

  • F114: MITRE ATT&CKは、実世界の観測に基づく攻撃者の戦術と技術の、世界中から利用できる知識ベースである
  • F116: ATT&CKでは、戦術は ATT&CK の技術または副技術の「なぜ」を表す
  • F125: ATT&CKでは、技術は、攻撃者が行動を実行して戦術上の目的を達成する「どのように」を表す
  • F610: NIST SP 800-61 Rev.3 は、インシデントのトリアージ、優先度付け、エスカレーション、上位への引き上げ、復旧を始める判断を、一連のリスク評価の要因に基づかせるよう推奨し、要因の例として、資産の重要度、機能への影響、データへの影響、観測された活動の段階、脅威主体の特徴、回復可能性を挙げている

仮置き

  • 主張の種類: structure(構造・階層)
  • 見せるもの: ATT&CKの戦術(なぜ)と技術(どのように)の2層と、架空のアラートの活動を1つの戦術に当てはめた例。当てはめた戦術から、優先度の要因「活動の段階」へ矢印(案)
  • 注目させる点: アラートの活動を戦術に当てはめると、攻撃のどの段階かを言えること

10 / 46 ・ ch2-s6 ・ 本編

1つのSOCの実測では、侵害に至った攻撃は0.01%、攻撃の試みは27%以上、想定内は49%以上

出典: Yangら(USENIX Security 2024)。1つのSOCのネットワークの検知(Zeek)の2020年12月〜2022年7月のアラート約1,443万件を著者らが分類。27%と49%は下限。分類できないものが約24%残る

  • F207: 実SOCの実測では、アラートのうち真の攻撃に関連するのは0.01%。攻撃の試み(侵害に至らなかった攻撃)が27%、正当な業務上の理由がある「良性のトリガー」が49%を占めた

仮置き

  • 主張の種類: composition(構成比)
  • 見せるもの: 1つのSOCのアラートの内訳を1本の帯で示す。侵害に至った攻撃0.01%、攻撃の試み27%以上、想定内の検知49%以上、分類できないもの約24%。27%と49%が下限であることを帯に書く
  • 注目させる点: 誤検知でも想定内でもない攻撃の試みの帯(27%以上)

11 / 46 ・ ch2-s7 ・ 本編

「8割が誤検知」に近い値は、調べた範囲ではベンダーの調査の自己申告(83%)だけだった

出典: Vectra AI の調査(2023年、解析者2,000人の回答)。「誤検知」の定義は示されていない

  • F204: 業界調査(ベンダーのVectra)では、解析者は受けるアラートの67%に対応できず、アラートの83%が誤検知で時間をかける価値がないと答えた
  • F220: Yangらは、良性のトリガーを『組織の環境における業務上正当で許容される挙動によって説明される、正しく発火したアラート』と定義し、一般的な『誤検知』(良性の挙動に対して誤って発火したアラート。悪い規則・エラー・誤設定による等)とは異なると述べる

仮置き

  • 主張の種類: statement(言い切り)
  • 見せるもの: 「83%」の値と、その条件の注記: ベンダーの調査、解析者の自己申告、「誤検知」の定義が示されていない。別の出典では誤検知と想定内の検知を分けて定義していることを1行で添える
  • 注目させる点: 調べた範囲で8割に近い値はこの自己申告の1つだけで、その「誤検知」の定義も示されていないこと

12 / 46 ・ ch2-s8 ・ 本編

誤検知の原因には、弱いルールや緩く書かれたルールなど、検知の条件の誤りがある

出典: NIST の文書(2003年、ネットワーク型の検知)、Alahmadiら(USENIX Security 2022、一部の解析者の認識)。原文の語は signature

  • F208: NISTの文書は、誤検知を『通常の非悪性の背景トラフィックで起きたアラート』と定義し、ネットワークIDSでの原因に、弱いシグネチャ、正当なネットワーク管理ツールのトラフィックを挙げる。誤検知率はネットワーク環境ごとに異なることがある
  • F214: SOC実務者の一部は、シグネチャが『緩く(広く)書かれている』ことで多くの誤検知が出ると述べた

仮置き

  • 主張の種類: causality(因果)
  • 見せるもの: 緩く書かれた(弱い)検知のルール→無害な通信にも合ってしまう→誤検知、のつながり。ルールの書き方の例を架空で添える
  • 注目させる点: 原因が検知の条件の側にあること

13 / 46 ・ ch2-s9 ・ 本編

1つのSOCの実測では、社内の脆弱性スキャンや外部の診断が想定内の検知を起こしていた

出典: Yangら(USENIX Security 2024)。1つのSOCのネットワークの検知(Zeek)の2020年12月〜2022年7月のアラート約1,443万件を著者らが分類

  • F215: 同SOCで、定期的な内部スキャン(脆弱性・設定不備の確認)は、悪性のスキャンと似た振る舞いをするが、アラートは無視してよい良性のトリガーの共通の原因の1つだった
  • F221: 同SOCで、第三者のセキュリティベンダーによる外部のペネトレーションテストと年次の監査に対応するアラートが約270万件あった。うち92%は2022年前半のLog4j関連だった

仮置き

  • 主張の種類: list(並列の列挙)
  • 見せるもの: 1つのSOCの実測で、想定内の検知を起こした業務上正当な活動の2例: 定期の内部の脆弱性スキャン、外部のベンダーによる診断(ペネトレーションテスト)
  • 注目させる点: どちらも業務上正当な活動で、ルールは正しく反応していること

15 / 46 ・ ch3-s1 ・ 本編

何から確かめるかは出典で食い違い、NISTは確認を、民間の解説は優先付けを判定より先に置く

出典: NIST SP 800-61 Rev.3(2025年。インシデントの報告の扱い)、CyberDefenders(SOC解析者の訓練事業者)の解説(2026年)。標準や公的文書ではない

  • F303: NIST SP 800-61r3 は、新しいインシデント報告に対して、インシデントが起きたかを確かめる予備的な確認を行い、その後に深刻度と対応の緊急度を見積もるとする
  • F312: 民間の SOC 向け解説は、アラートのトリアージを一つの判断ではなく、意図的な段階の連なりとし、各段階は前の段階の上に成り立ち、どの段階を飛ばしても誤分類の危険が増すとする

仮置き

  • 主張の種類: item-comparison(項目の比較)
  • 見せるもの: 2つの出典の段を横に並べる。NIST SP 800-61 Rev.3(インシデントの報告): 起きたかの確認→インシデントの重さの見積もり。民間の解説(アラート): 取り込み→分類→優先付け→調べる→本物か誤検知かの判定
  • 注目させる点: NISTは確認が最初で、民間の解説は判定より前に優先付けを置くこと

16 / 46 ・ ch3-s2 ・ 本編

閉じる・調べる・上げるの線は調べた公的な文書になく、この講義の線は案とこのSOCの運用である

  • F600: NIST SP 800-61 Rev.3 は、インシデントを宣言するかを決めるときに、分析した活動の既知の特徴と推定される特徴にインシデントの基準を当てはめ、既知の誤検知を考慮するよう推奨している
  • F610: NIST SP 800-61 Rev.3 は、インシデントのトリアージ、優先度付け、エスカレーション、上位への引き上げ、復旧を始める判断を、一連のリスク評価の要因に基づかせるよう推奨し、要因の例として、資産の重要度、機能への影響、データへの影響、観測された活動の段階、脅威主体の特徴、回復可能性を挙げている

仮置き

  • 主張の種類: list(並列の列挙)
  • 見せるもの: 上に「調べた公的な文書の線: なし」。下に、この講義の線の出どころ2つ: 案(公開資料の材料から組み立てたもの)、このSOCの運用(リーダーが決めたもの)
  • 注目させる点: 公的な文書の線がないこと

17 / 46 ・ ch3-s3 ・ 本編

案として、まず根拠とログで3つに分け、次に影響の大きさで優先度を付ける

出典: NIST SP 800-61 Rev.3(2025年)と、CyberDefenders(SOC解析者の訓練事業者)の解説(2026年)。標準や公的文書ではない。この2つの材料から組み立てた案

  • F303: NIST SP 800-61r3 は、新しいインシデント報告に対して、インシデントが起きたかを確かめる予備的な確認を行い、その後に深刻度と対応の緊急度を見積もるとする
  • F305: NIST SP 800-61r3 は、資源に限りがあるため、インシデントを到着順に扱わないとし、トリアージ・優先順位付け・エスカレーション・復旧開始の判断をリスク評価の要因の集合に基づけるとする。その集合は組織の必要と成熟度により単純なものから非常に複雑なものまである

仮置き

  • 主張の種類: process(手順)
  • 見せるもの: 2段の手順(案): 1. 根拠とログで3つに分ける 2. 影響の大きさで優先度を付ける
  • 注目させる点: 分けるのが先で、優先度が後であること

18 / 46 ・ ch3-s4 ・ 本編

案として、アラートを出したルールの条件と、含まれる利用者や端末を、元のログと照らす

出典: Microsoft Learn(Microsoft Sentinel の文書、2026年)の、ルールがアラートを出す仕組みから組み立てた案

  • F709: Microsoft Sentinel は、組織の全体からデータを集めた後、定期的に実行される脅威検知のルール(分析ルール)で、集めたデータに問い合わせて分析する。ルールは探しているものを見つけるとアラートを生成する。アラートは関わる実体(利用者、端末、アドレスなど)を含み、集約と相関によってインシデントにまとめられる
  • F710: Microsoft Sentinel の分析ルールで最も一般的な種類であるスケジュールされたルールは、一定の間隔で実行される Kusto の問い合わせで、定めた遡りの期間の生データを調べ、問い合わせの結果の件数がルールに設定した閾値を超えるとアラートを出す

仮置き

  • 主張の種類: process(手順)
  • 見せるもの: 根拠の確かめ方の2段(案): 1. アラートを出したルールの条件と、アラートに含まれる利用者や端末を読む 2. それを元のログと照らす
  • 注目させる点: 元のログと照らすところ

扱う量は出典で大きく違い、1つのSOCの実測は1日約13,764件、自己申告は1日平均4,484件

出典: Yangら(USENIX Security 2024。1つのSOCの2020年12月〜2022年7月。自動遮断の後に解析者が扱った件数)、Alahmadiら(USENIX Security 2022。SOC実務者20人の回答)、Vectra AI の調査(2023年、自己申告で1日平均4,484件)

  • F201: 同SOCの第2期で、自動遮断(BHR)で人手を介さず処理されたアラートは約44.9%(6,474,204件)あり、それを除いても解析者が処理するアラートは1日あたり約13,764件残った
  • F202: SOC実務者の調査(n=20)で、1日に受けるアラートが5,000件未満と答えたのは45%。10万件超を受ける回答者もいた
  • F203: 業界調査(ベンダーのVectra)では、SOCは1日平均4,484件のアラートを受け、解析者は1日に約2.7時間を手作業のトリアージに使う

  • 注目させる点: 調べ方と値が出典ごとに違うこと

上げるのが遅れる誤りも、上げすぎる誤りも、割合を測った公開の調査は見つからなかった

出典: Kerstenら(2025年)、Moosmannら(2026年)、Alahmadiら(USENIX Security 2022)。近い調査はあるが、どれも誤りの割合は測っていない

  • F508: Tier-1分析者の現地実験で、エスカレーションすべきアラート(Att)は、そうでないアラート(NAtt)より調査の操作数が平均で多く、したがって分析者はエスカレーションすべきアラートの分析に時間と認知の負担をかける可能性が高いとされる
  • F509: SOC分析者12人の事前調査で、不確かなときにチケットを作って引き継ぐと答えたのは33%にとどまり、同僚に相談する92%、自分で調べる71%と比べて少なかった
  • F510: 顧客に報告する立場のMSSPの分析者は、能力不足と見られることや罰金を避けるため、疑わしいアラームをできる限り全て顧客に上げる圧力を受ける

仮置き

  • 主張の種類: statement(言い切り)
  • 見せるもの: 近い調査の3件と、それぞれが測ったもの(調べる操作の数、不確かなときの行動の自己申告、上げすぎる圧力の証言)。どれも誤りの割合は測っていないことを示す
  • 注目させる点: どちらの誤りも、割合を測った調査がないこと
