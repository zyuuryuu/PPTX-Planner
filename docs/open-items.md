# 未検証の前提と未決定の事項

[目次に戻る](README.md)

## 未検証の前提

- 要点の復元が、中身と要点の不一致を実際に検出できるか。
- 題と要点を分ける書式で、長すぎる文と、題と中身の重複が実際に減るか。
- 要点を「中身の下」に置く位置には、出典の裏付けがない。どの型に使うか、読み手が要点を見落とさないかを、試して決める。
- 限定と出どころを脚注や印で示す方法で、読み手が限定を見落とさないか。提案書と製品紹介の `annotation` の既定は、仮の値である。
- 演習の問題のスライドを、立証の設計の書式(`show`、`focus`)で表せるか。
- 研修資料で、主張の骨子を学習の目標に読み替えて、工程がそのまま使えるか。
- 章の前提と到達点を、設計の時点でどこまで具体的に書けるか。
- 検査と記録を守る仕組み(作業の枝での変更の拒否、本流の検査のコマンドでの実行)を、実装でどこまで確かにできるか。
- 重大な検査を別のモデルで2回行う方法で、見逃しがどの程度減るか。2回の結果が食い違う割合が、人が見られる量に収まるか。
- 語彙の検査の対象を、対象を指す一般の語に広げた場合の、誤検出と登録の手間。
- 不合格のときの共通の手順で、往復が実際に収束するか。
- 結合テストで、読み手の役のセッションが状態を持ち越してエラーを挙げる方法が、実際に働くか。見逃しと誤検出がどの程度か。特に、枠組みの放棄、抽象度の急変、水準の揺れ、語の意味のずれは、通読に頼る。
- 使う語彙を先に決める方法で、用語の揺れを実際に防げるか。一般の語と分野に固有の語の線引きで、誤検出がどの程度出るか。縛りによって文が不自然にならないか。
- 語の登録の審査で、設計セッションが類似の語と誤用を正しく判定できるか。審査を1件ずつ順に行うことが、製造の進みを妨げないか。
- 検査セッションが判断する検査(裏付けのない文、限定の残存、削る検査、読み戻し)の見逃しと誤検出が、どの程度か。
- 含意の照合(型の `implies` とスライドの `holds`)が、形と中身の食い違いを実際に防げるか。`holds` の申告を、検査セッションが正しく確かめられるか。
- LLMが画像から要素の位置を推定する精度と、印の周辺を切り出して確かめる検査で、誤りを拾えるか。
- 写り込みの検査で、隠すべきものを検査セッションが見落とさないか。
- 形の手がかりの含意の強さの見立てが、読み手の実際の受け取り方と合うか。
- 見本の分だけスライド仕様を先に書く進め方が、工程の順序として無理なく回るか。
- 描画の実装によらない型の語彙を、表現力を落とさずに定められるか。
- 要点に直接書いた数値を、単位と表記を正規化して台帳と機械的に照合できるか。丸めや「約」で誤検出がどの程度出るか。
- 全体を扱う成果物(章構成、ストーリーライン、章の前提と到達点、立証設計)が、100枚規模でも1つのセッションで扱える分量に収まるか。
- SlideCraftを使う場合、表現の型をレイアウト固定の記法で制御できるか。SlideCraftは内容の形からレイアウトを自動で選ぶため、同じ種類のスライドが別のレイアウトになる可能性がある。
- SlideCraftの図の種類(12種とMermaid経由の4種)と区切りの記法で、ビジネス文書に必要な型が足りるか。
- Pythonのコードを使う場合、型ごとの関数を使い回す方式で、文字のあふれを画像を見ずに検出できるか。
- 成果物の書式(YAML)が、LLMにとって書きやすく、人にとって読みやすいか。
- 独立した導出と反論の検査が、仮の結論への偏りを実際に見つけられるか。
- 仕組みの定義を挟む方法で、図の捏造と図をまたぐ不整合を実際に防げるか。抜き出しの手間が引き合うか。
- 独立した2回の抜き出しの差分が、誤りの発見に役立つか。
- 意味の検査が、検査セッションによって実際に中身のない主張を落とせるか。検査セッションもLLMで、AIらしい文章を自然だと感じる傾向は同じである。
- 字数による収容量の見積もりに、どの程度の余裕が要るか。文字の幅は一定でない。
- PMを新しく起こす場合と、設計セッションが兼ねる場合とで、読み込み量と判断の質がどう違うか。
- 執筆の子セッションが章を担当し続ける場合、記憶に残った古い前提が、上流の変更の後に悪さをしないか。
- 画像の読み取りが、人の手直しをどの程度の細かさまで拾えるか。
- 規則の数が増えたとき、LLMがどこまで守れるか。数が増えるほど守られにくくなる見込みである。
- 必要なフォルダだけを取得して起こした子セッションが、結果を作業のブランチにプッシュできるか([Claude Code での実現](environments/claude-code.md))。
- Gitの履歴とスクリプトによる取り出しを、作業票の指示の文だけで防げるか。
- 入力を限る作業の子セッションが、人の許可を待つ表示を出さずに、作業を終えられるか。

## 未決定の事項

- 試作で最初に使う資料の型(提案書、調査報告、製品紹介、研修資料のどれか)。
- 複数の型が混ざる資料の扱い。資料全体の型は1つとし、章ごとに別の型の定型を借りる形が候補である。
- 資料の型の定義の `limits` の値。
- 1節あたりの枚数の上限(`section_max_slides`)。
- 題の字数の上限。仮に20字とする。試して決める。
- 要点の字数の上限(2行に収まる字数)。
- 節のまとめを置く境目の枚数(`section_summary_min_slides`)。仮に4枚とする。試して決める。
- 付録の枚数を、ブリーフの枚数の目安に含めるか。
- 主張と要約の文(工程2)の限定を、要点と同じく別の項目に持たせるか。
- 描画の道具(`tools/build.py`、`tools/render.py`、`tools/patterns-data.md`)は、題と要点を分けた今の書式に直した(v0.40)。残っているものは、下の「描画の道具で残っているもの」にある。
- 結合テストの集計で使う目安の値。
- 結合テストで、スライドの画像を読むか、ビルドした実物から抜き出した文字を読むか。
- 抜き取りの枚数。抜き取りで誤りが見つかった割合が、どの程度なら全ての章に検査を広げるか。
- 「言い切り」の種類で、言い切りの型と大きな数字の型を書き分ける鍵。
- 発表時間の見積もりに使う、話す速さの値。
- 発表の後の反応を記録する形。ユーザーが伝え、設計セッションが記録する。
- 主張の種類の語彙の名前と範囲。付属する型の一覧。
- 型ごとの収容量の値と、文字の大きさの下限の値。
- 文の機械的な検査の上限の値(1文の字数、読点の数など)。良い資料の実測から決めるのが望ましい。
- 往復の回数の上限。
- 仕組みの定義から生成した図で、配置の調整をどこまで認めるか。
- IssueをGitHubに置くか、リポジトリの中のファイルに置くか。
- 人が作った良い資料を見本として、表現規約の初期値を抽出するか。
- 既存の資料を直す場合の入口。新規に作る場合の工程が固まった後に扱う。
- スキルの数と分け方。今は15個である(設計セッションは工程0から6の工程ごとと工程7から9、PMは工程ごと、ほかは担当ごと)。試して決める。
- 成果物のファイル名と置き場が決まっていないもの。確認用の資料(目次と章扉、骨組み、仮置き)、型の見本の画像、章をビルドした実物、章の作業票、要約のスライドの仕様、資料の型の定義、個人の表現規約、抜き出した語の一覧、題と要点の一覧、否定する事実の数の一覧、集計で挙がったエラーの候補、実際の環境で確かめた結果の記録、資料に固有の受け入れの条件、型の定義。
- `04-scenarios.yaml` の書式のうち、場面の指定の項目。決まっているのは、期待する結果を `expected` に書くことだけである。「過去の指摘」の場面で確かめる指摘を、読み手の役のセッションにどの項目で渡すか。
- 数値を持つ事実の `metric` は、語彙表の語で書く(工程1)。語の登録は、工程2から4で行う。工程1で `metric` の語を登録する手順がない。
- 工程1の、事実の収集、画像の素材の登録、仕組みの定義の抜き出しの順序。調査依頼の文面の検査を行う時点。
- 素材台帳に `superseded_by` を書き込む担当。仕組みの定義の全体を図にする担当。
- 章の受け入れの時点で、エラーの重大度を決める担当。
- 結合テストで、場面ごとに、期待する結果と実行の結果を比べる担当。決まっているのは、章の出口の状態の照合(PM)だけである。
- 抜き取りの結果を、集計の記録に書く担当。選んだスライドの一覧の置き場。
- 設計セッションがユーザーから聞いた経験や伝聞と、提出を受けた資料を、収集セッションに渡す形。
- 再実行の指摘の扱いで、変えていないスライドについての指摘のうち、前回も出ていた指摘の扱い。
- 規則の追加と整理を行う時点([表現規約](style-rules.md))。
- 型の見本のスライド仕様に、工程7の検査と、文の機械の検査を当てるか。
- 重大な検査の2回目と、2回の結果が食い違ったときの判断を、工程表で別の作業にするか。2回目の検査の記録のファイル名。
- 工程表の機械の作業のうち、道具がないもの(`command` が null のもの)の実装。11件ある: `tally-contradicting-facts`、`extract-terms`、`make-chapter-brief`、`tally-chapter-phrases`、`check-term-application`、`extract-titles-and-points`、`tally-integration-errors`、`build-final`、`make-inspection-report`、`pick-samples`、`tally-metrics`。
- 承認を記録する命令は、`tools/status.py record-approval` として実装した。工程表の作業(`record-approval`、`accept-chapter`、`hand-over`)は機械の作業でないため、`command` を持たない。これらの作業の手順から命令を指す方法。
- 実行の記録の `carried` は、語だけを持つ。章の到達点の、語のほかの項目(納得した主張、答えた疑問など)を、実行の記録と機械的に照合する方法。
- 検査の指摘を受け入れると決めたこと、警告を直すか受け入れるかを決めたことを、記録する置き場。
- ブリーフ `00-brief.md` の書き方。項目の表だけがあり、項目と状態をどう書くかの定めがない。
- 写しを作れない入力。見本の画像(置き場が未決定)と、実行の記録の章の終わりの状態(写しの作り方が未決定)である。
- PMが自分で行う入力を限る作業(引き継ぎの検査の「説明を書く」)で、読むものをどう限るか。写しと結果の置き場を使わない。
- ファイル名が決まっていない入力(調査依頼、外部の資料、章の作業票など)の複製を、写しの置き場に置く手順。
- 子セッションが読んだファイルを、作業の後に機械で確かめる方法。採っていない。候補として残す。
- スライドの文の、中身(`body`)から除く項目。型の定義が、読み手に見える項目を示していないため、項目の名前で挙げている。
- 独立に書いた答え `work/answers/` を、比べた後に残すか。
- 検査セッションのスキルの `SKILL.md` が、先頭に収める量の目安を超えている。禁止と入力の制限の決まり、作業の一覧を先に置き、残りの決まりを後に置いている。検査セッションの共通の手順は、作業ごとのファイルに写している。
- 最初に対応する描画の実装。
- 機械的な検査を実装する言語と置き場。
- 元のファイルを作業の場所から外す手段がない環境で、入力を限る作業をどこまで行うか。今は、作業票の指示の文だけで縛る。
- 取り込んだ後の写しと結果を、作業のブランチの置き場に残すか。

### 道具を作る中で見つかった、決まりの不足と食い違い

- 台帳にない機械の確かめがある。[検査](checks.md)の「検査の実行」は、書式とIDの参照先を機械的な検査に挙げるが、台帳にIDがない。道具は「書式」として別に出し、検査の記録には書かない。
- 資料の表現規約 `style.yaml` の書式がない。上限を置く項目の名前で決まっているのは、`section_max_slides`、`section_summary_min_slides`、`point_position` だけである。主張の数、要約の文の字数、題の字数、要点の字数、読点の数、漢字の連なりの上限の名前と、`limits` の下に置くかどうかは、道具が決めた。
- 資料の型の定義と型の定義を、資料ごとに置くファイルがない。道具は `definitions/deck-type.yaml`、`definitions/patterns.yaml` とした。ブリーフで選んだ資料の型を、どの項目にどう書くかの定めもない。
- 型の定義の `expresses` が、付属する型の候補の表にない。`K06-03` の後半は、資料の定義がなければ確かめられない。
- 量の区分(`size`)は機械が決めるとあるが、収容量の値がなく、決めた区分を置く項目もない。`K06-01`、`K06-05`、`K07-03` に関わる。
- 立証の設計の、「言い切り」「並列の列挙」を選んだ理由を書く項目の名前がない(`K05-08`)。道具は `relation_reason` とした。`view` につながりを書く項目の名前もない。道具は `relations` とした。
- スライド仕様の保留(`status: blocked`)に、Issueの番号を添える項目の名前がない(`K07-38`)。道具は `issue` とした。
- テストの場面 `04-scenarios.yaml` で、場面を指す項目と、該当しないと記録する項目の名前がない(`K04-29`)。道具は `scenario`、`applicable: false`、`reason` とした。
- 型の見本 `06-samples/` と、付録のスライド仕様のファイル名がない。見本の資料では、`06-samples/<型の識別子>.yaml`、`07-slides/appendix.yaml` とした。
- スライド仕様の `body` の書式が、例の間で揃っていない。[工程7](stages/07-slide-spec.md)の1つ目の例は型のデータを `body.data` に置き、画像の型の例は `body` の直下に置く。`K07-11` は `body.data` を対象にするため、画像の型の `captions` の数値は検査から外れる。`tools/patterns-data.md` は、全ての型で `body` の直下に置く。
- `K07-11` は、説明、型のデータ、ノートに、事実のIDによらない数値を認めない。年度や時刻を含むラベル(「2024年度」「10時台」)を書く方法がない。見本の資料では、数字のないラベル(「前の年度」「午前」)にした。`tools/patterns-data.md` が認める書き方(`{F201:value}`、同じ文に事実の参照を置いた数値)は、docs にない。
- `K07-07` は、図や表を載せるスライドに `highlight` を求めるが、どの型が図や表に当たるかの定めがない。[工程7](stages/07-slide-spec.md)の画像の型の例には、`highlight` がない。
- [仕組みの定義](model.md)の例の、`summarizes` を持つつながりに `evidence` がない。`K01-24` は、全てのつながりに事実が紐づくことを求める。道具は、条件の文に従う。
- 内部のIDの書式の定めがない(`KX-15`)。道具は、資料にあるIDと、定義の例の形で探す。「Q1」のような短いIDは、普通の語と重なりうる。
- 数値の照合で、事実の「値」に何を含めるかの定めがない。道具は、`value` と `unit` に加えて、`statement`、`quote`、`qualifiers` に書かれた数値を値とした。「2つ」のような数え方、丸め、「約」の扱いも定めがなく、道具は全て数値として扱い、丸めを認めない。
- 検査の記録の `target` は、例ではファイル名1つである。機械の作業は複数の成果物を検査する。道具は、ファイル名を並べて書く。行がどの成果物についてのものかを書く項目がないため、状態の記録に写すときは、台帳の `target` の名前から決めている。
- 検査の記録の `commit` を、コミットしていない成果物を検査した場合にどう書くかの定めがない。道具は、既定では書くのを拒み、指定があれば null で書く。
- 状態を `checked` にする条件のうち、どの記録が揃えば「合否にする検査の全てに通った」と言えるかの定めがない。道具は、最後の回の記録に不合格がなければ `checked` にし、記録にない検査を知らせとして出す。実装していない機械の検査があるため、全ての検査を求めると、どの成果物も `checked` にならない。
- `invalid` を解く条件と、スライドの `invalid` を消す条件の定めがない。道具が決めた条件は、[tools/README.md](../tools/README.md)にある。
- 工程7の機械の検査は、執筆のセッションも実行する。執筆のセッションは検査の記録と状態の記録を変更できないため、`--write` を付けずに実行する。工程表の `command` は、受け入れる側の命令(`--write` つき)だけを持つ。
- 語彙の検査で、主張の骨子の `answer` が、厳しさの段階の表のどちらの行にも挙がっていない。道具は、主張と同じ行として扱う。数値の直後の単位(年、件、倍など)を語として扱うかの定めもない。道具は、語として扱わない。

## 描画の道具で残っているもの

描画の道具(`tools/render.py`、`tools/build.py`)を今の書式に直した時点(v0.40)の状況である。書式と描き方は、[tools/patterns-data.md](../tools/patterns-data.md)にある。

### 実装していないもの

- PPTX の出力。最終の出力(工程9の `build-final`)の道具がない。人に渡す形は、PDF で出している。
- 付属する型の候補のうち、描けない型。`stacked-bar-chart`、`line-chart`、`scatter-chart`、`histogram`、`versus`、`two-axis`、`big-number`、`sequence-diagram`、`state-diagram`、`gantt-chart`、`annotated-image-callouts`、`image-before-after`、`exhibit-image` の13個である。描ける型は13個である。
- 表紙と要約のスライド。章と節の現在地の表示(下の不足による)。
- ノートを置き場にした限定と出どころは、`deck.html` と診断にだけ出る。PDF と PNG には出ない。
- 流れ図、構成図、ER図の収容量は、今の配置で測り直していない。試行の資料の図を今の配置で描き、あふれと重なりの診断が出ないことだけを確かめた。
- 注釈の印と説明を置いた位置を、診断に書き出していない(`K07-18`)。印を指す対象の外に置けないときに、診断に出すだけである。
- 人の手直しを守る仕組み(出力の要約値の記録と照合)。

### 道具を直す中で見つかった、決まりの不足と食い違い

推測で決めた点は、道具の側の仮の決まりである。docs の決まりは変えていない。

- 章と節の現在地を、スライドのどこにどう出すかの定めがない。結合テストのエラーの種類に「現在地の喪失」があるだけである。道具は、現在地を出していない。
- 表紙に載せる資料の題を、どの成果物から取るかの定めがない。要約のスライドを置く位置と、その仕様の置き場の定めもない(`K08-07`)。道具は、表紙と要約を作っていない。
- 目次に載せるのは章と節の題と定めているが、付録と出典の一覧を目次に載せるかの定めがない。付録の前に扉を置くかの定めもない。道具は、目次に付録と出典の一覧の行を足し、付録の扉を置いた。
- 型のデータの置き場が、工程7の2つの例で違う。数量の型は `body.data` に置き、画像の型は `asset`、`crop`、`scenario`、`captions` を `body` の直下に置く。仕組みの定義を参照する型(流れ図など)の `scenario`、`elements` をどちらに置くかの定めがない。道具は、`body.data`、`body` の直下の順に探す。
- 型の定義の `data`(必要な項目)が、型ごとに決まっていない。型ごとのデータの形は、道具が決めた。見本の資料の `bar-chart` と `before-after` の形は、そのまま採った。
- 「言い切り」の型で、要点の位置が「中身そのもの」のとき、型のデータに何を書くかの定めがない。道具は、要点の文を中身として描き、`value`(大きく示す値)と、その説明の `text` を添える形にした。付属する型の候補には「大きな数字」(`big-number`)が別にあるが、見本は `statement` に `value` を書いている。
- 資料に共通の規則(文字の大きさの下限、色の割り当て、強調の方法、定位置、色相の数の上限)を、資料の表現規約にどの項目の名前で書くかの定めがない(`K06-08`)。道具は、`common.font_min`、`common.colors`、`common.max_hues_per_slide` を読み、ない場合は道具の既定を使う。見本の資料には、これらの項目がない。
- 文字と背景の色の差、隣り合う色の差の基準の値がない(`K06-11`、`K07-40`)。道具は、コントラスト比で 4.5(大きな文字は 3.0)と 1.3 とした。色相の数の上限の既定は 4 とした。
- 強調の方法は、資料の表現規約で1通りに決めると定めているが、書式がない。道具は、太い黒の線で囲み、文字を太字にする。色の割り当てのない面は、濃い灰色にする。
- 脚注に載せる出典の書き方の定めがない。道具は、事実の `source` だけを並べ、位置(`locator`)は載せない。導出した事実の出典は、`formula` の中の事実からたどる(`formula` の書式は未定義である。`K01-07`)。
- 節の要点を引くスライドの限定を、節の `qualifiers` から取るかの定めがない。節のまとめと章のまとめに、並べた要点の限定を載せるかの定めもない。道具は、節の `qualifiers` を使い、まとめには、載せた要点の限定をまとめて置き場に描く。まとめに出典は載せていない。
- 出どころの印の形と文字の定めがない。道具は、「出典」「案」「運用」の文字を、枠の線の種類を変えた小さな札で描く。
- 骨組みの資料で、要点のないスライドの役割と、節の要点を引くスライドを、どう見せるかの定めがない。道具は、確認用の資料にだけ、小さな札(「要点なし(役割: 詳しい説明)」「節の要点」)を付ける。完成形では、節の要点を引くスライドを、ほかのスライドと同じ形で描く。
- 骨組みの資料は工程4で作るが、要点の位置は工程6で決まる。道具は、型が決まらない間は、要点を題の直下に描く。
- 確認用の資料、型の見本、章をビルドした実物のファイル名と置き場の定めがない(工程表の覚え書きにも未決定とある)。道具は、`build/toc/`、`build/skeleton/`、`build/placeholder/`、`build/samples/`、`build/` に、`deck.html`、`deck.pdf`、`slides/`、`diagnostics.json` を置く。
- 「描画上の診断が0件」(`K06-11`、`K07-41`、`K08-04`)で、警告と情報の診断を数えるかの定めがない。道具の数え方は、上の「条件の一部だけを確かめている検査」にある。
- 工程表の `build-samples`、`build-chapter`、`build-full-deck` は、描くことと、描画上の診断の検査の両方を行う。`command` には、描く命令と検査の命令を続けて書いた。`K06-11` は、`build-samples` と `check-patterns-machine` の両方の `checks` にある。
- 題の字数の上限(仮に20字)は、今の配置で1行に収まる字数(36pxで32字)より小さい。要点は、題の直下と中身の下では1行に約43字、中身そのものでは1行に約34字が入る。要点の字数の上限(見本は60字)は、どの位置でも2行に収まる。
- 脚注の行の数の上限の定めがない。道具は、2行を超えると警告を出す。試行の資料の出典の名前は長く、脚注が3行から4行になるスライドがあった。
- 見本の資料の画像の素材は、64×36ピクセルの仮の画像である。注釈つきの画像の型の見た目は、実物の画面の画像では確かめていない。
