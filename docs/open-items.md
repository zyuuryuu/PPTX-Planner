# 未検証の前提と未決定の事項

[目次に戻る](README.md)

## 未検証の前提

- 見出しの復元が、中身と見出しの不一致を実際に検出できるか。
- 「1つの種類に1つの型」が、量の違いで破綻しないか。並列の列挙は、3項目ならカード、8項目なら表が適切である。種類に加えて量の区分を対応表の鍵にする必要があるかもしれない。
- 描画の実装によらない型の語彙を、表現力を落とさずに定められるか。
- 見出しと結論1行に数値を直接書く扱いで、台帳との不一致を検査セッションが拾えるか。
- 全体を扱う成果物(ストーリーライン、立証設計、要約版)が、100枚規模でも1つのセッションで扱える分量に収まるか。
- SlideCraftを使う場合、表現の型をレイアウト固定の記法で制御できるか。SlideCraftは内容の形からレイアウトを自動で選ぶため、同じ種類のスライドが別のレイアウトになる可能性がある。
- SlideCraftの図の種類(12種とMermaid経由の4種)と区切りの記法で、ビジネス文書に必要な型が足りるか。
- Pythonのコードを使う場合、型ごとの関数を使い回す方式で、文字のあふれを画像を見ずに検出できるか。
- 成果物の書式(YAML)が、LLMにとって書きやすく、人にとって読みやすいか。
- 独立した導出と反論の検査が、仮の結論への偏りを実際に見つけられるか。
- 意味の検査が、検査セッションによって実際に中身のない主張を落とせるか。検査セッションもLLMで、AIらしい文章を自然だと感じる傾向は同じである。
- 字数による収容量の見積もりに、どの程度の余裕が要るか。文字の幅は一定でない。
- PMを新しく起こす場合と、設計セッションが兼ねる場合とで、読み込み量と判断の質がどう違うか。
- 執筆の子セッションが章を担当し続ける場合、記憶に残った古い前提が、上流の変更の後に悪さをしないか。
- 画像の読み取りが、人の手直しをどの程度の細かさまで拾えるか。
- 規則の数が増えたとき、LLMがどこまで守れるか。数が増えるほど守られにくくなる見込みである。

## 未決定の事項

- 最初に作り込む資料の型(提案書、調査報告、製品紹介、研修資料のどれか)。
- 複数の型が混ざる資料の扱い。資料全体の型は1つとし、章ごとに別の型の定型を借りる形が候補である。
- 資料の型の定義の `limits` の値。
- 各工程の作り方(ストーリーラインの組み方、立証設計の進め方)。
- 1つの子セッションで扱う枚数の上限。
- 1節あたりの枚数の上限と、見出しの字数の上限。
- IssueをGitHubに置くか、リポジトリの中のファイルに置くか。
- 人が作った良い資料を見本として、表現規約の初期値を抽出するか。
- 既存の資料を直す場合の入口。新規に作る場合の工程が固まった後に扱う。
- 提供形態(Claude Codeのスキル群とするか)。
- 最初に対応する描画の実装。
- 機械的な検査を実装する言語と置き場。
