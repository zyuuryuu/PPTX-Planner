# 使う語彙

[目次に戻る](README.md)

状態: 仮決め。試作の結果を見て見直す。

用語の揺れを、書いた後に見つけて直す方法では防がない。直す作業そのものが、意味の取り違えを生むためである。設計の間に使う語彙を決め、執筆はその語彙だけで書く。禁じる語を並べることを主な手段にせず、使う語を決める。使わない語の一覧(`banned`)は、2つの意味で使われうる語、意味が定まらない語、登録した語と同じ対象を指しうる別の語、繰り返し申請されて退けた語に限って持つ。

航空機の整備文書で使われている制限言語(ASD-STE100)と同じ考え方をとる。使ってよい語を辞書で定め、1つの語に1つの意味を割り当て、対象の分野に固有の名称は案件ごとに決めて足す。

## 原則

1. **管理する単位は、語ではなく概念とする。** 1つの概念に1つの語、1つの語に1つの概念を割り当てる。
2. **同じものかどうかを決めるのは人である。** LLMは候補を挙げるところまでとする。
3. **執筆は、登録済みの語だけで書く。** 登録のない語は、機械的な検査で止める。
4. **一括の置き換えと、LLMによる用語の修正をしない。** 違反は、その文を書いたセッションが、その文を直す。語彙表の語そのものを変える場合だけは、下の「語を後から変える場合」による。

## 成果物

`terms.yaml`(語彙表)。資料の表現規約の一部である。

```yaml
terms:
  - id: T-customer
    term: 契約企業
    kind: noun                 # noun(対象を指す語) / action(動作を指す語)
    definition: 当社と契約を結んでいる法人
    not: [T-end-user]          # 近いが別の概念
    note: 個人の利用者は「利用者」とする
    defined_in: ch1-s3         # 資料の中で定義するスライド。定義が要らない場合は null とする
    no_definition: null        # 定義が要らない理由。ブリーフの「読み手が既に知っていること」にある、など
  - id: T-send
    term: 送信する
    kind: action
    definition: 部品が、別の部品にデータを渡す
banned:                      # 使わない語と、その理由
  - term: ユーザー
    reason: 利用者と契約企業の両方を指しうる
    use: [T-customer, T-end-user]
  - term: 連携する
    reason: 何をするのかが決まらない。「送信する」「取得する」など、動作を特定する語を使う
allowed:                     # 対象を指さない一般の語。検査で止めない
  - 四半期
```

- 対象とするのは、この資料の中で、人、組織、役割、製品、仕組みの部品、データなどの対象を指す語と、分野に固有の動作を指す語である。一般の語であっても、対象を指す語は登録する。「顧客」「クライアント」「取引先」のような語が、これにあたる。
- それ以外の一般の語(「市場」「成長」「課題」など)は、`allowed` に入れる。
- 対象を指す語を登録するときは、同じ対象を指しうる別の語を設計セッションが挙げ、ユーザーが確かめたうえで `banned` に入れる。「契約企業」を登録するなら、「顧客」「クライアント」「取引先」がこれにあたる。説明の文に別の語が紛れ込むのを、機械で止めるためである。
- 仕組みの定義の要素の名前は、語彙表に自動で含める。
- 2つの意味で使われうる語は、`banned` に入れ、意味ごとに別の語を登録する。

## 作り方

### 厳しさの段階

語彙の検査は、文の種類によって厳しさを変える。

| 文の種類 | 登録も許可もされていない名詞と動作の語 |
|---|---|
| 要約の文、主張、章の主張、見出し、結論1行、図のラベル、表の見出し、仕組みの定義の要素の名前 | 不合格とする。一般語の辞書は使わない。語彙表にも `allowed` にもない語は、全て止める |
| 説明、表のセル、図の注記、ノート | 語彙表、`allowed`、一般語の辞書のいずれにもない語を、警告とする。試作で誤検出の程度を見て、不合格に上げるかを決める |

`banned` の語は、文の種類によらず不合格とする。

### 設計の時期: 登録する

工程2から4で、要約の文、主張、章の主張、見出しから、名詞と動作を指す語を機械的に全て抜き出す。設計セッションが、1つ1つを、対象を指す語(登録する)か、それ以外の一般の語(`allowed` に入れる)かに分ける。対象を指す語の一覧は、ユーザーが確認する。これらの文は数十から百程度で、抜き出される語は数百にとどまる見込みである。その後に新しい語が必要になった場合は、下の「語の登録の手順」による。


### 工程6: 凍結する

型の見本の承認とあわせて、ユーザーが語彙表を承認する。判断が要る候補だけを先に示し、残りは一覧で示す。承認の後は、語彙表を凍結する。凍結の後は、「語の登録の手順」を経ない限り、語を足すことも変えることもできない。

凍結の前に、設計セッションは、登録した語の全体を見渡して、同じ概念を指していそうな語の組と、2つの意味で使われていそうな語を、候補として挙げる。

### 製造の時期: 登録済みの語だけで書く

章の作業票に、その章に関わる語と、その定義、近いが別の概念を載せる。

執筆のセッションは、登録のない語が必要になったら、下の「語の登録の手順」で登録を申請する。自分では語彙表を変えない。結果が出るまで、そのスライドは保留にして、ほかのスライドを進める。

## 語の登録の手順

使いたい語が出てきたときに、その1語について、似た語がないか、誤用でないかを確かめてから登録する。資料の全体から揺れを探すより、1語を文脈つきで判定するほうが、確かに判定できる。

### 1. 申請

申請するセッションは、次を書いてIssueを立てる。

- 使いたい語と、種類(対象を指す語、動作を指す語)
- その語を使う文
- その語が指すものの説明
- 既にある語では足りない理由

### 2. 機械的な確認

- 既にある語の表記の揺れでないか。
- `banned` の語でないか。
- 過去に申請されて、既にある語を使うことになった語でないか。
- 出典(素材台帳の引用、仕組みの定義)に現れる語か。どこにも現れない語は、LLMが作った言い回しである疑いがあるため、その旨を審査に伝える。

ここで決着するものは、審査に回さない。

### 3. 審査

審査は、設計セッションが1件ずつ順に行う。複数の章から同時に申請が来ても、並行して処理しない。同じ概念に別々の語が登録されるのを防ぐためである。

設計セッションは、語彙表の中から、定義の近い語を候補として挙げる。候補のそれぞれについて、次を確かめる。

| 確かめること | 問い |
|---|---|
| 類似の語 | 申請された語が指すものは、既にある語の定義に当てはまるか |
| 誤用 | 申請された文は、既にある語、または一般の語で、意味を変えずに書けるか |
| 多義 | 申請された語は、この資料の中で別の意味にも取れるか |
| 新しい概念 | 申請された語が指すものは、設計の成果物(主張の骨子、仕組みの定義など)にあるか |

### 4. 結果

| 結果 | 内容 | 決める人 |
|---|---|---|
| 既にある語を使う | 申請を退け、使う語を返す | 設計セッション。申請したセッションが、指すものが違うと考える場合は、理由を添えてユーザーに上げる |
| 一般の語として認める | `allowed` に加える | 設計セッション |
| 言い換える | 語を使わずに書く方法を返す | 設計セッション |
| 登録する | 定義と、近いが別の概念を添えて、語彙表に加える | ユーザー。設計セッションが、候補との違いを示して確認を求める |
| 設計に戻す | 指すものが設計の成果物にない。語の問題ではなく、設計の漏れである | ユーザー。設計の見直しとして扱う |

同じものかどうかを最後に決めるのは人である。設計セッションが「既にある語と同じ」と判定しても、申請したセッションが異を唱えた場合は、ユーザーが決める。LLMどうしの判定で概念を統合しない。

ユーザーへの確認は、1件ずつではなく、まとめて行ってよい。その間、該当するスライドは保留のままとする。

### 5. 記録

申請と結果は、退けたものも含めてIssueに残す。同じ語の申請が繰り返された場合は、`banned` に、使う語とあわせて加える。

章ごとの申請の数を記録する。申請が多い場合は、設計の時期の語の拾い方が足りていない。

## 検査

- 全ての文から、名詞と動作を指す語を機械的に抜き出し、語彙表、`allowed` と照合する。扱いは、上の「厳しさの段階」の表による(機械)。
- `banned` の語を含まない(機械)。
- 表記の揺れ(長音の有無、送り仮名、全角と半角)を、正規化して語彙表と照合する(機械)。
- 出典の引用、画面に表示されている名前、固有の名称は、検査の対象から外す。これらはデータの上で別の項目(`quote`、`regions` の `label` など)に入っているため、機械的に外せる。
- 語が、定義するスライドより前に使われていない(機械。工程8の開始の条件)。
- 対象を指す語の全てに、`defined_in` か、定義が要らない理由がある(機械。工程6)。
- `defined_in` が示すスライドが、その語を実際に説明している。定義が要らない理由が、ブリーフの読み手の水準に合っている(検査セッション。工程7の、そのスライドの検査)。

## 語を後から変える場合

概念を指す語を変える場合に限り、置き換えを機械的に行ってよい。上の原則と検査が最初から守られていれば、古い語は1つの概念だけを指しているためである。置き換えた文は、限定の残存の検査と、読み戻しの検査([文章の書き方](writing.md))を受ける。

概念を分ける、または統合する場合は、置き換えを機械的に行わない。該当する文を一覧にし、章の執筆のセッションが1文ずつ直す。

## 残る危険

- 登録済みの語を、違う意味で使う誤りは、機械では見つからない。作業票に定義と近い概念との違いを載せて減らす。
- 一般の語と、分野に固有の語の線引きは、辞書に頼る。最初は誤検出が多い見込みで、`allowed` に足すことで減らす。
- 縛りが強く、文が不自然になる恐れがある。
