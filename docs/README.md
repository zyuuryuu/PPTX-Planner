# スライド作成工程の定義(草案 v0.34)

状態: 草案。細部と書式は未確定である。実物で確かめていない前提は、[未検証の前提と未決定の事項](open-items.md)を参照。

## 目的

LLMによるスライド作成は、枚数が増えると次の問題を起こす。

- 文章が崩れ、スライド間の一貫性が失われる。
- 何を伝えるのかが決まっていないスライドが増える。
- 中身のない言い回し、目的に対して多すぎる情報、基準のないグルーピングが混じる。
- 修正のたびにPPTXの座標や書式を読み込み、消費するトークンが膨らむ。

この定義は、スライド作成を工程に分け、工程ごとに成果物と合格条件を定めることで、これらを防ぐ。

## 対象

30枚以上のスライドからなる資料を、新規に作る場合を対象とする。それより少ない枚数の資料は対象としない。工程と承認の回数は、この規模を前提に定める。

## 検査の台帳

全ての検査を、台帳 [`checks.yaml`](checks.yaml) に置く。各工程の定義の合格条件は、道具 `tools/checks_table.py` が台帳から作る。台帳の項目は、[検査](checks.md)に定める。

| すること | コマンド |
|---|---|
| 台帳から、文書の合格条件を作り直す | `python3 tools/checks_table.py` |
| 文書が台帳と一致するかを確かめる。ずれていれば、ずれた文書を表示して失敗する | `python3 tools/checks_table.py --check` |
| 工程ごと、判定者ごとの件数を出す | `python3 tools/checks_table.py --stats` |

道具は、Python 3 と PyYAML で動く。台帳の先頭の `count` は、検査の件数である。項目を足すとき、消すときに、あわせて直す。合わなければ、道具はエラーで終わる。台帳か文書を変えたら、コミットの前に `--check` を実行する。

## 工程表

工程の文書の手順を、作業に分けて、工程表 [`tasks.yaml`](tasks.yaml) に置く。作業は、1つの担当が、決まった入力から決まった成果物を作る、ひとまとまりの仕事である。手順の正本は工程の文書である。工程の文書の「作り方」は、手順ごとに、行う担当を「担当: 」の行で示す。

| 項目 | 内容 |
|---|---|
| `id` | 作業の名前。一度付けたら変えない |
| `stage` | 工程の番号。複数の工程で行う作業は並べる |
| `name` | 日本語の名前 |
| `notes` | 作業を行う条件と、未決定の点の覚え書き。スキルと作業票に写す |
| `role` | 担当。`user`(ユーザー)、`designer`(設計セッション)、`collector`(収集セッション)、`writer`(執筆のセッション)、`inspector`(検査セッション)、`reader`(読み手の役のセッション)、`pm`(PM)、`machine`(機械) |
| `skill` | 手順を持つスキルの名前。工程表の `skills` にある名前で書く。機械とユーザーの作業は null |
| `command` | 機械の作業だけに書く。今ある道具で実行できる場合は、そのコマンド。なければ null |
| `inputs`、`outputs` | 読む成果物と、作る成果物のファイル名。`inputs` は、項目まで絞る場合に「ファイル#項目」の形で書く。ファイル名が決まっていないものは、名前を「」で囲んで書く |
| `restricted` | true なら、`inputs` に挙げたもの以外を読まない。入力を限ることが目的の作業に書く |
| `restricted_by` | `restricted` の作業で、ファイルをまるごと渡す場合に、そう定めた箇所(検査のID、または「文書#見出し」) |
| `sections` | 手順が書かれている文書の見出し。「文書#見出し」の形で書く。見出しは、その直下の文だけを指す。下位の見出しは、個別に書く。「文書#前文」は、文書の題から最初の見出しまでを指す |
| `references` | 手順を行うのに読む、ほかの文書の見出し |
| `checks` | 担当が自分で満たす、または判定する検査のID |
| `next` | 次に行う作業 |
| `start`、`end` | 始点の作業に `start: true`、終点の作業に `end: true` を書く |

工程の文書の見出しは、いずれかの作業の `sections` に割り当てる。直下に文がない見出しと、合格条件、開始の条件、終了の条件の見出しは、対象から外す。合格条件は、検査のIDで渡す。

| すること | コマンド |
|---|---|
| 工程表から、[体制とセッション](organization.md)の作業の一覧とスキルの一覧を作り直す | `python3 tools/tasks_table.py` |
| 工程表と文書を確かめる。誤りがあれば、その箇所を表示して失敗する | `python3 tools/tasks_table.py --check` |
| 作業ごと、担当ごとの読む量を出す | `python3 tools/tasks_table.py --stats` |
| 工程ごとの作業の一覧を出す | `python3 tools/tasks_table.py --table` |

`--check` は、次を確かめる。

- `sections` と `references` の見出しが実在する。
- 工程の文書の全ての見出しが、いずれかの作業の `sections` にある。
- 見出しの直下の「担当: 」の行と、その見出しを `sections` に持つ作業の担当が合う。
- 台帳の全ての検査が、判定者ごとに、その判定者が担当である作業の `checks` にある。
- 担当が、決めた一覧にある。`skill` が、工程表の `skills` にある、その担当と工程のスキルである。
- 工程表の `skills` と `roles` の書式が正しい。`roles` の見出しが実在する。
- `next` が、実在する作業を指す。始点と終点のほかに、どこからも来ない作業と、次がない作業がない。
- `restricted` の作業の `inputs` が、項目まで絞られている。まるごとのファイルを渡す場合は、`restricted_by` がある。

工程の文書の見出し、台帳、工程表のいずれかを変えたら、コミットの前に実行する。

## スキルと作業票

担当のセッションが読む手順を、スキルとして `.claude/skills/` に置く。スキルは、道具 `tools/build_skills.py` が、工程表、工程の文書、検査の台帳から作る。正本は、この3つである。スキルは生成物で、直接は直さない。

スキルの一覧と、担当ごとの項目は、工程表に置く。

| 項目 | 内容 |
|---|---|
| `skills` | スキルの一覧。1件ごとに、名前(`name`)、担当(`role`)、扱う工程(`stages`)、いつ使うか(`description`)を持つ |
| `roles` | 担当ごとの項目。`rules` は、スキルの「守ること」に写す見出し。`report` は、報告の書式を定めた見出し |

設計セッションとPMのスキルは、工程ごとに1つとする。設計セッションが工程7から9で行う作業は、1つのスキルにまとめる。収集、執筆、検査、読み手の役のスキルは、担当ごとに1つとする。一覧は、[体制とセッション](organization.md)にある。

スキルは、`SKILL.md` と、作業ごとのファイル `tasks/<id>.md` からなる。`SKILL.md` は、守ることと作業の一覧だけを持つ。要約の後に読み直されるのは先頭だけなので、守ることをここに置く。

| ファイル | 中身 |
|---|---|
| `SKILL.md` | 守ること(工程表の `roles` の `rules` が指す見出しの文面)。作業の一覧(順序、`id`、名前、手順のファイル) |
| `tasks/<id>.md` | 作業1件の、条件と覚え書き、入力、読まないもの、手順、成果物、検査、参照、報告の書式、次の作業 |

- 手順は、工程表の `sections` が指す見出しの文面を、言い換えずに写す。番号つきの手順の一部だけを行う作業には、ほかの番号を行う作業を添える。
- 検査は、台帳のIDと条件の文を写す。その担当が判定する検査と、成果物が満たす合格条件に分ける。
- `references` は、文面を写さない。文書のパスと見出しを挙げる。リンクの先は、スキルの置き場から届く形に直す。
- `restricted` の作業は、正本の文書を開かずに済む形にする。`references`、検査の定義、入力の制限の定め、報告の書式が指す見出しの文面を、作業のファイルに写す。写した文面のリンクは、先を消して文字だけにする。手順の先頭に、守ることの表より入力の制限が優先すると書く。
- 収集、執筆、検査、読み手の役のセッションは、作業票が指すファイルを1つだけ読む。設計セッションとPMは、いま行う作業のファイルを読み、前後の作業のファイルは必要なら読んでよい。
- 複数の工程で行う作業の手順は、最初の工程のスキルが持つ。後の工程のスキルは、作業の一覧からそのファイルを指す。

| すること | コマンド |
|---|---|
| 正本から、スキルを作り直す | `python3 tools/build_skills.py` |
| スキルが正本と一致するかを確かめる。誤りを表示して失敗する | `python3 tools/build_skills.py --check` |
| スキルごとの行数とバイト数、作業1件あたりの読む量、工程表に定めがない項目の数を出す | `python3 tools/build_skills.py --stats` |

`--check` は、次を確かめる。

- スキルのファイルが、正本から作り直したものと一致する。ないファイルと、余分なファイルがない。
- `SKILL.md` の先頭の `name` と `description` が読める。`SKILL.md` が500行未満である。
- 写した文面が指す見出しが、スキルにある。指し方は、見出しへのリンクと、「」で囲んだ見出しの名前である。`restricted` の作業では、指す先の文面が写してある。ほかの作業では、写してあるか、参照に挙がっている。足りなければ、工程表の `sections` か `references` に足す。文書の全体を指すリンクは、確かめない。
- `restricted` の作業の `references` が、見出しまで絞られている。

`--stats` は、`SKILL.md` が先頭の12,000バイト(約5,000トークン)に収まらないスキルがあれば、失敗する。

作業票は、作業1件を行うセッションに渡す指示である。道具 `tools/work_order.py` が、工程表から作る。子セッションを起こすときは、作業票を最初のメッセージにする。設計セッションとPMは、自分が次に行う作業の確認に使う。

| すること | コマンド |
|---|---|
| 作業の作業票を出す。`--chapter` と `--target` で、対象の章、ファイル、コミットを書き入れる | `python3 tools/work_order.py <id> [--chapter ch2] [--target <対象>]` |
| 作業の一覧を、順序つきで出す | `python3 tools/work_order.py --list` |

| 担当 | 作業票の中身 |
|---|---|
| LLMの担当 | 1行目に `/スキルの名前`。続けて、作業、手順のファイル、対象、条件と覚え書き、入力、読まないもの、成果物、次の作業。手順と報告の書式の文面は写さない。作業のファイルが持つ |
| 機械 | 実行するコマンド。道具がない作業は、ないと出す |
| ユーザー | ユーザーに示すものと、答えてもらうこと(判定者がユーザーの検査) |

工程の文書、台帳、工程表のいずれかを変えたら、スキルを作り直し、コミットの前に `--check` を実行する。
