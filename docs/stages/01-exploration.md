# 工程1 探索

[目次に戻る](../README.md)

問いに答えるための事実を集める。収集の手段(Web検索、資料の読み込み、ユーザーへの聞き取り)は、この文書では定めない。定めるのは、何を調べるか、いつ終えるか、集めた結果が満たす条件である。

仮の結論に合う事実だけを集めることを防ぐため、次の3つを行う。

- 探索の範囲を、仮の結論ではなく問いから決める。
- 収集セッションに、仮説を見せない。
- 対立する仮説を置き、それぞれを支持する事実と否定する事実を記録する。

## 成果物

### 仮説の一覧 `01-hypotheses.yaml`

仮の結論と、それに対立する仮説を1つ以上書く。対立する仮説は、逆の結論や「何もしない」などである。

```yaml
- id: H1
  statement: 〇〇事業は、△△に絞って継続すべきである
  proposed_by: user   # user(ユーザーが持っていた結論) / session(設計セッションが立てた)
- id: H2
  statement: 〇〇事業は撤退すべきである
  proposed_by: session
```

### 探索の計画 `01-plan.yaml`

ブリーフの問いを、小さな問いの木に分解したもの。

```yaml
- id: Q1
  question: △△の領域の市場は今後も伸びるか
  parent: null
  axis: 市場、自社、採算       # この問いを子に分けた基準。末端の問いでは省く
- id: Q1.1
  question: △△の領域の市場規模は、過去5年でどう変わったか
  parent: Q1
  evidence_type: 統計          # 答えに必要な証拠の種類。末端の問いで必須
  priority: high               # high(答えによって結論が変わる) / low(結論を補う)
  perspective: null            # 資料の型の定義が定める観点に対応する場合は、その名前
  result: null                 # 収集の後に書く。answered / partial / not-found / disputed
```

### 素材台帳 `01-sources.yaml`

全工程を通じて唯一の事実の置き場とする。スライド上の数値と出典の表記は、台帳から生成する。

```yaml
- id: F012
  statement: 2025年の国内市場規模は1.2兆円
  value: 1.2            # 本文から参照する数値。数値でない事実では省く
  unit: 兆円
  kind: fact
  source: 〇〇白書 2025年版
  locator: p.34 図表2-1  # ページ、URL、節など
  as_of: 2025-03        # 出典の日付または版
  metric: T-domestic-market-size   # 何の指標か。数値を持つ事実で必須。語彙表の語で書く。同じ指標の事実を見つけるために使う
  superseded_by: null    # 同じ指標の別の事実を使うと決めた場合に、使う事実のID。値があるものは、根拠に使えない
  quote: "国内市場は1兆2,000億円に達した"
  qualifiers: [2025年, 国内]   # この事実に付いている限定(条件、範囲、数量の幅、不確かさなど)
  origin: 〇〇省の統計    # 元をたどった情報源。別の資料が同じ情報源を引いている場合に、同じ値になる
  answers: [Q1.1]        # 探索の計画のどの問いに答えるか
  stance: {H1: supports, H2: contradicts}   # 仮説ごとに、supports(支持) / contradicts(否定) / neutral(どちらでもない)
  verified: true
```

事実の種類(`kind`)は次の通り。

| 種類 | 内容 | `verified: true` にする条件 | 根拠に使えるか |
|---|---|---|---|
| `fact` | 出典のある事実。ユーザーが提出した社内の資料にある事実を含む | `quote` が出典に実在し、`statement`、`value`、`unit`、`qualifiers` が `quote` と合っている | 使える |
| `derived` | 合計や比率などの計算値。`formula` に元の事実と計算式を書く | 元の事実が全て `verified: true` で、再計算の結果が一致する | 使える |
| `testimony` | ユーザーの証言。現場での経験、聞いた話など。誰の、何に基づく証言かを `source` に書く | ユーザーが内容を確認した | 使える。証言だけに頼る主張は、工程2でユーザーに示す |
| `image` | 画像の素材。下の「画像の素材」の節に定める | 同じ節に定める | 使える |
| `inference` | 推測 | 対象外 | 使えない |
| `opinion` | 意見 | 対象外 | 使えない |

`inference` と `opinion` をスライドに載せる場合は、推測または意見であることを文面に明示する。

出典のない事実を台帳に入れられるのは、`testimony` だけである。「広く知られている」ことを理由に、LLMが出典なしで事実を加えることは認めない。

使われない事実が台帳に残ることは問題としない。

### 画像の素材

スクリーンショット、写真、文書の抜粋、他の資料から引用した図は、画像の素材として素材台帳に登録する。画像をLLMに生成させて、実物として載せることは認めない。

```yaml
- id: A003
  kind: image
  file: assets/order-screen.png
  statement: 注文の入力画面
  source: 受注管理システム          # 何を写したものか。引用した図では、引用元
  version: "4.2"                    # 対象の版
  captured_at: 2026-11-10           # 取得した日
  environment: 検証環境             # 取得した環境
  regions:                          # 画像の中の要素と、その位置
    - id: due-date-field
      element: E-ui-due-date
      label: 納期の欄
      box: [0.30, 0.42, 0.25, 0.05]
      box_origin: recorded
    - id: save-button
      element: E-ui-save            # 仕組みの定義の要素。対応するものがある場合
      label: 保存ボタン
      box: [0.82, 0.90, 0.10, 0.05] # 画像の幅と高さに対する割合(左、上、幅、高さ)
      box_origin: recorded          # recorded(取得と同時に機械的に記録) / user(ユーザーが指定) / estimated(LLMが推定)
  masked: [顧客名の列]               # 隠した箇所
  verified: true
```

隠す作業は、収集セッションが画像そのものを加工して行う。加工する前の画像は、資料のリポジトリに置かない。画像を差し替えた場合にやり直す検査は、[不合格と修正の手順](../rework.md)の表による。

画像の中の位置は、レイアウトではなく、画像に付属する事実として扱う。位置を書くのは画像の素材の `regions` だけである。スライド仕様は、位置ではなく `regions` の `id` を参照する。

位置の出どころの信頼の順位は、`recorded`、`user`、`estimated` の順とする。`estimated` の位置は、注釈を描いた後に確かめる([工程7](07-slide-spec.md))。

`verified: true` にする条件は、下の合格条件の「画像の素材」の全てである。

### 仕組みの定義 `01-model.yaml`

実在の仕組みを写す図を使う資料では、要素とつながりを出典から抜き出して登録する。書式と抜き出し方は[仕組みの定義](../model.md)に定める。合格条件は、下の合格条件の「仕組みの定義」に置く。

## 作り方

### 問いの分解

担当: 設計セッション。

1. [資料の型](../deck-types.md)の定義が定める問いの最初の分解(`decomposition`)を出発点にする。問いに合わなければ変えてよい。
2. 枝分かれのたびに、分けた基準を `axis` に書く。
3. 何を見れば答えが分かるかを言えるところまで分解する。言えたら、それを `evidence_type` に書いて末端とする。
4. 資料の型の定義が定める観点(`perspectives`)を、全て問いとして含める。
5. 末端の問いに重要度を付ける。対立する仮説の間で予想される答えが分かれる問いを `high` とする。どの仮説でも答えが同じになる問いは `low` とする。

### 計画の承認

担当: ユーザー。

集める前に、ユーザーが探索の計画を承認する。

### 調査依頼

担当: 設計セッション。

調査は設計セッションや執筆のセッションから直接行わず、調査依頼として収集セッションに渡す。調査依頼は、Issueとして出す([Gitでの管理](../git.md))。調査依頼は、探索の計画の末端の問いをそのまま渡す。「Aを裏付ける事実を探せ」のような、結論を含む聞き方をしない。

調査依頼の項目:

- 知りたいこと(1文の問い)
- 探索の計画のどの問いに対応するか
- 返す形式(素材台帳の書式)
- 見つからなかった場合は「見つからない」と返すこと

### 収集

担当: 収集セッション。

素材台帳の `answers` までの項目を書く。収集セッションは仮説の一覧を読まない。

ユーザーの知識は、次のように取り込む。

- 社内の資料にある事実は、資料を提出してもらい、`fact` として引用箇所を確認する。
- 資料のない経験や伝聞は、`testimony` として記録する。

### 仮説への立場

担当: 設計セッション。

収集の後に、事実ごとに、仮説に対する `stance` を書く。

### 終了の判断

担当: 設計セッション。

収集のたびに、末端の問いごとの結果を次の4つのいずれかで記録する。

| 結果 | 意味 |
|---|---|
| `answered` | 答えが出た |
| `partial` | 一部だけ出た |
| `not-found` | 見つからない |
| `disputed` | 見解が割れている |

`answered` とする条件は、重要度による。

| 重要度 | 条件 |
|---|---|
| `high` | 独立した `origin` が2つ以上ある、または一次情報が1つある |
| `low` | 情報源が1つある |

次のいずれかで探索を終える。

- 重要度が `high` の問いの全てが `answered` または `disputed` になった。
- 追加の収集を2回続けても、新しい事実が出なかった。
- ユーザーが決めた上限(回数や期限)に達した。

2つ目と3つ目で終えた場合は、`answered` にならなかった問いを限界としてユーザーに示す。ユーザーの判断は、設計の判断の記録に残す。

`disputed` は結果として認める。見解が割れていることを、工程2で主張に反映する。

網羅したことは証明できない。確かめられるのは、承認した計画に対して漏れがないことまでである。

工程2で裏付けのない主張が見つかれば、この工程に戻って調べるか、その主張を捨てる。

### 限界の扱い

担当: ユーザー。

限界を明記して先に進むか、探索を延ばすかは、ユーザーが決める。

探索の計画:

- 全ての枝分かれに `axis` がある。全ての末端の問いに `evidence_type` と `priority` がある(機械)。 `K01-01`
- 資料の型の定義が定める観点が、全て問いに含まれる(機械)。 `K01-02`
- 枝分かれが、分類の軸の検査を通る(検査セッション)。 `K01-03` [定義](../checks.md#意味の検査)
- 末端の問いが全て答えられたら、ブリーフの問いに答えられる(検査セッション)。 `K01-04`
- 計画の内容に同意する(ユーザー)。 `K01-05`

素材台帳:

- 全ての `fact` に `source`、`locator`、`quote` がある(機械)。 `K01-06`
- 全ての `derived` の計算式が、元の事実の値から再計算して一致する(機械)。 `K01-07`
- `fact` の `quote` が出典に実在する。`quote` の切り取り方が、出典の前後にある条件、範囲、主体を落としていない。落としている場合は、`quote` を広げる(検査セッション。重大な検査)。確認できないものは `verified: false` のまま残す。 `K01-08`
- `fact` の `value` と `unit` が、`quote` の中の数値と単位に一致する(機械。表記を正規化して照合する)。 `K01-09`
- `fact` の `statement` が、`quote` の述べていることと合う。`qualifiers` が、`quote` にある条件、範囲、数量の幅、不確かさを漏れなく挙げている(検査セッション。重大な検査)。 `K01-10`
- 数値を持つ全ての事実に `metric` があり、語彙表の語である(機械)。 `K01-11`
- 同じ `metric` を持つ事実どうしで、時点と範囲が同じなのに値が違うものを挙げる。使わない事実に `superseded_by` を書くか、該当する問いの結果を `disputed` とする(機械が挙げ、設計セッションが決める)。 `K01-12`
- 全ての `testimony` に、誰の、何に基づく証言かの記録がある(機械)。 `K01-13`
- 探索の計画の全ての末端の問いに `result` がある(機械)。 `K01-14`
- 調査依頼の文面が、仮説や結論を含まない(検査セッション)。 `K01-15`
- 画像の素材を除く全ての事実に、全ての仮説に対する `stance` がある(機械)。 `K01-16`
- 仮説の一覧に、対立する仮説が1つ以上ある(機械)。 `K01-17`
- 終了の判断の条件のいずれかを満たす(機械)。 `K01-18`

画像の素材(`verified: true` にする条件):

- `source`、`version` または `captured_at` がある(機械)。 `K01-19`
- 画像が `statement` の通りのものを写している(検査セッション)。 `K01-20`
- `regions` の全てについて、位置が `label` の対象を囲んでいる。位置の出どころによらず確かめる(検査セッション)。 `K01-21`
- 写り込みの検査を通る。検査セッションには、ブリーフの「外に出せない情報」を渡す。個人の名前、顧客の情報、認証の情報、社外に出せない名称が、隠されずに写っていない(検査セッション。重大な検査)。例外を認めない。 `K01-22`
- 引用した図では、引用元の表記に必要な情報がある(機械)。 `K01-23`

仕組みの定義(実在の仕組みを写す図を使う資料):

- 全ての要素、つながり、場面に、`verified: true` の事実が紐づく(機械)。 `K01-24` [定義](../model.md)
- 要素の1件ごとに、その要素が出典にあり、名前と種類が出典の記述と合う(検査セッション。重大な検査)。 `K01-25` [定義](../model.md#抜き出し)
- つながりの1件ごとに、向きと条件が出典の記述と合う(検査セッション。重大な検査)。 `K01-26` [定義](../model.md#抜き出し)
- 場面の1件ごとに、順序が出典の記述と合う(検査セッション。重大な検査)。 `K01-27` [定義](../model.md#抜き出し)
- `summarizes` のあるつながりが、元のつながりを順にたどったものになっている(機械)。 `K01-28` [定義](../model.md#抜き出し)
- 資料の中心になる図に使う範囲は、別のセッションが同じ出典から独立に抜き出し、差分を出す。一方にしかない要素とつながりを、ユーザーが確認する(検査セッションとユーザー)。 `K01-29` [定義](../model.md)
- 定義の全体を図にしたものを見て、内容に同意する。証言に基づく箇所と `unknown` の箇所には印を付けて示す(ユーザー)。 `K01-30` [定義](../model.md)
