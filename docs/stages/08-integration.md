# 工程8 全体検査(結合テスト)

[目次に戻る](../README.md)

状態: 下書き。ユーザーとの合意の前である。末尾に、未決の点と、ほかの工程に及ぶ変更を挙げる。

章ごとに作ったスライドを結合し、通しで動かして、エラーが出ないことを確かめる。ソフトウェア開発の結合テストの方法を、スライドに当てはめる。

資料が動くのは、読み手が最初から順に読むときである。読み手は、前のスライドで得た理解を持ったまま次に進む。この持ち越される理解が、プログラムの実行中の状態にあたる。通しで動かすとは、結合した実物を順に読み、読み手が止まる箇所を見つけることである。

## 対応

| ソフトウェアの結合テスト | スライドでの対応 |
|---|---|
| 部品 | スライド。章は部品のまとまり |
| 部品の間のつなぎ目 | スライドや章をまたいで受け渡されるもの。語、事実、主張、図の要素、色と型の約束、他のスライドへの言及、章から章へのつなぎ |
| つなぎ目の仕様 | 章の契約(下の節)、ストーリーライン、語彙表、表現の対応表 |
| 単体テスト | 工程7のスライドごとの検査 |
| 結合テスト | この工程。結合した実物を順に読む |
| 受け入れテスト | 工程9。ユーザーがブリーフに照らして判断する |
| 実行 | 読み手の役のセッションが、最初から順に読む |
| 実行中の状態 | 読み手がここまでに得た理解 |
| エラー | 読み手が止まる箇所 |
| テストの場面と、期待する結果 | 読み方の種類と、読み終えたときに読み手が得ているはずの理解。設計の時期に書く |
| 仮の部品(スタブ) | まだ書かれていない章の、見出しだけのスライド |
| 段階的な結合 | 章を受け入れるたびに、骨組みの資料の該当部分を実物に差し替えて通す |
| 開始の条件、終了の条件 | 下の節 |
| 不具合の記録 | Issue。再現の方法、期待した結果、実際の結果、重大度、混入した工程 |
| 回帰テスト | 直した後に、変わった章から先を再び通す。過去の指摘を、場面として足していく |
| 網羅の確認 | 全てのつなぎ目を、いずれかの場面が通ったか |
| テストする者と作る者の分離 | 読み手の役のセッションは、設計の成果物を見ない |

## 章の契約

章と章のつなぎ目の仕様として、章ごとに、入口と出口の状態を定める。工程4で、ストーリーラインとあわせて書く。

```yaml
- chapter: ch3
  entry:                       # この章に入る時点で、読み手が既に得ているもの
    terms: [契約企業, 利用者]
    accepted: [C1]             # 納得している主張
    open_questions: [なぜ△△の領域だけが伸びるのか]
  exit:                        # この章を出る時点で、読み手が得ているもの
    terms: [継続率]
    accepted: [C2]
    answered: [なぜ△△の領域だけが伸びるのか]
    open_questions: [自社はその領域で勝てるのか]
    concerns_answered: [費用が見合うのか]   # ブリーフの読み手の懸念のうち、この章で答えるもの
```

ある章の入口の状態は、それより前の章の出口の状態で満たされていなければならない。これは設計の時点で機械的に確かめられる。結合テストでは、実際に読んだ結果の状態が、契約の通りになっているかを確かめる。

章の執筆のセッションには、その章の契約を渡す。章を単独で書くときの前提が、これで決まる。

## テストの場面

場面と、期待する結果は、設計の時期に書く。作った後で、出来上がりに合わせて期待を決めない。

| 場面 | 読み方 | 期待する結果 |
|---|---|---|
| 主な読み手の通読 | ブリーフの主な読み手として、最初から最後まで読む | 各章の出口で、章の契約の通りの状態になる。最後に、結論と、求められている行動を述べられる。未回答の疑問がない |
| 反対の立場の通読 | 結論に懐疑的な読み手として読む | 主張の骨子に書いた反論の全てに、本編か付録で答えを得る |
| 要約だけ | 要約のスライドだけを読む | 結論と、支える主張を述べられる |
| 途中から | 配布する資料で、指定した章から読み始める | その章の入口の状態を、章扉と前の章のまとめから得られる |
| 発表の通し | 口頭の資料で、ノートを話として順に読む | 話が切れずにつながる。章ごとの時間が、配分の通りに収まる |
| 過去の指摘 | 過去に受けた指摘が再発していないかを、該当の箇所で確かめる | 再発していない |

## 結合の進め方

最後に全ての章をまとめて初めて通すのではなく、段階的に結合する。最後にまとめて通すと、エラーの原因の切り分けが難しく、手戻りが大きい。

1. 工程4の骨組みの資料を土台にする。この時点では、全てのスライドが見出しだけの仮の部品である。
2. 章を受け入れるたびに、その章を実物に差し替えてビルドし、主な読み手の通読を、その章について実行する。前の章が未完成なら、入口の状態は章の契約から与える。
3. 全ての章がそろい、要約と章のまとめを組み立てた後に、全ての場面を通しで実行する。

### 要約と章のまとめの組み立て

全体を通す前に、設計セッションが組み立てる。新しい文を書かない。承認済みの文を選び、並べ、短くする。

| スライド | 材料 |
|---|---|
| 要約 | 主張の骨子の `answer` と主張、結びの章の主張 |
| 章のまとめ | その章の主張、その章のスライドの結論1行 |

各行に、元にした文を `from` として記録する。読み手に合わせた強調は、どの文を選ぶかと、並べる順で表す。

## 開始の条件

次を満たしてから、通しの実行に入る。これらはテストそのものではなく、動かすための前提である。

- 機械的な検査のコマンドが通る。コミット前の検査は飛ばされうるため、ここで再実行する(機械)。
- 保留のスライドが0件である(機械)。
- 合格が無効になったスライドが0件である(機械。[体制とセッション](../organization.md))。
- ビルドが成功し、描画上の診断が0件である(機械)。
- 枚数と見出しが、ストーリーライン、および導出したスライドと一致する(機械)。
- 要約と章のまとめの全ての行に `from` があり、数値が元の文と一致し、工程7と同じ文の検査を通る(機械)。

## 実行の方法

読み手の役のセッションに、ブリーフの読み手の情報(立場、既に知っていること、懸念)だけを渡す。設計の成果物は渡さない。

読むのは、ビルドした実物である。要約版や仕様ではなく、読み手が実際に目にするスライドの画像を、順に読む。

セッションは、次の状態を持ち越す。

- ここまでに定義された語
- ここまでに示された事実と、納得した主張
- まだ答えられていない疑問
- まだ果たされていない約束(「後で述べる」とされた内容、目次に挙げられた内容)

1枚ごとに、次を行う。

1. そのスライドが、状態にないものを前提にしていないかを確かめる。
2. エラーがあれば、種類と、食い違う相手の箇所を添えて記録する。
3. 状態を更新する。

章の終わりごとに、状態を保存する。状態を明示して持ち越すので、章ごとに区切って実行でき、後から途中の章から再実行できる。

実行の記録(スライドごとの状態とエラー)は、成果物として残す。

## エラーの種類

| エラー | 内容 |
|---|---|
| 未定義の語 | まだ説明されていない語や略語が出てくる |
| 前提の先取り | まだ示されていない事実や主張を、既知のものとして使っている |
| 既出との矛盾 | 前のスライドで述べたことと食い違う |
| 繰り返し | 既に述べたことを、初めてのように述べ直している |
| 飛躍 | 前のスライドから、なぜ次の話になるのかが分からない |
| 約束の未回収 | 「後で述べる」とした内容や、目次に挙げた内容が出てこない |
| 問いの置き去り | 途中で読み手に抱かせた疑問に、最後まで答えていない |
| 作法の変化 | 章が変わると、文体、図の描き方、数値の書き方、色の使い方が変わる |
| 現在地の喪失 | 今どの章のどの話なのかが分からなくなる |
| 契約との不一致 | 章の出口の状態が、章の契約と違う |

## 不具合の記録と裁定

エラーは、1件ずつIssueにする。項目は次の通り。

- 場面と、発生したスライド
- エラーの種類
- 期待した結果と、実際の結果。食い違う相手の箇所があれば、両方を引用する
- 重大度
- 混入した工程(裁定で決める)

| 重大度 | 基準 |
|---|---|
| 高 | 読み手が結論にたどり着けない、または誤った理解をする |
| 中 | 読み手が止まるが、読み進めれば分かる |
| 低 | 気になるが、理解を妨げない |

読み手の役のセッションの指摘は、候補として扱う。設計セッションが、引用された箇所を見比べて、実際にエラーかどうかを裁く。エラーと認めたものについて、混入した工程を決め、その工程に戻す。

- 中身の文や結論1行に原因がある場合は、章の執筆のセッションに返す(工程7)。
- 見出しや順序に原因がある場合は、ストーリーラインに戻す(工程4)。ユーザーの承認を取り直す。
- 章の契約そのものに原因がある場合も、工程4に戻す。

修正は1件ずつ行わず、章ごとにまとめて1回で行う。PMや、テストしたセッションは、スライドを直さない。

## 回帰テスト

直した後は、変わった章の入口の状態を保存済みの状態から復元し、その章から先を再び通す。変わっていない前の章は、読み直さない。

ユーザーから受けた指摘は、直すだけでなく、「過去の指摘」の場面に加える。次に資料を直したときに、同じ問題が戻っていないかを確かめられる。

引き渡した後に資料を改訂する場合も、同じ方法をとる。変えた箇所から先を通し、過去の指摘の場面を実行する。

## 網羅の確認

次のつなぎ目の全てが、いずれかの場面の実行で通ったことを、実行の記録から機械的に確かめる。

- 全ての章の境目
- 全ての語の初出
- 他のスライドへの全ての言及
- ブリーフの読み手の全ての懸念
- 主張の骨子の全ての主張と反論

あわせて、上流から下流までの対応(問い、答え、主張、章、スライド、事実)を表にし、対応のない項目がないことを確かめる。

## 終了の条件

- 全ての場面を実行している(機械)。
- 網羅の確認で、通っていないつなぎ目がない(機械)。
- 重大度が高のエラーが0件である(機械。Issueの状態)。
- 重大度が中のエラーは、直すか、ユーザーが受け入れると決めている(ユーザー)。
- 重大度が低のエラーと、受け入れたエラーは、工程9の検査の報告に載せる(機械)。
- 往復の回数が上限を超えた場合は、PMがユーザーに上げる。

## この工程でやらないこと

- 工程7で済んだスライドごとの検査(裏付けのない文、限定の残存、削る検査、文体)を、全スライドでやり直さない。
- 文の好みや語感の調整をしない。
- 事実、スライド、型を足さない。足りなければ上流に戻す。
- 通すために、期待する結果や終了の条件を緩めない。

## 未決の点

- 読み手の役のセッションが、状態を正しく持ち越し、エラーを見逃さずに挙げられるか。誤検出がどの程度出るか。
- 章の契約を、設計の時点でどこまで具体的に書けるか。
- 画像を読む方法と、ビルドした実物から文字を抜き出して読む方法の、どちらが確かで安いか。
- 往復の回数の上限。
- 要約を組み立てに限ることで、読み手に合わせた強調が足りるか。

## ほかの工程に及ぶ変更

- 工程4で、章の契約と、テストの場面の期待する結果を書く。ブリーフの読み手の懸念を、どの章で答えるかを決める。
- 工程7で、章の受け入れのたびに、その章を骨組みの資料に差し替えて通す。描画上の診断を、章の受け入れの条件にする。
- 「同じ事実が複数のスライドに出ない」と「やり取りの図の要素が構成の図にも出る」の検査を、工程5に移す。
- 「全体図と詳細図で要素の位置が保たれる」を、描画の実装の条件に移す。
- 結びの章の主張に、誰が、何を、いつまでにするかを書くことを、工程3の条件にする。
- 合格が無効になったスライドの仕組みを、体制の文書に加える。
