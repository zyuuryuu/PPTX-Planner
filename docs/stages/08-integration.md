# 工程8 全体検査(結合テスト)

[目次に戻る](../README.md)

状態: 方向はユーザーと合意した。読み手の役のセッションの確かさなど、試作で確かめる点を末尾に挙げる。

章ごとに作ったスライドを結合し、通しで動かして、エラーが出ないことを確かめる。ソフトウェア開発の結合テストの方法を、スライドに当てはめる。

資料が動くのは、読み手が最初から順に読むときである。読み手は、前のスライドで得た理解を持ったまま次に進む。この持ち越される理解が、プログラムの実行中の状態にあたる。通しで動かすとは、結合した実物を順に読み、読み手が止まる箇所を見つけることである。

## 対応

| ソフトウェアの結合テスト | スライドでの対応 |
|---|---|
| 部品 | スライド。章は部品のまとまり |
| 部品の間のつなぎ目 | スライドや章をまたいで受け渡されるもの。語、事実、主張、図の要素、色と型の約束、他のスライドへの言及、章から章へのつなぎ |
| つなぎ目の仕様 | 章の前提と到達点(下の節)、ストーリーライン、語彙表、表現の対応表 |
| 単体テスト | 工程7のスライドごとの検査 |
| 結合テスト | この工程。結合した実物を順に読む |
| 受け入れテスト | 工程9。ユーザーがブリーフに照らして判断する |
| 実行 | 読み手の役のセッションが、最初から順に読む |
| 実行中の状態 | 読み手がここまでに得た理解 |
| エラー | 読み手が止まる箇所 |
| テストの場面と、期待する結果 | 読み方の種類と、読み終えたときに読み手が得ているはずの理解。設計の時期に書く |
| 仮の部品(スタブ) | まだ書かれていない章の、見出しだけのスライド |
| 段階的な結合 | 章を受け入れるたびに、骨組みの資料の該当部分を実物に差し替えて通す |
| 開始の条件、終了の条件 | 下の節 |
| 不具合の記録 | Issue。再現の方法、期待した結果、実際の結果、重大度、混入した工程 |
| 回帰テスト | 直した後に、変わった章から先を再び通す。過去の指摘を、場面として足していく |
| 網羅の確認 | 全てのつなぎ目を、いずれかの場面が通ったか |
| テストする者と作る者の分離 | 読み手の役のセッションは、設計の成果物を見ない |

## 章の前提と到達点

章と章のつなぎ目の仕様として、章ごとに、読み手が何を知った状態で入り、何を知った状態で出るかを定める。[工程4](04-storyline.md)で、ストーリーラインとあわせて書く。

```yaml
- chapter: ch3
  entry:                       # この章に入る時点で、読み手が既に得ているもの
    terms: [契約企業, 利用者]
    accepted: [C1]             # 納得している主張
    open_questions: [なぜ△△の領域だけが伸びるのか]
  exit:                        # この章を出る時点で、読み手が得ているもの
    terms: [継続率]
    accepted: [C2]
    answered: [なぜ△△の領域だけが伸びるのか]
    open_questions: [自社はその領域で勝てるのか]
    concerns_answered: [費用が見合うのか]   # ブリーフの読み手の懸念のうち、この章で答えるもの
```

ある章の入口の状態は、それより前の章の出口の状態で満たされていなければならない。これは設計の時点で機械的に確かめられる。結合テストでは、実際に読んだ結果の状態が、定めた通りになっているかを確かめる。

章の執筆のセッションには、その章の前提と到達点を渡す。章は別々のセッションが並行して書くため、ほかの章の中身を読まなくても、どの語や主張を説明済みとして使ってよいかが、これで決まる。

## テストの場面

場面と、期待する結果は、設計の時期に書く。作った後で、出来上がりに合わせて期待を決めない。

| 場面 | 読み方 | 期待する結果 |
|---|---|---|
| 主な読み手の通読 | ブリーフの主な読み手として、最初から最後まで読む | 各章の出口で、定めた到達点の通りの状態になる。最後に、結論と、求められている行動を述べられる。未回答の疑問がない |
| 反対の立場の通読 | 結論に懐疑的な読み手として読む | 主張の骨子に書いた反論の全てに、本編か付録で答えを得る |
| 要約だけ | 要約のスライドだけを読む | 結論と、その理由を述べられる |
| 途中から | 配布する資料で、指定した章から読み始める | その章の入口の状態を、章扉と前の章のまとめから得られる |
| 発表の通し | 口頭の資料で、ノートを話として順に読む | 話が切れずにつながる。章ごとの時間が、配分の通りに収まる |
| 過去の指摘 | 過去に受けた指摘が再発していないかを、該当の箇所で確かめる | 再発していない |

## 結合の進め方

最後に全ての章をまとめて初めて通すのではなく、段階的に結合する。最後にまとめて通すと、エラーの原因の切り分けが難しく、手戻りが大きい。

1. 工程4の骨組みの資料を土台にする。この時点では、全てのスライドが見出しだけの仮の部品である。
2. 章を受け入れるたびに、その章を実物に差し替えてビルドし、主な読み手の通読を、その章について実行する。前の章が未完成なら、入口の状態は章の前提と到達点から与える。
3. 全ての章がそろい、要約と章のまとめを用意した後に、全ての場面を通しで実行する。

### 要約と章のまとめ

全体を通す前に、設計セッションが用意する。この工程で新しい文を書かない。設計の時期に承認済みの文を使う。

| スライド | 使う文 |
|---|---|
| 要約 | 主張の骨子の要約の文(`summary`)。工程2でユーザーが承認している。そのまま使う |
| 章のまとめ | その章の主張(`message`)。工程3でユーザーが承認している。そのまま使う |

要約は、結論と理由を1つの文にまとめたものとする。結論の下に根拠を箇条書きで並べる形は、主張を並べ直しただけで、要約にならない。

```yaml
- id: summary
  kind: summary
  text: 〇〇事業は、伸びている△△領域に絞れば、当社の継続率の高さを生かして2年で黒字に戻せる見込みである
  from: summary
  ask: 来月の経営会議で、△△領域への集中を決定いただきたい   # 結びの章の主張。載せるかどうかは表現規約で決める
  ask_from: ch7
```

要約に根拠を短く添えるかどうかは、資料の表現規約で決める。既定は、添えない。添える場合は、主張の骨子の主張を短くして並べ、元にした主張を記録する。元の主張より強い言い方にしない。

工程7の結果、承認済みの文が本編と合わなくなっている場合は、ここで書き直さない。工程2または工程3に戻し、ユーザーの承認を取り直す。

## 開始の条件

次を満たしてから、通しの実行に入る。これらはテストそのものではなく、動かすための前提である。

- 機械的な検査のコマンドが通る。コミット前の検査は飛ばされうるため、ここで再実行する(機械)。
- 保留のスライドが0件である(機械)。
- 合格が無効になったスライドが0件である(機械。[体制とセッション](../organization.md))。
- ビルドが成功し、描画上の診断が0件である(機械)。
- 枚数と見出しが、ストーリーライン、および導出したスライドと一致する(機械)。
- 要約と章のまとめの文が、元にした承認済みの文と一致する(機械)。
- 要約に根拠を添える場合は、各行に元にした主張があり、数値が一致し、元の主張より強い言い方になっていない(機械と検査セッション)。

## 実行の方法

読み手の役のセッションに、ブリーフの読み手の情報(立場、既に知っていること、懸念)だけを渡す。設計の成果物は渡さない。

読むのは、ビルドした実物である。要約版や仕様ではなく、読み手が実際に目にするスライドの画像を、順に読む。

セッションは、次の状態を持ち越す。

- ここまでに定義された語
- ここまでに示された事実と、納得した主張
- まだ答えられていない疑問
- まだ果たされていない約束(「後で述べる」とされた内容、目次に挙げられた内容)
- 示された枠組み(「3つの観点で評価する」など)と、それが後で使われたか
- 説明に使われた例と、想定の場面
- 冒頭で示された結論

1枚ごとに、次を行う。

1. そのスライドが、状態にないものを前提にしていないかを確かめる。
2. ブリーフの読み手の水準で、そのスライドを理解できたかを記録する。
3. エラーがあれば、種類と、食い違う相手の箇所を添えて記録する。
4. 状態を更新し、何が増えたかを記録する。

章の終わりごとに、状態を保存する。状態を明示して持ち越すので、章ごとに区切って実行でき、後から途中の章から再実行できる。

実行の記録(スライドごとの状態とエラー)は、成果物として残す。

## エラーの種類

全体を通して初めて分かる悪い品質を、エラーとして定める。フィードバックで新しい種類が見つかれば、既存の種類に入らないことを確かめたうえで足す。

### 通読で見つけるもの

読み手の役のセッションが、状態と照らして見つける。

| 区分 | エラー | 内容 |
|---|---|---|
| 前提 | 未定義の語 | まだ説明されていない語や略語が出てくる |
| 前提 | 専門的すぎる説明 | 説明はあるが、ブリーフの読み手の水準では理解できない |
| 前提 | 前提の先取り | まだ示されていない事実や主張を、既知のものとして使っている |
| 筋 | 既出との矛盾 | 前のスライドで述べたことと食い違う |
| 筋 | 飛躍 | 前のスライドから、なぜ次の話になるのかが分からない |
| 筋 | 停滞 | 読む前と後で、読み手の状態が変わらない。理解が深まらない |
| 筋 | 繰り返し | 既に述べたことを、初めてのように述べ直している |
| 筋 | 枠組みの放棄 | 冒頭で示した観点や分類が、後で使われない。または、別の観点に入れ替わる |
| 筋 | 結論のぶれ | 冒頭の結論、結びの結論、要約の結論が食い違う。要約が本編より強いことを述べている |
| 筋 | 語の意味のずれ | 同じ語が、場所によって違う意味で使われる |
| 筋 | 抽象度の急変 | 方針の話から、橋渡しなしに細部の話に移る。またはその逆 |
| 筋 | 例の不統一 | 説明に使う例や想定の場面が、断りなく入れ替わる |
| 回収 | 約束の未回収 | 「後で述べる」とした内容や、目次に挙げた内容が出てこない |
| 回収 | 問いの置き去り | 途中で読み手に抱かせた疑問に、最後まで答えていない |
| 回収 | 依頼の曖昧 | 読み終えても、何を求められているかが分からない |
| 負担 | 水準の揺れ | あるスライドは初歩から説明し、別のスライドは専門知識を前提にする |
| 負担 | 現在地の喪失 | 今どの章のどの話なのかが分からなくなる |
| 作法 | 作法の変化 | 章が変わると、文体、図の描き方、数値の書き方、色の使い方が変わる |
| 到達点 | 到達点との不一致 | 章の出口の状態が、定めた到達点と違う |

### 集計で見つけるもの

実行の記録と、スライド仕様から、機械的に集計する。目安を超えたものをエラーの候補とする。目安の値は、資料の表現規約に置く。

| 区分 | エラー | 集計するもの |
|---|---|---|
| 負担 | 新出の集中 | スライドごと、および連続する数枚での、新しい語と概念の数。実行の記録の状態の変化から数える |
| 負担 | 緩急のなさ | スライドごとの字数と要素の数の並び。重いスライドの連続、全体が同じ密度であること |
| 負担 | 単調 | 同じ型が連続する枚数 |
| 筋 | 尻すぼみ | 章ごとの、スライドあたりの字数と事実の数。後半の章だけ薄くなっていないか |
| 筋 | 配分の偏り | ブリーフの読み手の懸念ごとの、答えているスライドの枚数。懸念に対応しない章の枚数 |
| 信頼 | 数値の基準の不一致 | 同じ指標を表す事実どうしで、時点、範囲、単位が違うもの。素材台帳の `qualifiers` と `unit` を比べる |
| 信頼 | 言い回しの反復 | 資料全体での、同じ言い回しと同じ文型の出現回数 |
| 信頼 | 人称と語調の揺れ | 書き手を指す語(当社、弊社、我々など)と、文末の形の混在 |
| 信頼 | 残骸 | 存在しないスライドや事実への言及。語彙表にない固有の名称。置き換えられずに残ったID |

言い回しの反復は、1枚ずつでは問題のない文でも、資料全体で並ぶと目立つ。スライドごとの検査では見つからない。

## 不具合の記録と裁定

エラーは、1件ずつIssueにする。項目は次の通り。

- 場面と、発生したスライド
- エラーの種類
- 期待した結果と、実際の結果。食い違う相手の箇所があれば、両方を引用する
- 重大度
- 混入した工程(裁定で決める)

| 重大度 | 基準 |
|---|---|
| 高 | 読み手が結論にたどり着けない、または誤った理解をする |
| 中 | 読み手が止まるが、読み進めれば分かる |
| 低 | 気になるが、理解を妨げない |

読み手の役のセッションの指摘は、候補として扱う。設計セッションが、引用された箇所を見比べて、実際にエラーかどうかを裁く。エラーと認めたものについて、混入した工程を決め、その工程に戻す。

- 中身の文や結論1行に原因がある場合は、章の執筆のセッションに返す(工程7)。
- 見出しや順序に原因がある場合は、ストーリーラインに戻す(工程4)。ユーザーの承認を取り直す。
- 章の前提と到達点そのものに原因がある場合も、工程4に戻す。

修正は1件ずつ行わず、章ごとにまとめて1回で行う。PMや、テストしたセッションは、スライドを直さない。

## 回帰テスト

直した後は、変わった章の入口の状態を保存済みの状態から復元し、その章から先を再び通す。変わっていない前の章は、読み直さない。

ユーザーから受けた指摘は、直すだけでなく、「過去の指摘」の場面に加える。次に資料を直したときに、同じ問題が戻っていないかを確かめられる。

引き渡した後に資料を改訂する場合も、同じ方法をとる。変えた箇所から先を通し、過去の指摘の場面を実行する。

## 網羅の確認

次のつなぎ目の全てが、いずれかの場面の実行で通ったことを、実行の記録から機械的に確かめる。

- 全ての章の境目
- 全ての語の初出
- 他のスライドへの全ての言及
- ブリーフの読み手の全ての懸念
- 主張の骨子の全ての主張と反論

あわせて、上流から下流までの対応(問い、答え、主張、章、スライド、事実)を表にし、対応のない項目がないことを確かめる。

## 終了の条件

- 全ての場面を実行している(機械)。
- 網羅の確認で、通っていないつなぎ目がない(機械)。
- 重大度が高のエラーが0件である(機械。Issueの状態)。
- 重大度が中のエラーは、直すか、ユーザーが受け入れると決めている(ユーザー)。
- 重大度が低のエラーと、受け入れたエラーは、工程9の検査の報告に載せる(機械)。
- 往復の回数が上限を超えた場合は、PMがユーザーに上げる。

## この工程でやらないこと

- 工程7で済んだスライドごとの検査(裏付けのない文、限定の残存、削る検査、文体)を、全スライドでやり直さない。
- 文の好みや語感の調整をしない。
- 事実、スライド、型を足さない。足りなければ上流に戻す。
- 通すために、期待する結果や終了の条件を緩めない。

## 未決の点

- 読み手の役のセッションが、状態を正しく持ち越し、エラーを見逃さずに挙げられるか。誤検出がどの程度出るか。特に、枠組みの放棄、抽象度の急変、水準の揺れ、語の意味のずれは、通読に頼る。
- 集計で見つけるエラーの、目安の値。
- 章の前提と到達点を、設計の時点でどこまで具体的に書けるか。
- 画像を読む方法と、ビルドした実物から文字を抜き出して読む方法の、どちらが確かで安いか。
- 往復の回数の上限。
