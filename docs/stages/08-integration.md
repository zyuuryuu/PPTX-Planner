# 工程8 全体検査

[目次に戻る](../README.md)

状態: 下書き。ユーザーとの合意の前である。末尾に、未決の点と、ほかの工程に及ぶ変更を挙げる。

章ごとに書いたスライド仕様を合わせ、全体でしか確かめられないことを確かめる。あわせて、要約と章のまとめを組み立てる。

この工程が見るのは、工程7で初めて生まれたものである。結論1行、中身の文、ノート、章と章の継ぎ目、要約と章のまとめがこれにあたる。見出しは工程4で、事実の割り当ては工程5で、既に全体を通して検査している。

## この工程でやらないこと

- 工程7で済んだスライドごとの検査(裏付けのない文、限定の残存、削る検査、文体)を、全スライドでやり直さない。
- 全スライドの中身を、1つの検査セッションに通読させない。
- 全スライドの画像を、検査セッションに見せない。
- PMや、全体を扱うセッションが、スライド仕様を直さない。指摘はIssueにして、章の執筆のセッションに返す。
- 見出しを書き換えない。事実、スライド、型を足さない。足りなければ上流に戻す。
- 文の好みや語感の調整をしない。検査を通った章どうしの文体の小さな差は、そのまま受け入れる。
- 通すために合格条件を緩めない。

## 成果物

- 要約版 `08-digest.md`。全スライドの見出しと結論1行を順に並べたもの。機械的に作る。
- 要約と章のまとめのスライド仕様 `07-slides/derived.yaml`。
- 指摘のIssue。

## 作り方

### 1. 機械的な検査を全て再実行する

コミット前の検査は飛ばされうるため、同じコマンドをここでもう一度実行する。

### 2. 古くなったスライドを挙げる

章を受け入れた後に、その章が使う上流の成果物(ストーリーライン、立証の設計、素材台帳、語彙表、表現の対応表)が変わっていないかを、Gitの差分とIDで確かめる。変わっていたスライドは、章の執筆のセッションに返す。

### 3. 要約と章のまとめを組み立てる

設計セッションが行う。新しい文を書かない。承認済みの文を選び、並べ、短くする。

| スライド | 材料 |
|---|---|
| 要約 | 主張の骨子の `answer` と主張、結びの章の主張 |
| 章のまとめ | その章の主張、その章のスライドの結論1行 |

各行に、元にした文を記録する。

```yaml
- id: summary
  kind: summary
  lines:
    - text: 〇〇事業は、△△に絞って継続すべきである
      from: answer
    - text: △△の領域だけが伸びている       # 短くしてよい。意味を変えない
      from: C1
```

読み手に合わせた強調は、どの文を選ぶかと、並べる順で表す。

結びの「依頼したいこと」は、ここでは書かない。工程3で、結びの章の主張として、誰が、何を、いつまでにするかを書き、ユーザーが承認している。

### 4. 検査セッションが確かめる

| 検査 | 方法 |
|---|---|
| 結論の復元 | `answer` を隠して要約版だけを渡し、資料の結論を書かせる。`answer` と比べる |
| 要約の読み戻し | 要約のスライドだけを渡し、内容を書き直させる。主張の骨子と比べる |
| 章の境目 | 章のまとめと、次の章の章扉、最初の見出しを渡す。前の章から次の章に進む理由が分かるかを確かめる。対象は章の境目の数だけである |
| 章をまたぐ矛盾(組の検査) | 同じ事実、要素、語を共有するスライドの組を機械で挙げ、その組だけを渡す |
| 章をまたぐ矛盾(通読) | 要約版を1回通読する。事実や語を共有しない矛盾(前提の食い違いなど)を拾うためである |

矛盾の指摘には、食い違う両方の文の引用を必須とする。指摘は候補として扱い、直す前に、設計セッションが実際に矛盾しているかを裁く。

### 5. 指摘を扱う

指摘を、次の2つに分ける。

| 区分 | 例 | 扱い |
|---|---|---|
| 差し戻す | 事実の誤り、裁定で認められた矛盾、結論の復元の不一致、古くなったスライド | Issueにして、章の執筆のセッション、または上流に返す |
| 受け入れる | 文の好み、警告 | Issueに残し、検査の報告に載せる。直さない |

- 指摘は1件ずつ直させない。章ごとにまとめ、1回で直す。
- 直した後の再検査は、変わったスライドと、そのスライドを入力に使う上の検査に限る。
- 往復の回数が上限を超えたら、PMがユーザーに上げる。

## 合格条件

状態:

- 保留のスライドが0件である(機械)。
- 差し戻しの区分のIssueが、全て閉じている(機械)。
- 古くなったスライドが0件である(機械)。

つながり:

- 全ての主張に、対応するスライドが1枚以上ある(機械)。
- 章構成で載せないと決めた答えが、本編に入っていない(機械)。
- 付録の全てのスライドが、本編のスライドのいずれかを補っている(機械)。
- 工程4で読み手の懸念に対応させたスライドが、残っている(機械)。
- 語が、定義するスライドより前に使われていない(機械)。
- 他のスライドへの言及の参照先が存在し、保留でない(機械)。

要約と章のまとめ:

- 全ての行に `from` があり、元の文が存在する(機械)。
- 行の中の数値が、元の文の数値と一致する(機械)。
- 工程7と同じ、文の機械的な検査、使う語彙の検査、収容量の検査を通る(機械)。
- 短くした行が、元の文の限定を落としていない(検査セッション)。
- 要約の読み戻しが、主張の骨子と合う(検査セッション)。

全体:

- 結論の復元が、`answer` と合う(検査セッション)。
- 章の境目の検査で、進む理由が分からない境目がない(検査セッション)。
- 矛盾の指摘のうち、設計セッションが認めたものが、全て解消している(機械。Issueの状態)。

## 未決の点

- 往復の回数の上限。
- 要約版(見出しと結論1行)の通読で、説明や図の中にある矛盾をどこまで拾えるか。

## ほかの工程に及ぶ変更

この下書きは、次の変更を前提にしている。合意の後に反映する。

- 「同じ事実が複数のスライドに出ない」の検査を、工程5に移す。事実の割り当ては工程5で決まるためである。違反ではなく警告とする。
- 「やり取りや状態の遷移の図の要素が、構成の図にも出る」の検査を、工程5に移す。
- 「全ての図が仕組みの定義だけを含む」は、構造上保証されており、工程5と7でも検査しているため、この工程の条件から外す。
- 「全体図と詳細図で要素の位置が保たれる」は、描画の実装の条件に移す。
- 読み手の懸念と、それに答えるスライドの対応を、工程4で付ける。
- 結びの章の主張に、誰が、何を、いつまでにするかを書くことを、工程3の条件にする。
- 見出しと結論1行の数値と、素材台帳の値との照合を、工程7で機械的に行う。
- 描画上の診断を、工程7の章の受け入れの条件にする。
