# 工程8 全体検査(結合テスト)

[目次に戻る](../README.md)

章ごとに作ったスライドを結合し、通しで動かして、エラーが出ないことを確かめる。ソフトウェア開発の結合テストの方法を、スライドに当てはめる。

資料が動くのは、読み手が最初から順に読むときである。読み手は、前のスライドで得た理解を持ったまま次に進む。この持ち越される理解が、プログラムの実行中の状態にあたる。通しで動かすとは、結合した実物を順に読み、読み手が止まる箇所を見つけることである。

## 対応

| ソフトウェアの結合テスト | スライドでの対応 |
|---|---|
| 部品 | スライド。章は部品のまとまり |
| 部品の間のつなぎ目 | スライドや章をまたいで受け渡されるもの。語、事実、主張、図の要素、色と型の約束、他のスライドへの言及、章から章へのつなぎ |
| つなぎ目の仕様 | 章の前提と到達点(下の節)、ストーリーライン、語彙表、表現の対応表 |
| 単体テスト | 工程7のスライドごとの検査 |
| 結合テスト | この工程。結合した実物を順に読む |
| 受け入れテスト | 工程9。ユーザーがブリーフに照らして判断する |
| 実行 | 読み手の役のセッションが、最初から順に読む |
| 実行中の状態 | 読み手がここまでに得た理解 |
| エラー | 読み手が止まる箇所 |
| テストの場面と、期待する結果 | 読み方の種類と、読み終えたときに読み手が得ているはずの理解。設計の時期に書く |
| 仮の部品(スタブ) | まだ書かれていない章の、題と要点だけのスライド |
| 段階的な結合 | 章を受け入れるたびに、骨組みの資料の該当部分を実物に差し替えて通す |
| 開始の条件、終了の条件 | 下の節 |
| 不具合の記録 | Issue。再現の方法、期待した結果、実際の結果、重大度、混入した工程 |
| 回帰テスト | 直した後に、変わった章から先を再び通す。過去の指摘を、場面として足していく |
| 網羅の確認 | 全てのつなぎ目を、いずれかの場面が通ったか |
| テストする者と作る者の分離 | 読み手の役のセッションは、設計の成果物を見ない |

## 章の前提と到達点

章と章のつなぎ目の仕様として、章ごとに、読み手が何を知った状態で入り、何を知った状態で出るかを定める。[工程4](04-storyline.md)で、ストーリーラインとあわせて書く。

```yaml
- chapter: ch3
  entry:                       # この章に入る時点で、読み手が既に得ているもの
    terms: [契約企業, 利用者]
    accepted: [C1]             # 納得している主張
    open_questions: [なぜ△△の領域だけが伸びるのか]
  exit:                        # この章を出る時点で、読み手が得ているもの
    terms: [継続率]
    accepted: [C2]
    answered: [なぜ△△の領域だけが伸びるのか]
    open_questions: [自社はその領域で勝てるのか]
    concerns_answered: [費用が見合うのか]   # ブリーフの読み手の懸念のうち、この章で答えるもの
```

ある章の入口の状態は、それより前の章の出口の状態で満たされていなければならない。これは設計の時点で機械的に確かめられる。結合テストでは、実際に読んだ結果の状態が、定めた通りになっているかを確かめる。

章の執筆のセッションには、その章の前提と到達点を渡す。章は別々のセッションが並行して書くため、ほかの章の中身を読まなくても、どの語や主張を説明済みとして使ってよいかが、これで決まる。

## テストの場面

場面と、期待する結果は、設計の時期に書く。作った後で、出来上がりに合わせて期待を決めない。

### 場面と読み方

| 場面 | 識別子 | 読み方 |
|---|---|---|
| 主な読み手の通読 | `main-reader` | ブリーフの主な読み手として、最初から最後まで読む |
| 反対の立場の通読 | `skeptic` | 結論に懐疑的な読み手として読む |
| 要約だけ | `summary-only` | 要約のスライドだけを読む |
| 題と要点だけ | `titles-and-points` | 機械が抜き出した、章、節、スライドの題と要点の一覧を、[題と要点の通読](../checks.md)の3段で読む |
| 途中から | `mid-entry` | 配布する資料で、指定した章から読み始める |
| 発表の通し | `talk-through` | 口頭の資料で、ノートを話として順に読む |
| 過去の指摘 | `past-feedback` | 過去に受けた指摘が再発していないかを、該当の箇所で確かめる |

### 期待する結果

| 場面 | 期待する結果 |
|---|---|
| 主な読み手の通読 | 各章の出口で、定めた到達点の通りの状態になる。最後に、結論と、求められている行動を述べられる。未回答の疑問がない |
| 反対の立場の通読 | 主張の骨子に書いた反論の全てに、本編か付録で答えを得る |
| 要約だけ | 結論と、その理由を述べられる |
| 題と要点だけ | 章の要点から結論を、節の要点から章の要点を、スライドの要点から節の要点を述べられる。題に重複がなく、話題の順が自然である |
| 途中から | その章の入口の状態を、章扉と、前の章の要点を載せるスライドから得られる。章のまとめがこれに当たる。節が1つだけの章では、節の要点を載せるスライドが当たる |
| 発表の通し | 話が切れずにつながる。全体の時間が、ブリーフの制約に収まる |
| 過去の指摘 | 再発していない |

## 結合の進め方

担当: PM。

最後に全ての章をまとめて初めて通すのではなく、段階的に結合する。最後にまとめて通すと、エラーの原因の切り分けが難しく、手戻りが大きい。

1. 工程4の骨組みの資料を土台にする。この時点では、全てのスライドが題と要点だけの仮の部品である。
2. 章を受け入れるたびに、その章を実物に差し替えてビルドし、主な読み手の通読を、その章について実行する。前の章が未完成なら、入口の状態は章の前提と到達点から与える。
3. 全ての章がそろい、要約、章のまとめ、節のまとめを用意した後に、全ての場面を通しで実行する。

通しの実行には、開始の条件を満たしてから入る。開始の条件はテストそのものではなく、動かすための前提である。

## 要約、章のまとめ、節のまとめ

### 使う文

全体を通す前に用意する。要約は設計セッションが用意し、章のまとめと節のまとめはビルドが組み立てる。この工程で新しい文を書かない。設計の時期に承認済みの文を使う。

| スライド | 使う文 |
|---|---|
| 要約 | 主張の骨子の要約の文(`summary`)。工程2でユーザーが承認している。そのまま使う |
| 章のまとめ、節のまとめ | 工程3と4でユーザーが承認している、章、節、スライドの要点。並べる文と、置く条件は、[語彙と区分](../vocabulary.md)に定める |

工程7の結果、承認済みの文が本編と合わなくなっている場合は、ここで書き直さない。その文を決めた工程(工程2、3、4のいずれか)に戻し、ユーザーの承認を取り直す。

### 要約を用意する

担当: 設計セッション。

要約は、結論と理由を1つの文にまとめたものとする。結論の下に根拠を箇条書きで並べる形は、主張を並べ直しただけで、要約にならない。

```yaml
- id: summary
  kind: summary
  text: 〇〇事業は、伸びている△△領域に絞れば、当社の継続率の高さを生かして2年で黒字に戻せる見込みである
  from: summary
  ask: 来月の経営会議で、△△領域への集中を決定いただきたい   # 結びの章の要点。載せるかどうかは表現規約で決める
  ask_from: ch7
```

要約に根拠を短く添えるかどうかは、[工程6](06-patterns.md)の資料に共通の規則で決める。添える場合は、主張の骨子の主張を短くして並べ、元にした主張を記録する。元の主張より強い言い方にしない。

### 章のまとめと節のまとめを組み立てる

担当: 機械。

ビルドが、承認済みの要点を並べて、章のまとめと節のまとめを組み立てる。

## 実行の方法

### 渡すもの

担当: PM。

読み手の役のセッションに、ブリーフの読み手の情報(立場、既に知っていること、懸念)だけを渡す。設計の成果物は渡さない。例外として、前の章が未完成の場合と、途中の章から再実行する場合は、その章の入口の状態を渡す。「題と要点だけ」の場面では、機械が抜き出した、題と要点の一覧を渡す。場面の指定は、テストの場面から期待する結果を除いた写しで渡す。

### 題と要点の一覧の抜き出し

担当: 機械。

「題と要点だけ」の場面のために、章構成とストーリーラインから、題と要点の一覧を抜き出す。

### 通読

担当: 読み手の役のセッション。

読むのは、ビルドした実物である。スライド仕様ではなく、読み手が実際に目にするものを、順に読む。スライドの画像を読むか、実物から抜き出した文字を読むかは、試作で決める。口頭の資料の「発表の通し」の場面では、ノートも読む。

セッションは、次の状態を持ち越す。

- ここまでに定義された語
- ここまでに示された事実と、納得した主張
- まだ答えられていない疑問
- まだ果たされていない約束(「後で述べる」とされた内容、目次に挙げられた内容)
- 示された枠組み(「3つの観点で評価する」など)と、それが後で使われたか
- 説明に使われた例と、想定の場面
- 冒頭で示された結論

1枚ごとに、次を行う。

1. そのスライドが、状態にないものを前提にしていないかを確かめる。
2. ブリーフの読み手の水準で、そのスライドを理解できたかを記録する。
3. エラーがあれば、種類と、食い違う相手の箇所を添えて記録する。
4. 状態を更新し、記録する。

状態を明示して持ち越すので、章ごとに区切って実行でき、後から途中の章から再実行できる。

### 実行の記録

担当: 読み手の役のセッション。

1つの場面を通すごとに、1つのファイルを `runs/` に置く。ファイル名は「場面の識別子--回.yaml」とする。回は、その場面を実行した回数で、1から数える。

```yaml
# runs/main-reader--1.yaml
scenario: main-reader
commit: 3f2a9c1
round: 1
steps:
  - slide: ch1-s1
    understood: この講義で、アラートを3つに分けて扱いを決める方法を学ぶ
    carried: [アラート, 重大度]          # ここまでに覚えた語
  - slide: ch1-s2
    understood: 根拠があるものだけ閉じ、迷ったら上げる
    stuck: 「持ち時間」が何を指すか分からない
findings:
  - slide: ch1-s2
    kind: undefined-term     # エラーの種類
    note: 「持ち時間」が定義より前に出る
```

- `steps` は、読んだスライドごとに、読んだ順に書く。
- `understood` は、そのスライドから理解した内容である。持ち越す状態のうち、語のほかのもの(事実、主張、疑問、約束、枠組み、例、結論)は、ここに文で書く。
- `carried` は、ここまでに定義された語である。前のスライドから変わらなければ、書かない。
- `stuck` は、理解できなかった点である。なければ書かない。
- `findings` は、エラーである。`kind` は、下の「通読で見つけるもの」の識別子から選ぶ。`note` に、内容と、食い違う相手の箇所を書く。

### 出口の状態の照合

担当: PM。

章の出口の状態が到達点と合うかどうかは、読み手の役のセッションが書いた状態と、章の前提と到達点を、PMが機械的に照合して確かめる。

## エラーの種類

全体を通して初めて分かる悪い品質を、エラーとして定める。フィードバックで新しい種類が見つかれば、既存の種類に入らないことを確かめたうえで足す。

### 通読で見つけるもの

読み手の役のセッションが、状態と照らして見つける。

| 区分 | エラー | 識別子 | 内容 |
|---|---|---|---|
| 前提 | 未定義の語 | `undefined-term` | まだ説明されていない語や略語が出てくる |
| 前提 | 専門的すぎる説明 | `too-technical` | 説明はあるが、ブリーフの読み手の水準では理解できない |
| 前提 | 前提の先取り | `premature-premise` | まだ示されていない事実や主張を、既知のものとして使っている |
| 筋 | 既出との矛盾 | `contradiction` | 前のスライドで述べたことと食い違う |
| 筋 | 飛躍 | `leap` | 前のスライドから、なぜ次の話になるのかが分からない |
| 筋 | 停滞 | `stall` | 読む前と後で、読み手の状態が変わらない。理解が深まらない |
| 筋 | 繰り返し | `repetition` | 既に述べたことを、初めてのように述べ直している。1枚の中で、要点と同じことを別の場所でもう一度述べている |
| 筋 | 枠組みの放棄 | `abandoned-framework` | 冒頭で示した観点や分類が、後で使われない。または、別の観点に入れ替わる |
| 筋 | 結論のぶれ | `conclusion-drift` | 冒頭の結論、結びの結論、要約の結論が食い違う。要約が本編より強いことを述べている |
| 筋 | 語の意味のずれ | `meaning-shift` | 同じ語が、場所によって違う意味で使われる |
| 筋 | 抽象度の急変 | `abstraction-jump` | 方針の話から、橋渡しなしに細部の話に移る。またはその逆 |
| 筋 | 例の不統一 | `example-switch` | 説明に使う例や想定の場面が、断りなく入れ替わる |
| 回収 | 約束の未回収 | `unkept-promise` | 「後で述べる」とした内容や、目次に挙げた内容が出てこない |
| 回収 | 問いの置き去り | `unanswered-question` | 途中で読み手に抱かせた疑問に、最後まで答えていない |
| 回収 | 依頼の曖昧 | `unclear-ask` | 読み終えても、何を求められているかが分からない |
| 負担 | 水準の揺れ | `level-swing` | あるスライドは初歩から説明し、別のスライドは専門知識を前提にする |
| 負担 | 現在地の喪失 | `lost-position` | 今どの章のどの話なのかが分からなくなる |
| 作法 | 作法の変化 | `convention-change` | 章が変わると、文体、図の描き方、数値の書き方、色の使い方が変わる |
| 到達点 | 到達点との不一致 | `exit-mismatch` | 章の出口の状態が、定めた到達点と違う |
| 形 | 形と中身の不一致 | `form-content-mismatch` | スライドの形から読み取れる関係(まとまり、対比、順序など)が、中身にない。基準の分からないグルーピングを含む |
| 形 | 要点と図の不一致 | `point-figure-mismatch` | 図や表が、要点の述べていることを示していない |
| 形 | 注目する箇所の不明 | `unclear-focus` | 図や表のどこを見ればよいかが分からない |
| 文 | 意味の取れない文 | `unreadable-sentence` | 主語がない、語の関係が分からないなどで、文の意味が取れない |
| 文 | くどい文 | `wordy-sentence` | 同じことを言い換えて繰り返す。読み飛ばしても意味が変わらない語が多い |
| 語 | 同じものを指す別の語 | `synonym` | 違う語が、同じ対象を指しているように読める |

### 集計で見つけるもの

実行の記録と、スライド仕様から、機械的に集計する。目安を超えたものをエラーの候補とする。目安の値は、資料の表現規約に置く。

| 区分 | エラー | 集計するもの |
|---|---|---|
| 負担 | 新出の集中 | スライドごと、および連続する数枚での、新しい語と概念の数。実行の記録の状態の変化から数える |
| 負担 | 緩急のなさ | スライドごとの字数と要素の数の並び。重いスライドの連続、全体が同じ密度であること |
| 負担 | 単調 | 同じ型が連続する枚数 |
| 筋 | 尻すぼみ | 章ごとの、スライドあたりの字数と事実の数。後半の章だけ薄くなっていないか |
| 筋 | 配分の偏り | ブリーフの読み手の懸念ごとの、答えているスライドの枚数。懸念に対応しない章の枚数 |
| 信頼 | 数値の基準の不一致 | 同じ指標を表す事実どうしで、時点、範囲、単位が違うもの。素材台帳の `qualifiers` と `unit` を比べる |
| 信頼 | 言い回しの反復 | 資料全体での、同じ言い回しと同じ文型の出現回数 |
| 信頼 | 人称と語調の揺れ | 書き手を指す語(当社、弊社、我々など)と、文末の形の混在 |
| 信頼 | 残骸 | 存在しないスライドや事実への言及。語彙表にない固有の名称。読み手に見せる文に残った内部のID |

言い回しの反復は、1枚ずつでは問題のない文でも、資料全体で並ぶと目立つ。スライドごとの検査では見つからない。

## 不具合の記録と裁定

### 不具合の記録

担当: PM。

読み手の役のセッションは、読んで指摘を書く。Issueにするのは、PMである。PMは、重大度と、混入した工程を決めない。

エラーは、1件ずつIssueにする。項目は次の通り。

- 場面と、発生したスライド
- エラーの種類
- 期待した結果と、実際の結果。食い違う相手の箇所があれば、両方を引用する
- 重大度(裁定で決める)
- 混入した工程(裁定で決める)

### 裁定

担当: 設計セッション。

読み手の役のセッションの指摘と、集計で挙がった候補は、どちらも候補として扱う。設計セッションが、引用された箇所を見比べて、実際にエラーかどうかを裁く。エラーと認めたものについて、重大度と、混入した工程を決め、その工程に戻す。戻し先と、無効になる範囲は、[不合格と修正の手順](../rework.md)の表による。

| 重大度 | 基準 |
|---|---|
| 高 | 読み手が結論にたどり着けない、または誤った理解をする。資料の信頼を損なう(事実の食い違い、同じ対象の名前や色の不一致、資料全体に及ぶ言い回しの反復、残骸) |
| 中 | 読み手が止まるが、読み進めれば分かる |
| 低 | 気になるが、理解も信頼も損なわない |

修正は1件ずつ行わず、章ごとにまとめて1回で行う。複数の章にまたがる修正の扱いは、[不合格と修正の手順](../rework.md)による。PMや、テストしたセッションは、スライドを直さない。

往復の回数が上限を超えた場合の扱いは、[不合格と修正の手順](../rework.md)による。往復は、資料全体について数える。

### 退けた指摘の確認

担当: ユーザー。

原因が設計の成果物(工程0から6の成果物、要約、章のまとめ、節のまとめ)にあると見られる指摘を、設計セッションがエラーでないと裁く場合は、ユーザーが確かめる。自分の成果物への指摘を、自分だけで退けないためである。

## 回帰テスト

### 再実行

担当: PM。

直した後は、変わった章の入口の状態を保存済みの状態から復元し、その章から先を、全ての場面で再び通す。変わっていない前の章は、読み直さない。集計で見つけるエラーは、集計をやり直す。

引き渡した後に資料を改訂する場合も、同じ方法をとる。変えた箇所から先を通し、過去の指摘の場面を実行する。

### 再実行の指摘の扱い

担当: PM。

再実行で挙がった指摘のうち、変えていないスライドについてのものを、機械的に照合して挙げる。挙げた指摘は、差し戻さずに候補として記録する。読み手の役のセッションは毎回新しく起こすため、判定がぶれる。変えていない箇所への指摘で、往復を増やさないためである。

### 再実行の指摘の裁定

担当: 設計セッション。

候補を、前回の実行の記録と比べる。前回は出なかった指摘が新しく出たものを、まとめて裁く。

### 過去の指摘の場面

担当: 設計セッション。

ユーザーから受けた指摘は、直すだけでなく、「過去の指摘」の場面に加える。次に資料を直したときに、同じ問題が戻っていないかを確かめられる。

## 網羅の確認

担当: 機械。

次のつなぎ目の全てが、いずれかの場面の実行で通ったことを、実行の記録から機械的に確かめる。

- 全ての章の境目
- 全ての語の初出
- 他のスライドへの全ての言及
- ブリーフの読み手の全ての懸念
- 主張の骨子の全ての主張と反論

あわせて、上流から下流までの対応(問い、答え、主張、章、スライド、事実)を表にし、対応のない項目がないことを確かめる。

## この工程でやらないこと

- 工程7で済んだスライドごとの検査(裏付けのない文、限定の残存、削る検査、文体)を、全スライドでやり直さない。

- 事実、スライド、型を足さない。足りなければ上流に戻す。
- 通すために、期待する結果や終了の条件を緩めない。
