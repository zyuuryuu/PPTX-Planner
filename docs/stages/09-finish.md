# 工程9 仕上げ(受け入れテスト)

[目次に戻る](../README.md)

状態: 方向はユーザーと合意した。試作で確かめる点を末尾に挙げる。

出来上がった資料が、ブリーフの目的を果たすかを、ユーザーが判断する。ソフトウェア開発の受け入れテストの方法を当てはめる。工程8の結合テストは、読み手の役のセッションが通して、止まる箇所を見つけた。この工程では、ユーザー自身が、実際に使う形で通す。

## 対応

| ソフトウェアの受け入れテスト | スライドでの対応 |
|---|---|
| 要件に照らして確かめる | ブリーフの項目の1つ1つに照らして確かめる |
| 受け入れの基準を、先に決めておく | 工程0で、ブリーフとあわせて受け入れの問いを決める |
| 利用者が、実際の使い方で試す | ユーザーが、口頭の資料なら話してみる。配布する資料なら読み手として読む |
| 本番と同じ環境で確かめる | 実際に映す機器、配る形式、印刷で確かめる |
| 既知の問題の一覧を付けて引き渡す | 残った問題と受け入れたエラーを、検査の報告にまとめる |
| 引き渡し後の利用の結果を集める | 発表の後に得た反応を記録する |

## 成果物

- `build/deck.pptx`
- 検査の報告 `09-report.md`
- 承認の記録(Gitのタグ)
- 集計の記録

## 作り方

### 1. 最終のビルドを行い、出力を機械的に検査する

描画上の診断は、工程7の章の受け入れで通っている。ここでは最終のビルドで再実行し、最終の出力でしか確かめられないことを加えて確かめる。

### 2. 検査の報告を作る

機械が、次を1ページにまとめる。ユーザーが通す前に読み、どこに気を付けて見るかを知るためのものである。

受け入れの問いと、その材料:

| ブリーフの項目 | 受け入れの問い | 材料 |
|---|---|---|
| 目的 | 読み終えた読み手は、求めた判断や行動に進めるか | 結合テストの主な読み手の通読で、最後に読み手の役が述べた、求められている行動 |
| 答えるべき問い | 資料の結論は、問いへの答えになっているか | 同じ通読で、読み手の役が述べた結論 |
| 読み手の懸念 | 懸念の1つ1つに、答えがあるか | 懸念ごとの、答えているスライドと、反対の立場の通読の結果 |
| 扱わない範囲 | 範囲の外の内容が入っていないか | ブリーフの「扱わない範囲」と、スライドの見出しの一覧 |
| 制約 | 枚数、時間、テンプレート、期限を守っているか | 枚数、発表時間の見積もり |

判断が要る箇所:

| 載せるもの | 理由 |
|---|---|
| 結合テストで受け入れたエラーと、重大度が低のエラー | 問題が残っている |
| 骨組みの承認の後に、見出しや順序が変わった箇所 | 承認済みのものが変わっている |
| 証言だけに頼る主張、見解が割れている主張 | 根拠が弱い |
| 図の中で不明のまま残した箇所、位置を推定した注釈 | 正確さが確かめきれていない |
| 収容量を超えた型を使ったスライド、表現規約の例外 | 規則から外れている |
| 閉じていないIssue | 対応が済んでいない |

### 3. 抜き取りで確かめる

無作為に選んだスライドについて、ユーザーが、中身と、出典の引用箇所を見比べる。検査の報告は、危ないと分かっている箇所しか示せない。誰も気づいていない誤りがどの程度残っているかを知るために行う。結果は集計の記録に残す。

### 4. ユーザーが、実際に使う形で通す

| 伝え方 | 通し方 |
|---|---|
| 口頭で説明する | ノートを見ながら、最初から最後まで話してみる。時間を測る |
| 配布して読ませる | 読み手として、最初から最後まで読む |

通すのは1回とする。機械的な検査と結合テストを済ませているので、欠陥を探すためではなく、受け入れの問いに答えるために通す。

通しながら気づいた点は、その場で直させない。メモとして集め、通し終えた後に、[フィードバックと修正](../feedback.md)の手順でまとめて扱う。

### 5. 実際の環境で確かめる

機械では確かめきれず、ユーザーの環境でしか分からないことを、一覧にして渡す。

- 発表に使うPowerPointの版と機器で開き、フォントの置き換わりや配置のずれがないか。
- 映したときに、後ろの席から文字が読めるか。
- 配布する形式(PDFなど)に変換したときに、崩れないか。
- 白黒で印刷したときに、色で区別していた内容が読み取れるか。

該当しない項目は、該当しないと記録する。

### 6. ユーザーが承認する

受け入れの問いの1つ1つに、ユーザーが答える。あわせて、残っている問題を承知のうえで出せるかを答える。

通した結果、直す必要がある場合は、反映先の範囲に従って該当する工程に戻す。直した後は、工程8の回帰テストを行ってから、この工程に戻る。

### 7. 引き渡す

- 承認した時点の版に、Gitのタグを付ける。
- 以後のPowerPointでの手直しは自由とする。作り直すと手直しが消えることを伝える。

### 8. 発表の後に、反応を記録する

資料の結果は、読み手に見せた後にしか分からない。発表や配布の後に、次をフィードバックとして記録する。

- 質問されたこと。
- 伝わらなかった箇所。
- 読み手が実際にとった判断や行動。

質問されたことは、次の資料の反対の立場の通読と、想定問答の材料にする。伝わらなかった箇所は、テストの場面と表現規約に反映する。

### 9. 集計する

次の資料のための材料として、次を集計する。合格条件にはしない。

- 守らせる方法ごとの、検査で見つかった違反の数。
- 結合テストのエラーの数。種類、重大度、混入した工程ごとに数える。
- 全ての検査を通った後に、ユーザーの通しと抜き取りで見つかった問題の数。
- 語の登録の申請の数、検査と執筆の往復の回数。

表現規約、型の定義、資料の型の定義への書き戻しは、引き渡しの後に、規則の追加と整理の手順([表現規約](../style-rules.md))で行う。

## 合格条件

出力:

- 描画上の診断(文字のあふれ、要素の重なり、描かれなかった内容、文字の大きさの下限、禁則と不自然な改行)が0件である(機械)。
- スライドの枚数と見出しが、ストーリーライン、および導出したスライドと一致する(機械)。
- 目次、ページ番号、他のスライドへの言及が、全て解決している(機械)。
- 出力から抜き出した文字の中の数値が、全て素材台帳の値と一致する(機械)。
- 出典の一覧が、使った事実を全て含む(機械)。
- 置き換えられずに残った事実のIDがない(機械)。
- 配布する資料のノートが空である。口頭の資料のノートに、内部向けの記述(Issueの番号、作業の覚え書き)がない(機械)。
- ファイルの作成者などの付帯情報が、表現規約の定めの通りである(機械)。

警告(合否にしない):

- 口頭の資料で、ノートの字数から見積もった発表時間が、ブリーフの制約を超える。

受け入れ:

- 検査の報告に、作り方の2の表の全ての項目が載っている(機械)。
- 抜き取りを行い、結果を記録している(ユーザー)。
- ユーザーが、実際に使う形で1回通している(ユーザー)。
- 実際の環境で確かめる項目の全てに、結果か、該当しないの記録がある(ユーザー)。
- 受け入れの問いの全てに、ユーザーが答えている(ユーザー)。
- 残っている問題を承知のうえで出せると、ユーザーが答えている(ユーザー)。

## この工程でやらないこと

- 調査の追加、スライドの追加、見出しの変更をしない。必要なら上流に戻すか、次の版に回す。
- ユーザーに、誤字や数値の全数の確認を求めない。機械で確かめる。抜き取りは、残る誤りの程度を知るために行う。
- ユーザーに、1枚ごとの承認を求めない。
- 警告を0件にするために直さない。
- 人がPowerPointで直した内容を、仕様に同期しない。

## 未決の点

- 抜き取りの枚数。誤りが見つかったときに、どこまで検査をやり直すか。
- 発表時間の見積もりに使う、話す速さの値。
- 発表の後の反応を、誰がどの形で記録するか。ユーザーが口頭で伝え、設計セッションが記録する形が候補である。
