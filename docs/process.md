# スライド作成工程の定義(草案 v0.1)

状態: 草案。ユーザーのレビュー前で、合意済みの内容ではない。
未検証の前提は「未検証の前提」の節にまとめた。

## 目的

LLMによるスライド作成は、枚数が増えると次の問題を起こす。

- 文章が崩れ、スライド間の一貫性が失われる。
- 主張のないスライドが増える。
- 修正のたびにPPTXの座標や書式を読み込み、消費するトークンが膨らむ。

この定義は、スライド作成を工程に分け、工程ごとに成果物と合格条件を定めることで、これらを防ぐ。

## 役割の分担

| 担当 | 範囲 |
|---|---|
| PPTX-Planner | 何を、どの順で、どの型で伝えるかの設計と検査 |
| SlideCraft | Markdownからのレイアウト、あふれの分割、PPTXの生成、描画上の診断 |

PlannerはSlideCraft向けのMarkdownを出力する。座標と書式はSlideCraftとテンプレートだけが持つ。

## 原則

1. **正本は仕様で、PPTXは生成物である。** 修正は仕様に対して行い、PPTXは作り直す。LLMはPPTXの中身を読まない。
2. **各工程は、承認済みの上流の成果物だけを読む。** 会話の履歴や生の資料に頼らない。これで工程ごとの読み込み量が一定に保たれる。
3. **収集、執筆、検査は別のセッションで行う。** 詳細は「セッションの分離」の節。
4. **執筆は素材台帳にある事実だけを使う。** 台帳にない事実が必要になったら、書かずに調査依頼を出す。
5. **合格条件を満たせないときは上流に戻る。** 合格条件のほうを書き換えて通すことはしない。
6. **機械で検査できるものは機械で検査する。** LLMの判断による検査は、執筆と別のセッションで行う。

## 工程の一覧

| # | 工程 | 成果物 | 合格条件 | 承認 |
|---|---|---|---|---|
| 0 | 依頼の確定 | ブリーフ | 聴衆、目的、答えるべき問い、制約が埋まっている | ユーザー |
| 1 | 探索 | 素材台帳、仮説メモ | 全ての事実に出典と引用箇所がある | 検査セッション |
| 2 | 主張の整理 | 主張の骨子 | 各主張に台帳の事実が紐づく | ユーザー |
| 3 | 章立て設計 | 章構成 | 章の主張だけを読んで結論が導ける | ユーザー |
| 4 | ストーリーライン | スライド見出しの一覧 | 見出しだけを読んで章の主張が導ける | ユーザー |
| 5 | 表現設計 | 表現の対応表 | 全ての型がテンプレートで実現できる | ユーザー |
| 6 | スライド仕様 | 章ごとのスライド仕様 | 対応表、用語集、素材台帳と整合する | 機械と検査セッション |
| 7 | ビルド | Markdown、PPTX | SlideCraftの診断が0件 | 機械 |
| 8 | レビュー | レビュー記録 | ブリーフの問いに答えている | ユーザー |

工程1と2は往復する。工程2で裏付けのない主張が見つかれば、工程1に戻って調べるか、その主張を捨てる。

## 各工程の定義

### 0. 依頼の確定

資料が答える問いを固定する。問いが決まらないと、探索の範囲が決まらない。

成果物 `00-brief.md` の項目:

- 聴衆(誰が読むか、何を既に知っているか)
- 目的(読んだ人に何を決めて、あるいは何をしてほしいか)
- 答えるべき問い(1文)
- 制約(枚数の目安、発表時間、テンプレート、言語、期限)
- 手元の資料の一覧

この段階では結論を書かない。結論は工程2で決まる。

### 1. 探索

問いに答えるための事実を集める。現時点では最小限の定義にとどめ、収集の手段(Web検索、資料の読み込み、ユーザーへの聞き取り)は既存の道具に任せる。

成果物 `01-sources.yaml`(素材台帳)の1件:

```yaml
- id: F012
  statement: 2025年の国内市場規模は1.2兆円
  kind: fact            # fact(事実) / inference(推測) / opinion(意見)
  source: 〇〇白書 2025年版
  locator: p.34 図表2-1  # ページ、URL、節など
  quote: "国内市場は1兆2,000億円に達した"
  verified: true        # 検査セッションが引用箇所を確認したか
```

成果物 `01-hypotheses.md`(仮説メモ)は作業用で、承認の対象にしない。後の工程はこれを読まない。

調査は執筆セッションから直接行わず、調査依頼として子セッションに渡す。調査依頼の項目:

- 知りたいこと(1文の問い)
- 使い道(どの主張を確かめるためか)
- 返す形式(素材台帳の書式)
- 見つからなかった場合は「見つからない」と返すこと

合格条件:

- 全ての `fact` に `source`、`locator`、`quote` がある。
- 検査セッションが、`quote` が出典に実在することを確認している。確認できないものは `verified: false` のまま残し、後の工程で使わない。

### 2. 主張の整理

集めた事実から、問いへの答えを組み立てる。

成果物 `02-claims.yaml`(主張の骨子):

```yaml
answer: 〇〇事業は、△△に絞って継続すべきである
claims:
  - id: C1
    statement: 市場全体は縮小するが、△△の領域だけは伸びている
    evidence: [F012, F015, F021]
  - id: C2
    statement: ...
    evidence: [F030]
```

合格条件:

- `answer` がブリーフの問いに答えている。
- 支える主張は3〜5個である。
- 全ての主張に、`verified: true` の事実が1件以上紐づく(機械で検査)。

### 3. 章立て設計

主張の骨子を章に割り当てる。章は話題の区分ではなく、主張の区分とする。

成果物 `03-chapters.yaml`:

```yaml
- id: ch1
  title: 市場の現状
  message: 市場全体は縮小するが、△△の領域だけは伸びている
  claims: [C1]
  slides: 6        # 枚数の目安
```

合格条件:

- 全ての主張がいずれかの章に割り当てられている(機械で検査)。
- 章の `message` を順に読むと `answer` が導ける(検査セッションとユーザー)。
- 枚数の合計がブリーフの制約に収まる(機械で検査)。

### 4. ストーリーライン

章ごとに、スライドの見出しを決める。見出しは体言止めの題名ではなく、主張を述べる文とする。

成果物 `04-storyline.yaml`:

```yaml
- id: ch1-s2
  chapter: ch1
  headline: △△の領域は過去5年、年率8%で伸びている
  relation: trend     # 主張の種類。工程5の対応表の鍵になる
  evidence: [F015]
```

`relation` の値は工程5で確定する。この工程では仮の値を置く。

合格条件:

- 1スライドに見出しは1つである。
- 章内の見出しを順に読むと、章の `message` が導ける(検査セッションとユーザー)。
- 全てのスライドに `evidence` がある。章扉など事実を要しないスライドは種別で区別する(機械で検査)。

### 5. 表現設計

主張の種類と表現の型の対応を、資料ごとに1つ定める。同じ種類の主張には同じ型を、違う種類の主張には違う型を使う。

成果物 `05-patterns.yaml`(表現の対応表):

```yaml
- relation: trend          # 時系列の変化
  pattern: xychart-line    # SlideCraftの図の種類、または区切りの記法
  layout: null             # 固定するレイアウト名。自動選択に任せる場合はnull
- relation: comparison-2   # 2案の対比
  pattern: compare
- relation: process        # 手順
  pattern: step
```

合格条件:

- ストーリーラインに現れる全ての `relation` が対応表にある(機械で検査)。
- 1つの `pattern` が複数の `relation` に使われていない(機械で検査)。
- 全ての `pattern` が、使用するテンプレートとSlideCraftで実現できる。実現できない型は、代わりの型を選ぶか、SlideCraftへの要望として記録する。

### 6. スライド仕様

スライドごとに、載せる内容を確定する。章ごとに1ファイルに分け、1章の執筆では他の章の仕様を読まない。

成果物 `06-slides/ch1.yaml`:

```yaml
- id: ch1-s2
  headline: △△の領域は過去5年、年率8%で伸びている
  relation: trend
  takeaway: 成長は一時的な要因ではなく、5年続いている
  body:
    type: xychart
    data: {...}
  sources: [F015]
  notes: 口頭で補う説明
```

合格条件:

- `headline` と `relation` がストーリーラインと一致する(機械で検査)。
- `body.type` が対応表の `pattern` と一致する(機械で検査)。
- `sources` が全て素材台帳にあり、`verified: true` である(機械で検査)。
- 数値が素材台帳の `statement` や `quote` と一致する(検査セッション)。
- 用語集の禁止表記が含まれない(機械で検査)。

### 7. ビルド

スライド仕様をSlideCraftのMarkdownに変換し、PPTXを生成する。変換は決まった規則で行い、この工程で内容を書き足さない。

成果物は `build/deck.md` と `build/deck.pptx`。

合格条件:

- SlideCraftの診断(`get_deck_issues`)が0件である。
- あふれの自動分割でスライドが増えた場合は、工程6に戻って内容を削るか、工程4に戻ってスライドを分ける。分割の結果をそのまま受け入れない。分割されたスライドは見出しが同じになり、1スライド1メッセージが崩れるためである。

### 8. レビュー

全スライドの画像を一覧で見て、ブリーフに照らして確認する。

成果物は `reviews/` 配下のレビュー記録。指摘は、どの工程の成果物を直すかを添えて記録する。

## 横断の成果物

### 用語集 `glossary.yaml`

```yaml
- term: 顧客
  forbid: [お客様, クライアント, ユーザー]
  note: 契約主体を指す。利用者個人は「利用者」とする
```

工程0から書き始め、工程6以降で機械的に検査する。

### 素材台帳 `01-sources.yaml`

工程1で作り、全工程を通じて唯一の事実の置き場とする。SlideCraftの `Source:` 行は、台帳の `source` から生成する。

## セッションの分離

| セッション | 読むもの | してはいけないこと |
|---|---|---|
| 収集 | 調査依頼、外部の資料 | 主張や見出しを書くこと |
| 執筆 | 承認済みの上流の成果物 | Web検索や資料の直接の読み込み、台帳にない事実の記述 |
| 検査 | 検査対象の成果物と、その上流の成果物 | 検査対象を自分で直すこと |

分ける理由:

- 執筆中のLLMは、文を完成させるために必要な事実を補ってしまう。事実を台帳のIDでしか参照できなくすれば、補う余地がなくなる。
- 生の資料が執筆の文脈に入らないため、読み込み量が抑えられる。
- 書いた本人による検査は、自分の誤りを見逃しやすい。

分離だけでは、収集セッション自身の捏造は防げない。そのため素材台帳に引用箇所を記録させ、検査セッションが出典と突き合わせる。

## 修正の流れ

修正は、その内容が属する工程の成果物に対して行い、下流を作り直す。

| 修正の内容 | 直す成果物 | 作り直す範囲 |
|---|---|---|
| 言い回し、数値の誤記 | スライド仕様 | 該当スライドのビルド |
| スライドの追加、順序の変更 | ストーリーライン | 該当章の仕様以降 |
| 図の型の変更 | 表現の対応表 | その型を使う全スライド |
| 章の入れ替え | 章構成 | 該当章以降 |
| 結論の変更 | 主張の骨子 | 章構成以降の全て |

## 未検証の前提

- 表現の型をSlideCraftのレイアウト固定の記法で制御できるか。SlideCraftは内容の形からレイアウトを自動で選ぶため、同じ `relation` のスライドが別のレイアウトになる可能性がある。
- SlideCraftの図の種類(12種とMermaid経由の4種)と区切りの記法で、ビジネス文書に必要な型が足りるか。
- 成果物の書式(YAML)が、LLMにとって書きやすく、人にとって読みやすいか。
- この工程が何枚以上の資料で引き合うか。数枚の資料には重すぎる見込みである。

これらは試作の資料を1本通して確かめる。
