# スライド作成工程の定義(草案 v0.3)

状態: 草案。方向はユーザーと合意したが、細部と書式は未確定である。
実物で確かめていない前提は「未検証の前提」の節にまとめた。

## 目的

LLMによるスライド作成は、枚数が増えると次の問題を起こす。

- 文章が崩れ、スライド間の一貫性が失われる。
- 主張のないスライドが増える。
- 修正のたびにPPTXの座標や書式を読み込み、消費するトークンが膨らむ。

この定義は、スライド作成を工程に分け、工程ごとに成果物と合格条件を定めることで、これらを防ぐ。

## 役割の分担

| 担当 | 範囲 |
|---|---|
| PPTX-Planner | 何を、どの順で、どの型で伝えるかの設計と検査 |
| 描画の実装 | スライド仕様からのレイアウトとPPTXの生成、描画上の診断 |

Plannerは特定の描画の実装に依存しない。上流の成果物は、描画の実装の名前や記法を含まない。描画の実装は差し替えられる部品とし、満たすべき条件を「描画の実装の条件」の節に定める。候補は、SlideCraftと、LLMが書くPythonのコード(python-pptxなど)である。

座標と書式は描画の実装だけが持つ。

## 原則

1. **正本は仕様で、PPTXは生成物である。** 修正は仕様に対して行い、PPTXは作り直す。LLMはPPTXの中身を読まない。
2. **全体で設計し、章ごとに書き、全体で検査する。** 1枚あたり数行で済む成果物は、資料全体を1つのセッションで扱う。分量の多いスライド仕様だけを章に分ける。
3. **各工程は、承認済みの上流の成果物だけを読む。** 会話の履歴や生の資料に頼らない。
4. **収集、執筆、検査は別のセッションで行う。** 詳細は「セッションの分離」の節。
5. **執筆は素材台帳にある事実だけを使う。** 台帳にない事実が必要になったら、書かずに調査依頼を出す。
6. **人はスライドの形で確認する。** ストーリーライン以降は、未完成でもビルドして見られるようにする。
7. **合格条件を満たせないときは上流に戻る。** 合格条件のほうを書き換えて通すことはしない。
8. **機械で検査できるものは機械で検査する。** LLMの判断による検査は、執筆と別のセッションで行う。

## 工程の一覧

| # | 工程 | 範囲 | 成果物 | 承認 |
|---|---|---|---|---|
| 0 | 依頼の確定 | 全体 | ブリーフ | ユーザー |
| 1 | 探索 | 全体 | 素材台帳、仮説メモ | 検査セッション |
| 2 | 主張の整理 | 全体 | 主張の骨子 | ユーザー |
| 3 | 章立て設計 | 全体 | 章構成 | ユーザー |
| 4 | ストーリーライン | 全体 | スライド見出しの一覧 | ユーザー(骨組みの資料を見て) |
| 5 | 立証設計 | 全体 | スライドごとの立証の設計 | 検査セッションとユーザー(仮置きの資料を見て) |
| 6 | 表現設計 | 全体 | 表現の対応表 | ユーザー |
| 7 | スライド仕様 | 章ごと | 章ごとのスライド仕様 | 機械と検査セッション |
| 8 | 全体検査 | 全体 | 要約版、検査の結果 | 機械と検査セッション |
| 9 | 仕上げ | 全体 | PPTX、レビュー記録 | ユーザー |

工程1と2は往復する。工程2で裏付けのない主張が見つかれば、工程1に戻って調べるか、その主張を捨てる。

## 各工程の定義

### 0. 依頼の確定

資料が答える問いを固定する。問いが決まらないと、探索の範囲が決まらない。

成果物 `00-brief.md` の項目:

- 聴衆(誰が読むか、何を既に知っているか)
- 目的(読んだ人に何を決めて、あるいは何をしてほしいか)
- 答えるべき問い(1文)
- 資料の種類(「資料の種類」の節の2つの軸)
- 制約(枚数の目安、発表時間、テンプレート、言語、期限)
- 手元の資料の一覧

この段階では結論を書かない。結論は工程2で決まる。

### 1. 探索

問いに答えるための事実を集める。現時点では最小限の定義にとどめ、収集の手段(Web検索、資料の読み込み、ユーザーへの聞き取り)は既存の道具に任せる。

成果物 `01-sources.yaml`(素材台帳)の1件:

```yaml
- id: F012
  statement: 2025年の国内市場規模は1.2兆円
  value: 1.2            # 本文から参照する数値。数値でない事実では省く
  unit: 兆円
  kind: fact            # fact(事実) / inference(推測) / opinion(意見) / derived(計算値)
  source: 〇〇白書 2025年版
  locator: p.34 図表2-1  # ページ、URL、節など
  quote: "国内市場は1兆2,000億円に達した"
  verified: true        # 検査セッションが引用箇所を確認したか
```

合計や比率などの計算値も、台帳に登録する。

```yaml
- id: F040
  statement: △△領域は国内市場の25%を占める
  value: 25
  unit: "%"
  kind: derived
  formula: F013 / F012   # 元になる事実と計算式
```

成果物 `01-hypotheses.md`(仮説メモ)は作業用で、承認の対象にしない。後の工程はこれを読まない。

調査は執筆セッションから直接行わず、調査依頼として子セッションに渡す。調査依頼の項目:

- 知りたいこと(1文の問い)
- 使い道(どの主張を確かめるためか)
- 返す形式(素材台帳の書式)
- 見つからなかった場合は「見つからない」と返すこと

合格条件:

- 全ての `fact` に `source`、`locator`、`quote` がある(機械)。
- 全ての `derived` の計算式が、元の事実の値から再計算して一致する(機械)。
- 検査セッションが、`quote` が出典に実在することを確認している。確認できないものは `verified: false` のまま残し、後の工程で使わない。

### 2. 主張の整理

集めた事実から、問いへの答えを組み立てる。

成果物 `02-claims.yaml`(主張の骨子):

```yaml
answer: 〇〇事業は、△△に絞って継続すべきである
claims:
  - id: C1
    statement: 市場全体は縮小するが、△△の領域だけは伸びている
    evidence: [F012, F015, F021]
  - id: C2
    statement: ...
    evidence: [F030]
```

合格条件:

- `answer` がブリーフの問いに答えている(ユーザー)。
- 支える主張は3〜5個である(機械)。
- 全ての主張に、`verified: true` の事実が1件以上紐づく(機械)。

### 3. 章立て設計

主張の骨子を章に割り当てる。章は話題の区分ではなく、主張の区分とする。

成果物 `03-chapters.yaml`:

```yaml
- id: ch1
  title: 市場の現状
  message: 市場全体は縮小するが、△△の領域だけは伸びている
  claims: [C1]
  slides: 6        # 枚数の目安
```

合格条件:

- 全ての主張がいずれかの章に割り当てられている(機械)。
- 章の `message` を順に読むと `answer` が導ける(検査セッションとユーザー)。
- 枚数の合計がブリーフの制約に収まる(機械)。

### 4. ストーリーライン

全ての章のスライドの見出しを、1つのセッションで決める。見出しは体言止めの題名ではなく、主張を述べる文とする。全体を一度に扱うことで、章をまたぐ主張の重複と矛盾をこの段階で防ぐ。

成果物 `04-storyline.yaml`:

```yaml
- id: ch1-s2
  chapter: ch1
  headline: △△の領域は過去5年、年率8%で伸びている
  evidence: [F015]
```

この時点で骨組みの資料をビルドする。各スライドには見出しと、根拠の事実の要約だけが載る。ユーザーはこの資料を見て承認する。

合格条件:

- 1スライドに見出しは1つである(機械)。
- 全てのスライドに `evidence` がある(機械)。
- 章内の見出しを順に読むと、章の `message` が導ける(検査セッションとユーザー)。
- 同じ主張を述べる見出しが複数ない(検査セッション)。

### 5. 立証設計

スライドごとに、見出しを読み手に納得させるために何を見せるかを決める。中身を書く前に行う。全体を1つのセッションで扱う。

成果物 `05-proof.yaml`:

```yaml
- id: ch1-s2
  relation: trend                 # 主張の種類
  show: 全体と△△領域の売上を5年分並べる   # 見せるもの
  focus: 2023年以降の差の広がり          # 注目させる点
  facts: [F015, F016]             # 使う事実
```

`facts` が足りなければ、調査依頼を出して工程1に戻る。

この時点で仮置きの資料をビルドする。各スライドには見出しと、図の型の仮置き(「ここに5年分の推移」など)が載る。

合格条件:

- `relation` が「主張の種類の語彙」にある(機械)。
- `facts` が全て素材台帳にあり、`verified: true` である(機械)。
- 見出しの復元: 検査セッションに見出しを隠して `show`、`focus`、`facts` だけを見せ、見出しを書かせる。元の見出しと意味が一致する(検査セッション)。

### 6. 表現設計

全スライドの立証設計を集計し、主張の種類と表現の型の対応を、資料ごとに1つ定める。同じ種類の主張には同じ型を、違う種類の主張には違う型を使う。

成果物 `06-patterns.yaml`(表現の対応表):

```yaml
- relation: trend          # 推移
  pattern: line-chart      # Plannerが定める型の名前。描画の実装の記法ではない
- relation: contrast       # 対比
  pattern: two-column-versus
- relation: process        # 手順
  pattern: step-flow
```

型の名前はPlannerの語彙で書く。それぞれの型を描画の実装のどの機能で描くかは、実装ごとの対応として別に置く。

合格条件:

- 立証設計に現れる全ての `relation` が対応表にある(機械)。
- 1つの `pattern` が複数の `relation` に使われていない(機械)。
- 全ての `pattern` が、選んだ描画の実装とテンプレートで実現できる。実現できない型は、代わりの型を選ぶか、描画の実装への要望として記録する。

### 7. スライド仕様

スライドごとに、載せる内容を確定する。章ごとに1ファイルに分け、章ごとに別のセッションで書く。1章の執筆では、他の章の仕様を読まない。読むのは、全体の成果物(工程2から6)と素材台帳、用語集である。

成果物 `07-slides/ch1.yaml`:

```yaml
- id: ch1-s2
  headline: △△の領域は過去5年、年率8%で伸びている
  takeaway: 成長は一時的な要因ではなく、5年続いている
  body:
    type: line-chart
    data: {...}
  text: 国内市場の{F040}を占めるまでに拡大した   # 数値は事実のIDで参照する
  sources: [F015, F016, F040]
  notes: 口頭で補う説明
```

数値は本文に直接書かず、事実のIDで参照する。ビルドの際に台帳の値に置き換える。他のスライドへの言及も、スライドのIDで書く。

合格条件:

- `headline` がストーリーラインと一致する(機械)。
- `body.type` が、立証設計の `relation` に対応する `pattern` と一致する(機械)。
- `sources` が立証設計の `facts` に含まれる(機械)。
- 本文に、事実のIDによらない数値がない(機械)。
- 用語集の禁止表記と、表記の規則への違反がない(機械)。
- 資料の種類が定める分量の上限に収まる(機械)。

### 8. 全体検査

章ごとに書いた仕様を合わせ、章をまたぐ問題を検査する。ソフトウェア開発の結合テストにあたる。

検査のために、全スライドの見出しと結論1行だけを並べた要約版 `08-digest.md` を作る。100枚の資料でも数百行に収まる。

| 検査する内容 | 方法 |
|---|---|
| 同じ事実が複数のスライドに出ていないか。2回目以降は「再掲」と明示したものだけ許す | 機械(事実のIDの使用箇所を集計) |
| 用語が、定義するスライドより前に使われていないか | 機械(用語集と初出の位置を照合) |
| 他のスライドへの言及の参照先が存在するか | 機械 |
| 章をまたいで主張が矛盾していないか | 検査セッション(要約版を通読) |
| 結論1行を順に読んで `answer` に至るか | 検査セッション(要約版を通読) |

### 9. 仕上げ

完成形をビルドし、全スライドの画像を一覧で見て、ブリーフに照らして確認する。

成果物は `build/deck.pptx` と、`reviews/` 配下のレビュー記録。指摘は、どの工程の成果物を直すかを添えて記録する。

合格条件:

- 描画上の診断(文字のあふれ、要素の重なり、描かれなかった内容)が0件である(機械)。
- 描画の実装があふれを自動で分割してスライドを増やした場合は、工程7に戻って内容を削るか、工程4に戻ってスライドを分ける。分割の結果をそのまま受け入れない。
- 資料がブリーフの問いに答えている(ユーザー)。

## ビルド

ビルドは1回きりの工程ではなく、工程4以降はいつでも実行できる機能とする。成果物の完成度に応じて、見える内容が増える。

| 時点 | 見えるもの |
|---|---|
| 工程4の後 | 見出しと、根拠の事実の要約 |
| 工程5の後 | 見出しと、図の型の仮置き |
| 工程7の後 | 完成形 |

描画の実装に渡す中間のファイル(SlideCraftならMarkdown、Pythonならコード)は `build/` に置くが、正本ではない。ビルドの際に内容を書き足さない。

## 主張の種類の語彙

Plannerが固定の核を持ち、資料ごとに追加を許す。機械的な検査と、描画の実装への対応づけが、固定の語彙を前提にするためである。

| 区分 | 種類 |
|---|---|
| 数量 | 構成比、項目の比較、推移、分布、相関 |
| 概念 | 手順、構造・階層、対比(2案、前後)、因果、位置づけ(2軸)、並列の列挙、言い切り |

数量の5種はZelazny『Say It With Charts』の分類による。語彙の名前と範囲は未確定である。

## スライドの区分

主張の骨子から導かれるスライド(本編)のほかに、次の区分がある。

| 区分 | 例 | 作り方 | 検査 |
|---|---|---|---|
| 導出 | 表紙、目次、章扉、出典の一覧 | 上流の成果物から機械的に作る | 不要 |
| 半導出 | 要約、章のまとめ、結論と次の一手 | 主張の骨子を材料として渡し、LLMが書く | 骨子にない主張や事実を含まないこと |
| 付録 | 詳細なデータ、本編から外した素材 | 本編と同じ。本編のどのスライドを補うかを記録する | 論旨の検査からは外す。事実と用語の検査は受ける |

要約は機械的には作らない。聴衆に合わせた圧縮と強調が要るためである。

## 資料の種類

ブリーフで次の2つの軸を指定し、合格条件を切り替える。

| 軸 | 値 |
|---|---|
| 伝え方 | 口頭で説明する / 配布して読ませる |
| 厳密さ | 意思決定のための要点 / 技術的な記録 |

切り替える条件の候補は、1枚あたりの文字数の上限、ノートを必須にするか、スライド上に出典を必ず載せるか、結論1行を必須にするか、である。具体的な値は未確定である。

## 横断の成果物

### 用語集 `glossary.yaml`

```yaml
- term: 顧客
  forbid: [お客様, クライアント, ユーザー]
  note: 契約主体を指す。利用者個人は「利用者」とする
  defined_in: ch1-s3    # 定義するスライド。定義が要らない一般語では省く
```

工程0から書き始め、工程7以降で機械的に検査する。用語集は資料の表現規約の一部である。

### 素材台帳 `01-sources.yaml`

工程1で作り、全工程を通じて唯一の事実の置き場とする。スライド上の数値と出典の表記は、台帳から生成する。

## セッションの分離

| セッション | 読むもの | してはいけないこと |
|---|---|---|
| 収集 | 調査依頼、外部の資料 | 主張や見出しを書くこと |
| 執筆 | 承認済みの上流の成果物 | Web検索や資料の直接の読み込み、台帳にない事実の記述 |
| 検査 | 検査対象の成果物と、その上流の成果物 | 検査対象を自分で直すこと |

分ける理由:

- 執筆中のLLMは、文を完成させるために必要な事実を補ってしまう。事実を台帳のIDでしか参照できなくすれば、補う余地がなくなる。
- 生の資料が執筆の文脈に入らないため、読み込み量が抑えられる。
- 書いた本人による検査は、自分の誤りを見逃しやすい。

分離だけでは、収集セッション自身の捏造は防げない。そのため素材台帳に引用箇所を記録させ、検査セッションが出典と突き合わせる。

## 描画の実装の条件

| 条件 | 内容 | 満たせない場合 |
|---|---|---|
| 入力 | スライド仕様の1スライド分から、そのスライドを描ける | 採用しない |
| 未完成の仕様 | 見出しだけ、あるいは型の仮置きだけの仕様でも描ける | 採用しない |
| 型の一覧 | 描ける型の一覧を返せる | 工程6の合格条件を人が確認する |
| 再現性 | 同じ型のスライドが、枚数や章をまたいでも同じ見た目になる | 型ごとの部品を先に1度だけ作り、全スライドで使い回す |
| 診断 | 文字のあふれ、重なり、描かれなかった内容を報告できる | 画像にして検査セッションが見る。読み込み量は増える |
| 画像化 | スライドを画像にできる | 採用しない |
| 部分的な作り直し | 1スライドだけを作り直せる | 全体を作り直す |

LLMが書くPythonのコードを使う場合は、再現性の条件に注意する。スライドごとにコードを書き下ろすと、枚数が増えるにつれて見た目がずれる。表現の対応表にある型ごとに描画の関数を1つ作り、スライド仕様をデータとして渡す形にする。

## 修正の流れ

修正は、その内容が属する工程の成果物に対して行い、下流を作り直す。

| 修正の内容 | 直す成果物 | 作り直す範囲 |
|---|---|---|
| 言い回しの変更 | スライド仕様 | 該当スライドのビルド |
| 数値の誤り | 素材台帳 | その事実を参照する全スライドのビルド |
| 見せ方の変更 | 立証設計 | 該当スライドの仕様以降 |
| スライドの追加、順序の変更 | ストーリーライン | 該当スライドの立証設計以降 |
| 図の型の変更 | 表現の対応表 | その型を使う全スライド |
| 章の入れ替え | 章構成 | 該当章以降 |
| 結論の変更 | 主張の骨子 | 章構成以降の全て |

## フィードバック

ビルドした資料への指摘を受け、仕様に反映する。生成後にPowerPointで人が直した内容は、データとして仕様に同期しない。「こうしたい」という意図を伝える見本として読む。

### 入口

- 言葉での指摘。
- スライドを指しての問題点の指定。
- 人が軽く直したPPTX。

直したPPTXは次の方法で読む。PPTXの座標や書式は読まない。

| 知りたいこと | 方法 |
|---|---|
| どのスライドが変わったか | 機械的に検出する |
| 文字の変更 | PPTXから文字だけを抜き出して差分をとる |
| 配置や見た目の変更 | 直す前と後の画像を並べて読む。変わったスライドだけを対象にする |

### 反映先の範囲

LLMは指摘を整理し、反映先の範囲を提案する。「そのスライドだけ」より広い反映は、ユーザーの承認を経る。LLMは1件の指摘を過度に一般化しがちなためである。

| 範囲 | 例 | 直す成果物 |
|---|---|---|
| そのスライドだけ | この言い回しを変える | スライド仕様 |
| 同じ型の全スライド | 比較の図は左右を逆にしたい | 表現の対応表、立証設計 |
| 資料全体 | 文字が全体に多い、この用語に統一 | 資料の表現規約 |
| 今後の全ての資料 | 結論はいつも左上に置く | 個人の表現規約 |
| 道具の側 | この図の型が描けない | 描画の実装への要望 |

### 記録

指摘は `reviews/` に1件ずつ記録する。項目は、指摘の内容、LLMの解釈、反映先の範囲、直した成果物、反映の結果である。作り直した後に、過去の指摘が守られているかを検査セッションが確認する。

### 再現できない手直し

図形を少し動かすなど、仕様で表現できない手直しは、黙って捨てない。作り直すと消えることを理由つきで伝え、描画の実装への要望にするか、最終版の後の手直しに回す。

最終版の後の手直しは自由とする。その後に作り直す場合は、手直しが消えることを警告する。

## 表現規約

資料の表現技法を一貫させるための規則の集まり。次の2層で持ち、資料の規約は個人の規約を引き継いだうえで上書きできる。

| 層 | 置き場 | 内容 |
|---|---|---|
| 個人の表現規約 | 資料のディレクトリの外 | 資料をまたいで守る規則 |
| 資料の表現規約 | 資料のディレクトリ | 用語集、表記の規則、表現の対応表、分量の上限、その資料だけの規則 |

規則の1件は次の項目を持つ。

```yaml
- id: R007
  rule: 対比の図では、現状を左、提案を右に置く
  reason: 読み手は左から右へ時間が進むと受け取る   # なぜその規則があるか
  check: inspection        # mechanical(機械) / inspection(検査セッション)
  origin: FB-012           # 元になった指摘
  exceptions: []           # 意図して外すスライドと、その理由
```

検査の方法を持たない規則は登録しない。守られているかを確かめられない規則は、守られないためである。

意図して一貫性を外す場合(最も重要な1枚だけ見た目を変えるなど)は、`exceptions` に理由つきで明示する。明示のない不一致は違反として扱う。

### 規則の追加と整理

規則を足すたびに、既存の規則との整理と統合を行う。足すだけの運用はしない。

1. **起案**: 指摘から規則の案を作る。
2. **照合**: 既存の全ての規則と比べ、次のいずれかを判定する。

   | 関係 | 対応 |
   |---|---|
   | 重複(同じことを言っている) | 1つにまとめる |
   | 矛盾(両立しない) | どちらを残すかをユーザーが決める |
   | 包含(一方が他方の特殊な場合) | 一般の規則と例外の形に組み直す |
   | 共通の原理がある(個別の規則が複数並ぶ) | 1つの規則に一般化する |

3. **影響の確認**: 整理後の規則を現在の資料に当て、違反になるスライドの一覧を出す。
4. **承認**: ユーザーが、整理後の規則と影響を見て承認する。
5. **反映**: 規則を更新し、違反になったスライドを直す。

整理は規則の数を減らす方向で行う。文章の規則より、表現の対応表や用語集のような、機械で検査できる構造への組み込みを優先する。

## 未検証の前提

- 見出しの復元が、中身と見出しの不一致を実際に検出できるか。
- 「1つの種類に1つの型」が、量の違いで破綻しないか。並列の列挙は、3項目ならカード、8項目なら表が適切である。種類に加えて量の区分を対応表の鍵にする必要があるかもしれない。
- 描画の実装によらない型の語彙を、表現力を落とさずに定められるか。
- 全体を扱う成果物(ストーリーライン、立証設計、要約版)が、100枚規模でも1つのセッションで扱える分量に収まるか。
- SlideCraftを使う場合、表現の型をレイアウト固定の記法で制御できるか。SlideCraftは内容の形からレイアウトを自動で選ぶため、同じ種類のスライドが別のレイアウトになる可能性がある。
- SlideCraftの図の種類(12種とMermaid経由の4種)と区切りの記法で、ビジネス文書に必要な型が足りるか。
- Pythonのコードを使う場合、型ごとの関数を使い回す方式で、文字のあふれを画像を見ずに検出できるか。
- 成果物の書式(YAML)が、LLMにとって書きやすく、人にとって読みやすいか。
- 画像の読み取りが、人の手直しをどの程度の細かさまで拾えるか。
- 規則の数が増えたとき、LLMがどこまで守れるか。数が増えるほど守られにくくなる見込みである。
- この工程が何枚以上の資料で引き合うか。数枚の資料には重すぎる見込みである。
