# スライド作成工程の定義(草案 v0.9)

状態: 草案。細部と書式は未確定である。実物で確かめていない前提は、末尾の「未検証の前提」を参照。

## 目的

LLMによるスライド作成は、枚数が増えると次の問題を起こす。

- 文章が崩れ、スライド間の一貫性が失われる。
- 主張のないスライドが増える。
- 中身のない言い回し、目的に対して多すぎる情報、基準のないグルーピングが混じる。
- 修正のたびにPPTXの座標や書式を読み込み、消費するトークンが膨らむ。

この定義は、スライド作成を工程に分け、工程ごとに成果物と合格条件を定めることで、これらを防ぐ。

## 対象

30枚以上のスライドからなる資料を、新規に作る場合を対象とする。それより少ない枚数の資料は対象としない。工程と承認の回数は、この規模を前提に定める。

## 役割の分担

| 担当 | 範囲 |
|---|---|
| PPTX-Planner(以下Planner) | 何を、どの順で、どの型で伝えるかの設計と検査。この文書が定める工程と、その検査の道具を指す |
| 描画の実装 | スライド仕様からのレイアウトとPPTXの生成、描画上の診断 |

Plannerは特定の描画の実装に依存しない。工程0から8の成果物は、描画の実装の名前や記法を含まない。描画の実装は差し替えられる部品とし、満たすべき条件を「描画の実装の条件」の節に定める。候補は、SlideCraft(Markdownからテンプレートに沿ったPPTXを生成する道具。https://github.com/zyuuryuu/slidecraft )と、LLMが書くPythonのコード(python-pptxなど)である。

座標と書式は描画の実装だけが持つ。

## 原則

1. **正本は仕様で、PPTXは生成物である。** 修正は仕様に対して行い、PPTXは作り直す。LLMはPPTXの中身を読まない。
2. **全体で設計し、章ごとに書き、全体で検査する。** 1枚あたり数行で済む成果物は、資料全体を1つのセッションで扱う。分量の多いスライド仕様だけを章に分ける。
3. **下流の作業は、承認済みの成果物だけで進められるようにする。** 会話の履歴にしかない情報を残さない。
4. **収集、執筆、検査は別のセッションで行う。** 詳細は「セッションの分離」の節。
5. **執筆は素材台帳にある事実だけを使う。** 台帳にない事実が必要になったら、書かずに調査依頼を出す。
6. **人はスライドの形で確認する。** ストーリーライン以降は、未完成でもビルドして見られるようにする。
7. **合格条件を満たせないときは上流に戻る。** 合格条件のほうを書き換えて通すことはしない。
8. **機械で検査できるものは機械で検査する。**

## 工程の一覧

| # | 工程 | 範囲 | 成果物 | 最終の承認 |
|---|---|---|---|---|
| 0 | 依頼の確定 | 全体 | ブリーフ | ユーザー |
| 1 | 探索 | 全体 | 探索の計画、仮説の一覧、素材台帳 | ユーザー(探索の計画)、機械と検査セッション(素材台帳) |
| 2 | 主張の整理 | 全体 | 主張の骨子 | ユーザー |
| 3 | 章立て設計 | 全体 | 章構成 | ユーザー |
| 4 | ストーリーライン | 全体 | スライド見出しの一覧 | ユーザー(骨組みの資料を見て) |
| 5 | 立証設計 | 全体 | スライドごとの立証の設計 | 検査セッションとユーザー(仮置きの資料を見て) |
| 6 | 表現設計 | 全体 | 表現の対応表 | ユーザー |
| 7 | スライド仕様 | 章ごと | 章ごとのスライド仕様 | 機械と検査セッション |
| 8 | 全体検査 | 全体 | 要約版、検査の結果 | 機械と検査セッション |
| 9 | 仕上げ | 全体 | PPTX、レビュー記録 | ユーザー |

最終の承認の前に、各工程の合格条件を全て満たす。合格条件ごとの判定者は、各工程の定義に記す。検査セッションは、執筆とは別に検査だけを行うセッションである(「セッションの分離」の節)。

工程1と2は往復する。工程2で裏付けのない主張が見つかれば、工程1に戻って調べるか、その主張を捨てる。

## 各工程の定義

### 0. 依頼の確定

資料が答える問いを固定する。問いが決まらないと、探索の範囲が決まらない。

成果物 `00-brief.md` の項目:

- 聴衆(誰が読むか、何を既に知っているか)
- 目的(読んだ人に何を決めて、あるいは何をしてほしいか)
- 答えるべき問い(1文)
- 資料の種類(「資料の種類」の節の2つの軸)
- 制約(枚数の目安、発表時間、テンプレート、言語、期限)
- 手元の資料の一覧

この段階では結論を書かない。結論は工程2で決まる。ユーザーが既に持っている結論は、仮説として工程1の仮説の一覧に書く。

作り方:

- 設計セッションが、上の項目を順に1つずつ聞く。選択肢があるものは選択肢を示す。
- 答えるべき問いは、聞かずに案を出す。ほかの項目の答えをもとに問いの文を2つか3つ作り、ユーザーが選ぶか直す。
- 「未定」を答えとして認める。未定の項目は、誰がいつ決めるかを添えて記録する。推測で埋めない。
- 目的ごとに、次を追加で聞く。

  | 目的 | 追加で聞くこと |
  |---|---|
  | 提案書 | 最終的に決める人は誰か。現状維持や他の案との比較になるか |
  | 調査報告 | 調査の範囲と、範囲に含めないもの |
  | 製品紹介 | 相手が今使っている手段と、その不満 |
  | 研修資料 | 受講者の今の水準。受講後に何で習得を確かめるか |

合格条件:

- 全ての項目に、答えか「未定」の記録がある(機械)。
- 検査セッションがブリーフだけを読んで書いた「誰に、何のために、何の問いに答える資料か」が、設計セッションの理解と一致する(検査セッション)。
- ブリーフの内容に同意する(ユーザー)。

### 1. 探索

問いに答えるための事実を集める。収集の手段(Web検索、資料の読み込み、ユーザーへの聞き取り)は、この文書では定めない。定めるのは、何を調べるかと、集めた結果が満たす条件である。

仮の結論に合う事実だけを集めることを防ぐため、次の3つを行う。

- 探索の範囲を、仮の結論ではなく問いから決める。
- 収集セッションに、仮説を見せない。
- 対立する仮説を置き、それぞれを支持する事実と否定する事実を記録する。

成果物 `01-plan.yaml`(探索の計画)は、ブリーフの問いを小さな問いに分解したものである。集める前にユーザーが承認する。

```yaml
- id: Q1
  question: △△の領域の市場は今後も伸びるか
  perspective: null          # 資料の目的が定める観点に対応する場合は、その名前
- id: Q4
  question: 何もしない場合、〇〇事業の収益はどうなるか
  perspective: 何もしない場合
```

計画は、「資料の種類」の節が目的ごとに定める観点を全て含む。

成果物 `01-hypotheses.yaml`(仮説の一覧)には、仮の結論と、それに対立する仮説を1つ以上書く。対立する仮説は、逆の結論や「何もしない」などである。

```yaml
- id: H1
  statement: 〇〇事業は、△△に絞って継続すべきである
  origin: user        # user(ユーザーが持っていた結論) / session(設計セッションが立てた)
- id: H2
  statement: 〇〇事業は撤退すべきである
  origin: session
```

成果物 `01-sources.yaml`(素材台帳)の1件:

```yaml
- id: F012
  statement: 2025年の国内市場規模は1.2兆円
  value: 1.2            # 本文から参照する数値。数値でない事実では省く
  unit: 兆円
  kind: fact            # fact(事実) / inference(推測) / opinion(意見) / derived(計算値)
  source: 〇〇白書 2025年版
  locator: p.34 図表2-1  # ページ、URL、節など
  quote: "国内市場は1兆2,000億円に達した"
  origin: 〇〇省の統計    # 元をたどった情報源。別の資料が同じ情報源を引いている場合に、同じ値になる
  answers: [Q1]          # 探索の計画のどの問いに答えるか
  stance: {H1: supports, H2: contradicts}   # 仮説ごとに、supports(支持) / contradicts(否定) / neutral(どちらでもない)
  verified: true        # 検査セッションが引用箇所を確認したか
```

`answers` までは収集セッションが書く。`stance` は、収集の後に設計セッションが書く。

合計や比率などの計算値も、台帳に登録する。計算値は、元の事実が全て `verified: true` で、再計算の結果が一致するときに `verified: true` とする。

```yaml
- id: F040
  statement: △△領域は国内市場の25%を占める
  value: 25
  unit: "%"
  kind: derived
  formula: F013 / F012   # 元になる事実と計算式
  verified: true
```

後の工程で根拠に使えるのは、`verified: true` の `fact` と `derived` だけである。`inference` と `opinion` は根拠に使えない。スライドに載せる場合は、推測または意見であることを文面に明示する。使われない事実が台帳に残ることは問題としない。

調査は設計セッションや執筆セッションから直接行わず、調査依頼として収集セッションに渡す。調査依頼は、探索の計画の問いをそのまま渡す。「Aを裏付ける事実を探せ」のような、結論を含む聞き方をしない。収集セッションは仮説の一覧を読まない。ブリーフに挙げた手元の資料も、収集セッションが読んで台帳に取り込む。調査依頼の項目:

- 知りたいこと(1文の問い)
- 探索の計画のどの問いに対応するか
- 返す形式(素材台帳の書式)
- 見つからなかった場合は「見つからない」と返すこと

合格条件:

- 全ての `fact` に `source`、`locator`、`quote` がある(機械)。
- 全ての `derived` の計算式が、元の事実の値から再計算して一致する(機械)。
- `fact` の `quote` が出典に実在する(検査セッション)。確認できないものは `verified: false` のまま残す。
- 探索の計画の全ての問いに、答える事実か「見つからない」の記録がある(機械)。
- 調査依頼の文面が、仮説や結論を含まない(検査セッション)。
- 全ての事実に、全ての仮説に対する `stance` がある(機械)。

網羅したことは証明できない。確かめられるのは、承認した計画に対して漏れがないことまでである。

### 2. 主張の整理

集めた事実から、問いへの答えを組み立てる。

成果物 `02-claims.yaml`(主張の骨子):

```yaml
answer: 〇〇事業は、△△に絞って継続すべきである
axis: 市場、自社の強み、採算   # 主張を何の基準で分けたか
claims:
  - id: C1
    statement: 市場全体は縮小するが、△△の領域だけは伸びている
    evidence: [F012, F015, F021]
    assumes: [△△の領域の伸びを支える規制が続く]   # 事実から主張を導くときに置いた前提
    objections:                                  # 反論と、それへの答え
      - objection: 伸びているのは大手の寡占による一時的な現象ではないか
        response: 新規参入の件数も増えている
        evidence: [F021]
  - id: C2
    statement: ...
    evidence: [F030]
```

合格条件:

- `answer` がブリーフの問いに答えている(ユーザー)。
- 主張の数が、資料の表現規約が定める上限以下である(機械)。
- `answer` と各主張が、否定の検査と具体性の検査を通る(検査セッション)。
- 主張の分け方が、分類の軸の検査を通る(検査セッション)。
- 全ての主張に、`verified: true` の事実が1件以上紐づく(機械)。
- 1つの `origin` だけに頼る主張がない。ある場合は、そのことを主張に明記する(機械)。
- 採用した仮説を否定する事実(`stance` が `contradicts`)の全てに、反駁する、結論に条件を付ける、結論を変える、のいずれかの扱いが記録されている(機械)。
- 独立した導出: 仮説の一覧を読んでいない検査セッションに、ブリーフの問いと素材台帳だけを渡して答えを書かせる。`answer` と食い違う場合は、違いをユーザーに示す(検査セッション)。
- 反論の検査: 検査セッションが、素材台帳を使って `answer` への最も強い反論を組み立てる。その反論が `objections` にあるか、付録の想定問答に入っている(検査セッション)。
- 事実から主張を導くのに必要な前提が、`assumes` に書かれている(検査セッション)。

最後に決めるのはユーザーである。証拠と食い違う点を承知のうえで結論を維持する場合は、その判断を設計の判断の記録に残す。

### 3. 章立て設計

主張の骨子を章に割り当てる。章は話題の区分ではなく、主張の区分とする。

成果物 `03-chapters.yaml`:

```yaml
- id: ch1
  title: 市場の現状
  message: 市場全体は縮小するが、△△の領域だけは伸びている
  claims: [C1]
  slides: 6        # 枚数の目安
```

合格条件:

- 全ての主張がいずれかの章に割り当てられている(機械)。
- 章の `message` を順に読むと `answer` が導ける(検査セッションとユーザー)。
- 枚数の合計がブリーフの制約に収まる(機械)。
- 章の `message` が、否定の検査と具体性の検査を通る(検査セッション)。
- 全ての章が除去の検査を通る(検査セッション)。
- 章の分け方が、分類の軸の検査を通る(検査セッション)。

### 4. ストーリーライン

全ての章のスライドの見出しを、1つのセッションで決める。見出しは体言止めの題名ではなく、主張を述べる文とする。全体を一度に扱うことで、章をまたぐ主張の重複と矛盾をこの段階で防ぐ。

成果物 `04-storyline.yaml`:

```yaml
- id: ch1-s2
  chapter: ch1
  headline: △△の領域は過去5年、年率8%で伸びている
  evidence: [F015]
```

この時点で骨組みの資料をビルドする。各スライドには見出しと、根拠の事実の `statement` だけが載る。ユーザーはこの資料を見て承認する。

合格条件:

- 1スライドに見出しは1つである(機械)。
- 全てのスライドに `evidence` がある(機械)。
- 章内の見出しを順に読むと、章の `message` が導ける(検査セッションとユーザー)。
- 同じ主張を述べる見出しが複数ない(検査セッション)。
- 全ての見出しが、否定の検査、具体性の検査、語彙と文体の検査を通る(検査セッション)。
- 見出しに、用語集の禁止表記と、表記の規則への違反がない(機械)。
- 見出しの中の数値が、そのスライドの `evidence` の事実と一致する(検査セッション)。
- 全てのスライドが除去の検査を通る。通らないスライドは、付録に回すか捨てる(検査セッション)。

### 5. 立証設計

スライドごとに、見出しを読み手に納得させるために何を見せるかを決める。中身を書く前に行う。全体を1つのセッションで扱う。

成果物 `05-proof.yaml`:

```yaml
- id: ch1-s2
  relation: trend                 # 主張の種類
  show: 全体と△△領域の売上を5年分並べる   # 見せるもの
  focus: 2023年以降の差の広がり          # 注目させる点
  facts: [F015, F016, F040]       # 使う事実
  axis: null                      # 項目をまとめるスライドでは、分類の軸を書く
```

`facts` が足りなければ、調査依頼を出して工程1に戻る。

この時点で仮置きの資料をビルドする。各スライドには見出しと、図の型の仮置き(「ここに5年分の推移」など)が載る。

合格条件:

- `relation` が「主張の種類の語彙」にある(機械)。
- `facts` が全て素材台帳にあり、`verified: true` である(機械)。
- スライド内の要素が除去の検査を通る。`show` が、`focus` に関係しない要素を含まない(検査セッション)。
- 項目をまとめるスライドが、分類の軸の検査を通る(検査セッション)。
- 仮置きの資料を見て、見せ方に同意する(ユーザー)。
- 見出しの復元: 検査セッションに見出しを隠して `show`、`focus`、`facts` だけを見せ、見出しを書かせる。元の見出しと意味が一致する(検査セッション)。

### 6. 表現設計

全スライドの立証設計を集計し、主張の種類と表現の型の対応を、資料ごとに1つ定める。同じ種類の主張には同じ型を、違う種類の主張には違う型を使う。

成果物 `06-patterns.yaml`(表現の対応表):

```yaml
- relation: trend          # 推移
  pattern: line-chart      # 型の名前
- relation: contrast       # 対比
  pattern: two-column-versus
- relation: process        # 手順
  pattern: step-flow
```

型の名前の一覧と、それぞれの型を描画の実装のどの機能で描くかの対応は、置き場と書式が未確定である。

合格条件:

- 立証設計に現れる全ての `relation` が対応表にある(機械)。
- 1つの `pattern` が複数の `relation` に使われていない(機械)。
- 全ての `pattern` が、選んだ描画の実装とテンプレートで実現できる。実現できない型は、代わりの型を選ぶか、描画の実装への要望として記録する(機械。型の一覧を返せない実装ではユーザー)。
- 対応表の内容に同意する(ユーザー)。

### 7. スライド仕様

スライドごとに、載せる内容を確定する。章ごとに1ファイルに分け、章ごとに別のセッションで書く。1章の執筆では、他の章の仕様を読まない。読むのは、ブリーフ、全体の成果物(工程2から6)、素材台帳、表現規約である。

成果物 `07-slides/ch1.yaml`:

```yaml
- id: ch1-s2
  headline: △△の領域は過去5年、年率8%で伸びている
  takeaway: 成長は一時的な要因ではなく、5年続いている   # 結論1行。本編のスライドでは必須
  body:
    type: line-chart
    data: {...}
  text: 国内市場の{F040}を占めるまでに拡大した   # 数値は事実のIDで参照する
  sources: [F015, F016, F040]
  notes: 口頭で補う説明
```

`text`、`body.data`、`notes` の数値は直接書かず、事実のIDで参照する。ビルドの際に台帳の値に置き換える。`headline` と `takeaway` は、ストーリーラインを人が読めるように数値を直接書いてよい。その数値は、そのスライドの `sources` の事実と一致させる。他のスライドへの言及は、スライドのIDで書く。

合格条件:

- `headline` がストーリーラインと一致する(機械)。
- `body.type` が、立証設計の `relation` に対応する `pattern` と一致する(機械)。
- `sources` が立証設計の `facts` に含まれる(機械)。
- `text`、`body.data`、`notes` に、事実のIDによらない数値がない(機械)。
- `headline` と `takeaway` の数値が、`sources` の事実と一致する(検査セッション)。
- 用語集の禁止表記と、表記の規則への違反がない(機械)。
- `takeaway`、`text`、`notes` が語彙と文体の検査を通る(検査セッション)。
- ブリーフに「聴衆が既に知っている」と書かれた内容の説明を含まない(検査セッション)。
- 資料の表現規約が定める分量の上限に収まる(機械)。

### 8. 全体検査

章ごとに書いた仕様を合わせ、章をまたぐ問題を検査する。

検査のために、全スライドの見出しと結論1行だけを並べた要約版 `08-digest.md` を機械的に作る。

要約、章のまとめ、結論と次の一手のスライドは、この工程で書く。主張の骨子と要約版を材料として、全体を扱う1つのセッションで書く。

合格条件:

| 条件 | 判定 |
|---|---|
| 同じ事実が複数のスライドに出ていない。2回目以降は「再掲」と明示したものだけ許す | 機械(事実のIDの使用箇所を集計) |
| 用語が、定義するスライドより前に使われていない | 機械(用語集と初出の位置を照合) |
| 他のスライドへの言及の参照先が存在する | 機械 |
| 章をまたいで主張が矛盾していない | 検査セッション(要約版を通読) |
| 結論1行を順に読んで `answer` に至る | 検査セッション(要約版を通読) |
| 要約、章のまとめ、結論と次の一手が、主張の骨子と要約版にない主張や事実を含まない | 検査セッション |

条件を満たさない場合は、問題のあるスライドの仕様(工程7)に戻る。主張の矛盾が見出しに由来する場合は、ストーリーライン(工程4)に戻る。

### 9. 仕上げ

最終のビルドを行い、全スライドの画像を一覧で見て、ブリーフに照らして確認する。

成果物は `build/deck.pptx`。指摘はIssueとして記録する(「フィードバック」の節)。

合格条件:

- 描画上の診断(文字のあふれ、要素の重なり、描かれなかった内容)が0件である(機械)。
- スライドの枚数と見出しが、ストーリーラインおよび導出したスライドと一致する(機械)。
- 資料がブリーフの問いに答えている(ユーザー)。

描画の実装があふれを自動で分割してスライドを増やした場合は、工程7に戻って内容を削るか、工程4に戻ってスライドを分ける。

## ビルド

| 時点 | 見えるもの |
|---|---|
| 工程4の後 | 見出しと、根拠の事実の要約 |
| 工程5の後 | 見出しと、図の型の仮置き |
| 工程7の後 | 完成形 |

描画の実装に渡す中間のファイル(SlideCraftならMarkdown、Pythonならコード)は `build/` に置くが、正本ではない。ビルドの際に内容を書き足さない。

## 意味の検査

次の検査を、主にスライドの中身を書く前の工程で行う。検査は、はいかいいえで答えられる問いにする。「良い文章か」という問いでは、LLMは見逃すためである。

| 検査 | 問い | 対象 | 工程 |
|---|---|---|---|
| 否定の検査 | その文を否定した文は、主張として成り立つか | 主張、章の主張、見出し | 2、3、4 |
| 具体性の検査 | 主語と述語があり、対象、数値、条件のいずれかを含むか | 主張、章の主張、見出し | 2、3、4 |
| 除去の検査 | それを抜くと、上位の主張が成り立たなくなるか | 章、スライド、スライド内の要素 | 3、4、5 |
| 分類の軸の検査 | 何の基準で分けたかを一言で言えるか。項目は同じ水準か。1つの項目が2つのグループに入らないか。グループの数は軸から決まっているか | 主張の分け方、章の分け方、項目をまとめるスライド | 2、3、5 |
| 語彙と文体の検査 | 個人の表現規約が禁じる書き方を含まないか | 見出し、本文 | 4、7 |

否定の検査の例: 「品質の向上は重要である」は、否定した「品質の向上は重要でない」が主張として成り立たない。この見出しは何も述べていない。

## 資料の種類

ブリーフで、資料の目的と伝え方を指定し、合格条件を切り替える。

| 目的 | 読み手に起こしたいこと | 頂点に置くもの | 探索で必ず調べる観点 |
|---|---|---|---|
| 提案書 | 決めてもらう | 提案とその理由 | 何もしない場合、他の案、費用、リスク、反対する立場の論点 |
| 調査報告 | 知ってもらう | 問いへの答え | 範囲の定義、対立する見解、データの限界 |

伝え方は、口頭で説明するか、配布して読ませるかのいずれかである。

研修資料では、主張の骨子の `answer` が学習の目標に、主張が習得する項目に替わる。この読み替えで工程がそのまま使えるかは未検証である。

切り替える条件の候補は、主張の数の上限、1枚あたりの文字数の上限、ノートを必須にするか、スライド上に出典を必ず載せるか、である。資料の種類はこれらの初期値を決め、値そのものは資料の表現規約に置く。具体的な値は未確定である。

## セッションの分離

| セッション | 読むもの | してはいけないこと |
|---|---|---|
| 収集 | 調査依頼、外部の資料 | 主張や見出しを書くこと、仮説の一覧を読むこと |
| 執筆 | 承認済みの上流の成果物 | Web検索や資料の直接の読み込み、台帳にない事実の記述 |
| 検査 | 検査対象の成果物と、その上流の成果物 | 検査対象を自分で直すこと |

分ける理由:

- 執筆中のLLMは、文を完成させるために必要な事実を補ってしまう。事実を台帳のIDでしか参照できなくすれば、補う余地がなくなる。
- 生の資料が執筆の文脈に入らないため、読み込み量が抑えられる。
- 書いた本人による検査は、自分の誤りを見逃しやすい。

分離だけでは、収集セッション自身の捏造は防げない。そのため素材台帳に引用箇所を記録させ、検査セッションが出典と突き合わせる。

## 体制

作業を、性質の違う2つの時期に分ける。

| | 設計の時期(工程0から6) | 製造の時期(工程7から9) |
|---|---|---|
| 成果物 | 小さい。全体を一度に扱える | 大きい。章ごとに分かれる |
| ユーザーとの対話 | 多い | 少ない |
| 並行する作業 | ない | ある |
| 進め方 | 1つの設計セッションが、ユーザーと対話しながら書く | PMが子セッションに割り振り、結果を受け入れる |

設計の時期にはPMを置かない。並行する作業がなく、PMを挟むとユーザーの意図が伝言で薄まるためである。

### 設計セッション

設計の時期を通して、ユーザーの相手をする1つのセッション。工程0から6の成果物のうち、素材台帳の収集を除くものを書く。事実の収集と検査は、別のセッションに任せる。

設計の途中の判断は、設計の判断の記録 `decisions.md` に残す。ソフトウェア開発の設計判断の記録(ADR)と同じ形をとる。

- 状況(何を決める必要があったか。関係する事実)
- 決めたこと
- 却下した案と、その理由
- 受け入れた影響(証拠との食い違い、残る危険など)
- 決めた人と日付

記録するのは、案を却下したとき、証拠と食い違う結論を維持したとき、表現規約の規則の矛盾をユーザーが裁いたときである。

製造の時期に入っても終了させず、設計担当として残す。製造中に設計の疑問や見直しが出たら、PMとユーザーはこのセッションに戻る。

### 引き継ぎの検査

製造の時期に入る前に行う。新しいセッションに成果物だけを読ませ、次を確かめる。

- 資料の結論、章の構成、各章の主張を、自分の言葉で説明できる。
- 設計の判断の記録にある却下した案を、再び提案しない。
- 作業を始めるうえで分からない点がない。

説明が設計セッションの意図と食い違う場合や、分からない点が挙がった場合は、成果物を直す。

### PM

製造の時期を進めるセッション。引き継ぎの検査に通った後、新しく起こすことを既定とする。承認済みの成果物だけを読んで始める。設計セッションがそのままPMを兼ねる形も許す。どちらの場合も、引き継ぎの検査は行う。PMが止まったときや、文脈が膨らみすぎたときに、新しいセッションに替えられるようにするためである。

- 中身を書かない。読むのは、状態の記録、全体を扱う成果物、検査の合否である。
- 章または節ごとに執筆の子セッションを起こし、検査セッションを起こす。
- 子セッションの成果物を、検査のコマンドが通った場合にだけ受け入れる。作る者と受け入れる者を分けることで、検査の回避を防ぐ。
- 子セッションには、成果物の場所と課題を渡す。内容を要約して伝えない。
- 設計の見直しが必要になったら、Issueを立てて設計セッションとユーザーに知らせる。自分では設計を直さない。

章が、1つの子セッションで扱う枚数の上限を超える場合は、節に分ける。上限の値は未確定である。

### 子セッション

子セッションは、ユーザーから見え、後から再開できるセッションとする。PMの内部で動いて結果だけを返す、ユーザーから見えない下請けの処理にはしない。

- ユーザーは、どの子セッションの作業も開いて読める。
- ユーザーは、子セッションに直接指示できる。その結果はコミットとIssueに残り、PMはそこから知る。
- 執筆の子セッションは、章や節を担当し続ける。その章への指摘は、同じセッションに渡す。
- 検査セッションは、検査のたびに新しく起こす。前回の検査を覚えていると、見たつもりで見落とすためである。作業の記録はユーザーから見える形で残す。
- セッションには、資料の名前、担当、役割が分かる名前を付ける。

セッションの記憶は正本ではない。正本は成果物のファイルである。上流の成果物が変わったら、担当のセッションに読み直させるか、新しいセッションに替える。どのセッションが止まっても、成果物と状態の記録から別のセッションが引き継げるようにする。

## Gitでの管理

資料ごとの成果物を、Gitのリポジトリで管理する。

| ソフトウェア開発 | スライド作成 |
|---|---|
| コミット前の自動検査 | 機械的な検査 |
| コードレビュー | 検査セッションによる検査 |
| 変更の受け入れ | PMによる受け入れ、ユーザーの承認 |
| Issue | 指摘、調査依頼、検査で残った問題、描画の実装への要望 |
| 機能ごとのブランチ | 章や節ごとの執筆 |
| 変更の差分 | 上流を直したとき、下流のどれが古くなったかの判定 |
| ビルドの生成物は管理しない | PPTXは管理の対象から外す |

- ユーザーの承認は、タグまたは状態の記録として残す。
- ユーザーにはYAMLの差分を読ませない。直す前と後のスライドを見せる。
- プルリクエストとCIは必須としない。複数人で1つの資料を作る場合の選択肢とする。

### 検査の実行

機械的な検査は、1つのコマンドにまとめる。

| 検査 | 実行する時点 |
|---|---|
| 書式、IDの参照先、用語集、数値の参照、分量の上限 | コミット前 |
| ビルド、描画上の診断 | 工程の合格判定のとき |
| 検査セッションによる検査 | 工程の合格判定のとき |

コミット前の検査は飛ばすことができる。そのため、工程の合格判定とPMによる受け入れの際に、同じコマンドをもう一度実行する。

## ユーザーとのやり取り

ユーザーの負担を抑えるため、次を守る。

- 一度に求める判断は1つにする。
- 白紙の質問ではなく、推奨と代案を示して選んでもらう。
- 全体の流れを先に見せ、その後は章ごとに進める。
- 検査に通ったものは見せず、判断が要るものだけを出す。
- 承認済みのものを再び聞かない。上流の変更で見直しが要るときは、変わった箇所だけを見せる。

## 中身の書式の方針

スライドの中身を意味の水準で記述する標準は見当たらない。部分ごとに、広く使われている考え方を組み合わせる。書式そのものは未確定である。

| 部分 | 参考にするもの |
|---|---|
| 文章 | Markdown |
| 数量の図 | データの表と、図の種類の指定を分けて書く(Vega-Liteの考え方) |
| 概念の図 | PowerPointのSmartArtの分類。どの型でも、データは階層のある箇条書き1つで表す |
| 矢印でつなぐ図 | Mermaid |
| 情報の種類 | Hornの情報マッピング(手順、構造、概念、分類など) |

文字のあふれは、描く前に防ぐ。型の項目ごとに収まる字数を定め、スライド仕様の段階で機械的に検査する。新聞や雑誌が、紙面の枠ごとに字数を決めてから原稿を発注するのと同じ考え方である。

## 描画の実装の条件

| 条件 | 内容 | 満たせない場合 |
|---|---|---|
| 入力 | スライド仕様の1スライド分から、そのスライドを描ける | 採用しない |
| 未完成の仕様 | 見出しだけ、あるいは型の仮置きだけの仕様でも描ける | 採用しない |
| 型の一覧 | 描ける型の一覧を返せる | 工程6の合格条件を人が確認する |
| 収容量 | 型の項目ごとに、収まる字数を返せる | 描いてから診断で確かめる。手戻りが増える |
| 再現性 | 同じ型のスライドが、枚数や章をまたいでも同じ見た目になる | 型ごとの部品を先に1度だけ作り、全スライドで使い回す |
| 診断 | 文字のあふれ、重なり、描かれなかった内容を報告できる | 画像にして検査セッションが見る。読み込み量は増える |
| 画像化 | スライドを画像にできる | 採用しない |
| 部分的な作り直し | 1スライドだけを作り直せる | 全体を作り直す |

LLMが書くPythonのコードを使う場合は、再現性の条件に注意する。スライドごとにコードを書き下ろすと、枚数が増えるにつれて見た目がずれる。表現の対応表にある型ごとに描画の関数を1つ作り、スライド仕様をデータとして渡す形にする。

## 修正の流れ

修正は、その内容が属する工程の成果物に対して行い、下流を作り直す。

| 修正の内容 | 直す成果物 | 作り直す範囲 |
|---|---|---|
| 言い回しの変更 | スライド仕様 | 該当スライドのビルド |
| 数値の誤り | 素材台帳 | その事実を参照する全スライドのビルド。見出しと結論1行に数値を直接書いたスライドは、その文も直す |
| 見せ方の変更 | 立証設計 | 該当スライドの仕様以降 |
| スライドの追加、順序の変更 | ストーリーライン | 該当スライドの立証設計以降 |
| 図の型の変更 | 表現の対応表 | その型を使う全スライド |
| 章の入れ替え | 章構成 | 該当章以降 |
| 結論の変更 | 主張の骨子 | 章構成以降の全て |

## フィードバック

ビルドした資料への指摘を受け、仕様に反映する。生成後にPowerPointで人が直した内容は、データとして仕様に同期しない。「こうしたい」という意図を伝える見本として読む。

### 入口

- 言葉での指摘。
- スライドを指しての問題点の指定。
- 人が軽く直したPPTX。

直したPPTXは次の方法で読む。PPTXの座標や書式は読まない。

| 知りたいこと | 方法 |
|---|---|
| どのスライドが変わったか | 機械的に検出する |
| 文字の変更 | PPTXから文字だけを抜き出して差分をとる |
| 配置や見た目の変更 | 直す前と後の画像を並べて読む。変わったスライドだけを対象にする |

### 反映先の範囲

LLMは指摘を整理し、反映先の範囲を提案する。「そのスライドだけ」より広い反映は、ユーザーの承認を経る。LLMは1件の指摘を過度に一般化しがちなためである。

| 範囲 | 例 | 直す成果物 |
|---|---|---|
| そのスライドだけ | この言い回しを変える | スライド仕様 |
| 同じ型の全スライド | 比較の図は左右を逆にしたい | 表現の対応表、立証設計 |
| 資料全体 | 文字が全体に多い、この用語に統一 | 資料の表現規約 |
| 今後の全ての資料 | 結論はいつも左上に置く | 個人の表現規約 |
| 道具の側 | この図の型が描けない | 描画の実装への要望 |

### 記録

指摘は1件ずつIssueとして記録する。項目は、指摘の内容、LLMの解釈、反映先の範囲、直した成果物、反映の結果である。作り直した後に、過去の指摘が守られているかを検査セッションが確認する。

### 再現できない手直し

図形を少し動かすなど、仕様で表現できない手直しは、黙って捨てない。作り直すと消えることを理由つきで伝え、描画の実装への要望にするか、最終版の後の手直しに回す。

最終版の後の手直しは自由とする。その後に作り直す場合は、手直しが消えることを警告する。

## 表現規約

資料の表現技法を一貫させるための規則の集まり。次の2層で持ち、資料の規約は個人の規約を引き継いだうえで上書きできる。

| 層 | 置き場 | 内容 |
|---|---|---|
| 個人の表現規約 | 資料のディレクトリの外 | 資料をまたいで守る規則 |
| 資料の表現規約 | 資料のディレクトリ | 用語集、表記の規則(単位、日付の書式、文末の形など)、表現の対応表、主張の数と分量の上限、その資料だけの規則 |

規則の1件は次の項目を持つ。

```yaml
- id: R007
  rule: 対比の図では、現状を左、提案を右に置く
  reason: 読み手は左から右へ時間が進むと受け取る   # なぜその規則があるか
  check: inspection        # mechanical(機械) / inspection(検査セッション)
  origin: "#12"            # 元になった指摘のIssue
  exceptions: []           # 意図して外すスライドと、その理由
```

個人の表現規約の初期値は、次の書き方の禁止と抑制とする。それぞれを上の書式の規則として登録し、検査の方法は `inspection` とする。

- 禁止: 情報を足さない飾りの形容、読み手が知っている前提の説明、本題の前の前置き、資料自身の狙いや構成を語る文、依頼や検討の経緯を写した文。
- 抑制: 補足のない専門用語と略語、接続詞の代わりに使う矢印や記号。

検査の方法を持たない規則は登録しない。守られているかを確かめられない規則は、守られないためである。

意図して一貫性を外す場合(最も重要な1枚だけ見た目を変えるなど)は、`exceptions` に理由つきで明示する。明示のない不一致は違反として扱う。

### 規則の追加と整理

規則を足すたびに、既存の規則との整理と統合を行う。

1. **起案**: 指摘から規則の案を作る。
2. **照合**: 既存の全ての規則と比べ、次のいずれかを判定する。

   | 関係 | 対応 |
   |---|---|
   | 重複(同じことを言っている) | 1つにまとめる |
   | 矛盾(両立しない) | どちらを残すかをユーザーが決める |
   | 包含(一方が他方の特殊な場合) | 一般の規則と例外の形に組み直す |
   | 共通の原理がある(個別の規則が複数並ぶ) | 1つの規則に一般化する |

3. **影響の確認**: 整理後の規則を現在の資料に当て、違反になるスライドの一覧を出す。
4. **承認**: ユーザーが、整理後の規則と影響を見て承認する。
5. **反映**: 規則を更新し、違反になったスライドを直す。

整理は規則の数を減らす方向で行う。文章の規則より、表現の対応表や用語集のような、機械で検査できる構造への組み込みを優先する。

## 未検証の前提

- 見出しの復元が、中身と見出しの不一致を実際に検出できるか。
- 「1つの種類に1つの型」が、量の違いで破綻しないか。並列の列挙は、3項目ならカード、8項目なら表が適切である。種類に加えて量の区分を対応表の鍵にする必要があるかもしれない。
- 描画の実装によらない型の語彙を、表現力を落とさずに定められるか。
- 見出しと結論1行に数値を直接書く扱いで、台帳との不一致を検査セッションが拾えるか。
- 全体を扱う成果物(ストーリーライン、立証設計、要約版)が、100枚規模でも1つのセッションで扱える分量に収まるか。
- SlideCraftを使う場合、表現の型をレイアウト固定の記法で制御できるか。SlideCraftは内容の形からレイアウトを自動で選ぶため、同じ種類のスライドが別のレイアウトになる可能性がある。
- SlideCraftの図の種類(12種とMermaid経由の4種)と区切りの記法で、ビジネス文書に必要な型が足りるか。
- Pythonのコードを使う場合、型ごとの関数を使い回す方式で、文字のあふれを画像を見ずに検出できるか。
- 成果物の書式(YAML)が、LLMにとって書きやすく、人にとって読みやすいか。
- 独立した導出と反論の検査が、仮の結論への偏りを実際に見つけられるか。
- 意味の検査が、検査セッションによって実際に中身のない主張を落とせるか。検査セッションもLLMで、AIらしい文章を自然だと感じる傾向は同じである。
- 字数による収容量の見積もりに、どの程度の余裕が要るか。文字の幅は一定でない。
- PMを新しく起こす場合と、設計セッションが兼ねる場合とで、読み込み量と判断の質がどう違うか。
- 執筆の子セッションが章を担当し続ける場合、記憶に残った古い前提が、上流の変更の後に悪さをしないか。
- 画像の読み取りが、人の手直しをどの程度の細かさまで拾えるか。
- 規則の数が増えたとき、LLMがどこまで守れるか。数が増えるほど守られにくくなる見込みである。
