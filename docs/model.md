# 仕組みの定義

[目次に戻る](README.md)

状態: 仮決め。試作の結果を見て見直す。

実在の仕組みを写す図(構成図、ER図、シーケンス図、状態遷移図、業務の流れ図、組織図など)を、正確に、かつ図をまたいで整合させるための成果物。書き手の整理を示す図(「3つの柱」など)は対象としない。

## 考え方

LLMに、出典から図を直接描かせない。出典から図を直接描くと、どの線が出典にあり、どの線がLLMの補完なのかを後から区別できない。次の2段階に分ける。

1. 出典から、要素とつながりを1件ずつ抜き出し、仕組みの定義に登録する。
2. 図は、仕組みの定義から要素とつながりを選んで作る。図の記述は、選んだ内容から機械的に生成する。

| 確かめること | 方法 |
|---|---|
| 図が、仕組みの定義にないものを含まない | 機械。図は定義からの選択であり、構造上含められない |
| 仕組みの定義が、出典にないものを含まない | 検査セッション。1件ずつ引用箇所と突き合わせる |

図の中の名前は定義から機械的に引くため、図によって名前が変わることがない。

## 成果物

`01-model.yaml`。工程1で作る。

```yaml
elements:
  - id: E-order
    kind: component          # component(部品) / actor(主体) / data(データ) / state(状態) など
    name: 注文サービス
    evidence: [F101]         # 素材台帳の事実
relations:
  - id: R-order-stock
    kind: call               # call(呼び出し) / send(送信) / contain(包含) / depend(依存) / transition(遷移) など
    from: E-order
    to: E-stock
    label: 在庫の確認
    mode: unknown            # 出典に書かれていない属性は unknown とする
    evidence: [F102]
  - id: R-web-db
    kind: call
    from: E-web
    to: E-db
    summarizes: [R-web-order, R-order-db]   # 間を省略したつながり。元のつながりを記録する
scenarios:
  - id: S-purchase
    name: 購入の処理
    steps: [R-web-order, R-order-stock, R-order-db]   # つながりを順に並べる
    evidence: [F110]         # 順序の出典
```

要素、つながり、場面の1件ごとに、素材台帳の事実を紐づける。事実の種類と確認の条件は、[工程1](stages/01-exploration.md)の定めに従う。

## 抜き出し

信頼の順位を次の通りとする。

| 順位 | 出どころ |
|---|---|
| 1 | 機械で読める出典(データベースの定義、APIの定義、構成の定義など)からの機械的な抜き出し |
| 2 | 文書からLLMが抜き出し、検査セッションが確認したもの |
| 3 | ユーザーの証言 |
| 不可 | LLMの推測 |

- 機械で読める出典がある場合は、LLMを使わずに抜き出す。
- 出典に書かれていないことは、`unknown` として登録する。よくある構成であることを理由に、書かれていない要素やつながりを足さない。`unknown` の項目は、ユーザーに聞くか、図の上で未確定と示す。
- 間の要素を省いたつながりは、実在しないつながりである。`summarizes` に元のつながりを記録したものだけを認める。
- 出典の日付または版を、素材台帳の事実の `as_of` に記録する。

## 合格条件

- 全ての要素、つながり、場面に、`verified: true` の事実が紐づく(機械)。
- 要素の1件ごとに、その要素が出典にあり、名前と種類が出典の記述と合う(検査セッション。重大な検査)。
- つながりの1件ごとに、向きと条件が出典の記述と合う(検査セッション。重大な検査)。
- 場面の1件ごとに、順序が出典の記述と合う(検査セッション。重大な検査)。
- `summarizes` のあるつながりが、元のつながりを順にたどったものになっている(機械)。
- 資料の中心になる図に使う範囲は、別のセッションが同じ出典から独立に抜き出し、差分を出す。一方にしかない要素とつながりを、ユーザーが確認する(検査セッションとユーザー)。
- 定義の全体を図にしたものを見て、内容に同意する。証言に基づく箇所と `unknown` の箇所には印を付けて示す(ユーザー)。

## 図での使い方

[工程5](stages/05-proof.md)で、スライドごとに、図に使う要素とつながり、または場面を選ぶ。[工程7](stages/07-slide-spec.md)のスライド仕様は、立証の設計の `view` をそのまま参照する。

- 図は、定義にある要素とつながりだけを含む(機械)。
- 「全体」を見出しで述べる図は、該当する種類の要素を全て含む(機械。工程5)。
- 要素とつながりの数が型の上限を超える図は、警告とする。全体像を示すために意図して密にする場合は、表現規約の例外として理由を添える。全体図と詳細図に分ける場合は、詳細図で、全体図での要素の位置と名前を保つ。
- 文字が読める大きさであることは、例外を認めない。

図をまたぐ整合は、[工程5](stages/05-proof.md)で、全てのスライドの `view` がそろった時点で検査する。図の中の名前は定義から引くため、名前の不一致は起きない。

## 画面の操作の手順

スクリーンショットに操作の順を書き足すスライドも、この定義から作る。

- 画面上の要素(ボタン、入力欄など)を、要素として登録する。画像の素材の `regions` が、要素と画像の中の位置を結びつける。
- 操作の手順を、場面として登録する。順序の出典は、手順書、実際の操作の記録、ユーザーの証言のいずれかとする。
- スライドに付ける番号は、場面の `steps` の順から機械的に決まる。

## 限界

- 出典が古い、または誤っている場合は防げない。
- 図を機械的に生成するため、配置の自由度が下がる。配置の調整をどこまで認めるかは未確定である。
