# 不合格と修正の手順

[目次に戻る](README.md)

状態: 方向はユーザーと合意した。往復の上限などの値は未確定である。

検査に落ちたとき、上流の成果物が変わったときに、誰が何を直し、何を検査し直すかを、全ての工程に共通の手順として定める。各工程の文書は合格条件だけを定め、不合格の後の扱いはこの文書に従う。

## 原則

1. 直すのは、その成果物を書いたセッションである。検査した側は直さない。
2. 原因が上流にある場合は、その場で辻褄を合わせない。上流に戻す。
3. 検査の指摘に、異を唱える経路を持つ。検査セッションの指摘には誤検出がある。
4. 検査し直すのは、落ちた条件と、直した箇所に依存する条件に限る。
5. 往復に上限を持つ。超えたら人が決める。
6. 合格も不合格も、記録に残す。記録は、検査した側が書く。

## 役割

| | 設計の時期(工程0から6) | 製造の時期(工程7から9) |
|---|---|---|
| 検査を起こす | 設計セッション | PM |
| 直す | 設計セッション。素材台帳、画像の素材、仕組みの定義は収集セッション | 章の執筆のセッション。設計の成果物は設計セッション |
| 異議を裁く | ユーザー | 設計セッション。設計セッションが書いた成果物への指摘は、ユーザー |
| 上限を超えたときに決める | ユーザー | ユーザー。PMが上げる |

仕組みの定義の抜き出し、画像の取得、画像の中の位置の記録、隠す作業は、収集セッションが行う。ユーザーが提供した画像も、収集セッションが素材台帳に登録する。

## 不合格のときの手順

1. **検査が不合格を返す。** 落ちた条件、該当する箇所、理由を添える。検査セッションの指摘には、対象の該当する箇所の引用を付け、条件のどの部分に反するかを書く。
2. **書いたセッションが、直すか、異議を唱えるかを選ぶ。**
3. **異議を唱える場合は、理由を添えて裁定を求める。** 裁く者は上の表による。裁定の結果は、設計の判断の記録に残す。
4. **直す場合は、原因のある成果物を直す。** 原因が自分の成果物にあれば直す。上流にあれば、Issueを立てて上流に戻し、自分の成果物は保留にする。
5. **検査し直す。**
   - 機械的な検査は、全て再実行する。
   - 検査セッションの検査は、落ちた条件と、直した箇所に依存する条件に限る。新しく起こした検査セッションに、前回の指摘を渡す。確かめるのは、指摘が解消したかと、直したことで新しい問題が生じていないかである。直していない箇所に、新しい指摘を出さない。
6. **往復を数える。** 1つの成果物(スライド仕様は章または節)について、不合格、修正、再検査の1巡を1回と数える。資料の表現規約が定める上限を超えたら、上の表の者に上げる。

上げられた者は、次のいずれかを選ぶ。

| 選択 | 内容 |
|---|---|
| 直し方を指示する | 具体的な直し方を示す |
| 受け入れる | 指摘を残したまま進める。検査の記録に残し、工程9の検査の報告に載せる |
| 上流に戻す | 原因が上流にあると判断し、上流の成果物を直す |
| 例外を認める | 合格条件から外す。資料の表現規約の例外として、理由とともに記録する |

合格条件そのものを、その場で書き換えることはしない。

## 警告

合否にしない指摘を、警告と呼ぶ。警告は検査の記録に残す。発生した工程の最終の承認の際に、承認する者に示し、直すか、受け入れるかを記録する。受け入れた警告は、工程9の検査の報告に載せる。

## 記録

| 記録 | 置き場 | 内容 | 書く者 |
|---|---|---|---|
| 状態の記録 | `status.yaml` | 成果物ごと、スライドごとの状態 | 検査のコマンドと、承認を記録する命令 |
| 検査の記録 | `checks/` | 検査1回ごとの、条件ごとの判定と引用 | 機械的な検査は、検査のコマンド。検査セッションの検査は、その検査セッション |
| 資料の表現規約 | `style.yaml` | [表現規約](style-rules.md)が定める内容。規則、上限と目安の値、例外 | 設計セッション |
| 結合テストの実行の記録 | `runs/` | 場面ごとの、スライドごとの理解と指摘。書式は[工程8](stages/08-integration.md)に定める | 読み手の役のセッション |
| 集計の記録 | `metrics.yaml` | 工程9が定める集計 | 検査のコマンド |

資料の表現規約は、工程0で、資料の型の定義の `limits` と個人の表現規約を写して作る。工程6で、資料に共通の見た目の規則を加える。表現の対応表(`06-patterns.yaml`)と語彙表(`terms.yaml`)は別のファイルに置き、資料の表現規約から参照する。

成果物を書いたセッションは、その成果物についての検査の記録を書かない。

### 検査の記録

検査1回につき、1つのファイルを `checks/` に置く。ファイル名は「作業のid--対象--回.yaml」とする。

- 対象は、章ごとに行う検査では章のID、そのほかでは `all` と書く。
- 回は、同じ作業と対象について検査した回数で、1から数える。再検査は新しいファイルに書く。前の回のファイルは書き換えない。

```yaml
# checks/inspect-sources--all--1.yaml
task: inspect-sources        # 工程表の作業
target: 01-sources.yaml      # 対象
commit: 3f2a9c1              # 対象の版
round: 1                     # 何回目か
model: claude-sonnet-5-5     # 判定したモデル
results:
  - check: K01-14            # 検査の台帳のID
    item: F015               # 対象の中のどれか
    verdict: fail            # pass / fail
    quote: "市場規模は約1.5倍"
    reason: 出典は「2019年比で1.4倍」とあり、値が合わない
  - check: K01-14
    item: F016
    verdict: pass
    quote: "継続率は業界平均より15ポイント高い"
```

- 条件ごと、対象の中の1件ごとに、1行を書く。対象の全体に当てる条件では、`item` を書かない。
- `quote` は、判定の根拠にした箇所の引用である。合格の行にも書く。
- `reason` は、不合格の行に書く。条件のどの部分に反するかを書く。
- 警告の検査(台帳の `level` が `warning`)も、同じ形で書く。条件を満たさなければ `fail` と書く。合否にしないことは、台帳が決める。
- 比べる作業は、`quote` に元の成果物の箇所を引用し、`reason` に、独立に書いた答えの箇所と、食い違いを書く。
- 機械的な検査の記録は、`model` を持たない。

### 状態の記録

書くのは、機械の命令だけである。検査のコマンドが、検査の記録と成果物の差分から書く。承認は、承認を記録する命令が書く。人とセッションは、直接は書かない。状態について事情の説明が要るときは、設計セッションが設計の判断の記録に書く。

```yaml
artifacts:
  01-sources.yaml:
    state: checked           # draft / checked / approved / invalid
    commit: 3f2a9c1
    rounds: 2
    checks: [checks/inspect-sources--all--2.yaml]
  02-claims.yaml:
    state: approved
    commit: 8b1d44e
    approved_by: user
    approved_on: 2026-11-23
slides:
  ch2-s3:
    state: invalid
    reason: F015 の値が変わった
```

| `state` | 意味 |
|---|---|
| `draft` | 作成中。合否にする検査のうち、通っていないものがある |
| `checked` | 検査済み。`commit` の版が、合否にする検査の全てに通った |
| `approved` | 承認済み。`commit` の版を、`approved_by` の者が承認した |
| `invalid` | 無効。合格または承認の後に、前提にした上流の項目か、成果物そのものが変わった |

- `rounds` は、検査した回数である。往復の回数は、これより1つ少ない。`checks` は、最後の回の検査の記録である。
- `approved_by` は、承認した者である。ユーザーは `user`、章を受け入れたPMは `pm` と書く。
- `slides` は、スライドごとの状態である。無効になった理由を `reason` に書く。
- スライドの保留は、スライド仕様の `status` が持つ。状態の記録には写さない。

### 承認の記録

ユーザーの承認と、PMによる章の受け入れは、状態の記録に書く。書くのは、承認を記録する命令である。命令を実行するのは、設計の時期(工程0から6)は設計セッション、製造の時期(工程7から9)はPMである。

- 命令は、成果物の `state` を `approved` にし、承認した版のコミットのIDを `commit` に、承認した者を `approved_by` に、日付を `approved_on` に書く。
- ユーザーの承認は、ユーザーが承認したと言った成果物についてだけ記録する。言っていないものを記録しない。
- 章の受け入れは、PMが、受け入れの条件を全て満たした章について記録する。
- 承認を取り直したときは、新しい版で記録し直す。

### 検査と記録を守る

検査で品質を守る以上、検査そのものと、その記録が書き換えられないことが前提になる。

- 検査のコマンド、辞書、検査の記録、状態の記録、上流の成果物は、執筆のセッションの作業の枝で変更できない。変更が含まれる場合は、受け入れを拒む。
- 受け入れる側は、執筆のセッションの作業の枝にある検査のコマンドを使わない。受け入れ済みの本流にある検査のコマンドと辞書で、自分で実行する。
- 承認の後に内容が変わった成果物は、検査のコマンドが、状態の記録にある承認した版との差分から機械的に挙げ、承認を取り直すまで、下流の工程の開始を止める。設計セッションが、検査を通すために承認済みの成果物を直すことを、これで拾う。
- 検査を通すための書き換えや、検査の回避が見つかった場合は、PMまたは設計セッションが、変更を取り消し、そのセッションを新しいセッションに替える。事実をIssueに記録する。

## 人の手直しを守る

ビルドは、出力したファイルの内容の要約値を記録する。次にビルドするとき、既にあるファイルの要約値が記録と違う場合は、人が手直ししたものとして、上書きせずに止まる。手直しの内容を[フィードバックと修正](feedback.md)の手順で読み取り、再現できない手直しの一覧を残してから、ビルドする。作り直した後に、一覧にある手直しをやり直す。

## 上流が変わったとき

検査の記録は、対象の版を `commit` に持つ。検査のコマンドは、その版の成果物の中の参照(事実のID、主張のID、スライドのIDなど)から、合格が前提にした上流の項目と、その時点の内容を導く。項目のいずれかが後で変わった場合は、その合格を無効とする。判定の単位は、ファイルではなく項目とする。

- 機械的な検査は、再実行すれば上流の変化を拾える。
- 検査セッションによる合格は、上流が変わっても失敗しない。そのため、この方法で拾う。
- 無効になった成果物だけ、検査セッションの検査をやり直す。変わっていないものは再検査しない。
- ユーザーが承認したもの(`answer`、要約の文、主張、章と節とスライドの題と要点、見せ方、型の見本、語彙表)が変わる場合は、ユーザーの承認を取り直す。
- 設計の時期は設計セッションが、製造の時期はPMが、無効になった成果物を挙げる。挙げる元になるのは、状態の記録である。

スライド、事実、主張などのIDは、一度付けたら変えない。順序や章を変えても、IDは変えない。

### 直す成果物と、無効になる範囲

| 直す内容 | 直す成果物 | 無効になるもの |
|---|---|---|
| 問い、読み手、目的 | ブリーフ | 探索の計画以降の全て。集めた事実は素材台帳に残し、新しい計画に照らして使えるものを使う |
| 制約、使われる場面など | ブリーフ | 影響を受ける成果物を設計セッションが挙げ、ユーザーが確認する |
| 事実の値、記述、限定 | 素材台帳 | その事実を根拠にする、問いごとの答え、主張、要点、立証の設計、スライド |
| 要素、つながり、場面 | 仕組みの定義 | 定義の合格条件。それを図に使う立証の設計とスライド |
| 画像の差し替え、画像の中の位置、隠す箇所 | 画像の素材 | その画像の全ての位置と、写り込みの検査。それを使うスライド |
| 結論 | 主張の骨子 | 章構成以降の全て |
| 主張の文言、要約の文 | 主張の骨子 | 章の要点、要約のスライド、その主張に属する節とスライドの要点 |
| 章と節の順序、入れ替え、分け方、題、要点、限定 | 章構成 | 該当する章以降のストーリーラインと、章の前提と到達点。章のまとめ、節のまとめ、節の要点を引くスライド |
| スライドの題、要点、役割、限定、出どころ | ストーリーライン | そのスライドの立証の設計とスライド仕様。その章の前提と到達点。その節のまとめ。そのスライドへの言及を持つスライド |
| スライドの追加、削除、順序 | ストーリーライン | 該当するスライドの立証の設計以降。章の前提と到達点。そのスライドへの言及を持つスライド |
| 章の前提と到達点 | 章の前提と到達点 | 該当する章と、それより後の章のスライド |
| 見せ方、注目させる点、使う事実 | 立証の設計 | そのスライドの仕様。表現の対応表の集計 |
| 型の割り当て | 表現の対応表 | その型を使う全てのスライドと、型の見本 |
| 規則、上限、目安 | 資料の表現規約 | 全ての成果物に機械的な検査を再実行する。違反の一覧を出し、[表現規約](style-rules.md)の手順で扱う |
| 語を変える、分ける、まとめる | 語彙表 | その語を使う全ての文。[使う語彙](terms.md)の手順で扱う |
| 中身の文、型のデータ | スライド仕様 | そのスライド。その章の、章の受け入れの通読。工程8を実行済みの場合は、工程8の回帰テスト |
| 問いの分解 | 探索の計画 | その問いより下の調査と、問いごとの答え。ユーザーの承認を取り直す |
| 仮説 | 仮説の一覧 | 全ての事実の、仮説に対する `stance`。主張の骨子の仮説の比較 |
| 問いごとの答え | 問いごとの答え | 親の問いの答え。それを素材にした主張、節の要点、スライドの要点 |
| 場面と、期待する結果 | テストの場面 | その場面の実行の結果 |
| 型の定義(含意、収容量) | 型の定義 | その型を使う全てのスライドの照合と、型の見本 |
| 外に出せない情報 | ブリーフ | 全ての画像の写り込みの検査 |

複数の章にまたがる修正(同じ言い回しの置き換えなど)は、章ごとに別々に決めさせない。設計セッションが直し方を1つ決め、該当する章の執筆のセッションに渡す。
