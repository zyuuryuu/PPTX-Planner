# 工程表の下書きの報告

[目次に戻る](../README.md)

状態: 記録。工程表の下書き(作業100件)を起こした時点の報告である。この後に、工程の文書の見出しを切り直し、工程表 [`tasks.yaml`](../tasks.yaml) を確定した。見出しの名前と作業の数は、今の文書と合わない。

工程の文書(`stages/00-brief.md` から `09-finish.md`)と検査の台帳(`checks.yaml`)から、作業の一覧を起こした。既存の文書と道具は変更していない。数は、`tasks.yaml` と各文書をスクリプトで読んで数えた。

## 表の作り方

- 作業は100件である。先頭に `count` を置き、`tasks` に並べた。書式は検査の台帳に合わせた。
- 担当の識別子は、台帳の `judge` の6つ(`user`、`designer`、`pm`、`inspector`、`reader`、`machine`)に、`collector`(収集セッション)と `writer`(執筆のセッション)を足した。どちらも [体制とセッション](../organization.md)にある担当である。
- 担当の定めがない作業は、`role` を `null` とした。3件ある。
- `stage` は工程の番号とした。工程2から4のそれぞれで行う語の登録の3件だけ、台帳の `KX` と同じく `[2, 3, 4]` と並べた。
- 合格条件、開始の条件、終了の条件の見出しは、`sections` に入れていない。条件は `checks` のIDで渡す前提である。
- `checks` は、作る担当の作業には、台帳の `target` がその成果物である検査を、判定者によらず入れた。検査、承認、機械の作業には、`judge` がその担当である検査を入れた。判定者が2つある検査は、両方の担当の作業に入れた。
- `next` は、分かれる場合のほか、順序の定めがない場合にも並べた。
- 設計の時期の「作り方」の手順のうち、行う者が書かれていないものは、設計セッションの作業に入れた。工程0から6の成果物は、素材台帳、画像の素材、仕組みの定義を除いて設計セッションが書く、という定め(organization.md)による。該当する手順は「決められなかった点」に挙げる。
- 文書から決められなかった点は、`tasks.yaml` の中に `#` の行で残した。機械で読む項目には入れていない。

- 要約のスライドの仕様
- 仮説ごとの否定する事実の一覧、抜き出した語の一覧、題と要点の一覧、集計で挙がったエラーの候補
- この資料に固有の受け入れの条件、実際の環境で確かめた結果の記録、検査セッションが書いた要約(`K00-06`)
- 承認の記録。Gitのタグとする定めがある

あわせて、`04-scenarios.yaml` は、ファイル名はあるが書式の定めがない。

### 定めどうしが合わない

- 工程1の `K01-11` は、`metric` を語彙表の語で書くことを求める。語の登録は、工程2から4で行うと定めている(terms.md)。工程1で `metric` の語を登録する手順がない。
- 検査 `KX-01` から `KX-19` の工程は、2、3、4、7である。工程6で設計セッションが書く型の見本のスライド仕様は、対象に入っていない。工程7の検査(`K07-`)を見本に当てるかどうかも決まらない。見本の仕様は、工程7でそのまま使う。
- 読み手の役のセッションは、設計の成果物を読まない。一方、読み方を定める「テストの場面」の表には、期待する結果の列がある。この表を読み手の役に渡してよいかが決まらない。
