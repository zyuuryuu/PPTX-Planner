# 体制とセッション

[目次に戻る](README.md)

## 体制

作業を、性質の違う2つの時期に分ける。

| | 設計の時期(工程0から6) | 製造の時期(工程7から9) |
|---|---|---|
| 成果物 | 小さい。全体を一度に扱える | 大きい。章ごとに分かれる |
| ユーザーとの対話 | 多い | 少ない |
| 並行する作業 | ない | ある |
| 進め方 | 1つの設計セッションが、ユーザーと対話しながら書く | PMが子セッションに割り振り、結果を受け入れる |

設計の時期にはPMを置かない。並行する作業がなく、PMを挟むとユーザーの意図が伝言で薄まるためである。

### 設計セッション

設計の時期を通して、ユーザーの相手をする1つのセッション。工程0から6の成果物のうち、素材台帳、画像の素材、仕組みの定義を除くものを書く。この3つは収集セッションが書く。事実の収集と検査は、別のセッションに任せる。

設計の途中の判断は、設計の判断の記録 `decisions.md` に残す。ソフトウェア開発の設計判断の記録(ADR)と同じ形をとる。

- 状況(何を決める必要があったか。関係する事実)
- 決めたこと
- 却下した案と、その理由
- 受け入れた影響(証拠との食い違い、残る危険など)
- 決めた人と日付

記録するのは、案を却下したとき、証拠と食い違う結論を維持したとき、表現規約の規則の矛盾をユーザーが裁いたとき、および各工程の定義と[不合格と修正の手順](rework.md)が記録を求めるときである。

製造の時期に入っても終了させず、設計担当として残す。製造中に設計の疑問や見直しが出たら、PMとユーザーはこのセッションに戻る。発表の後の反応は、ユーザーが伝え、このセッションが記録する([工程9](stages/09-finish.md))。

### 引き継ぎの検査

製造の時期に入る前に行う。新しく起こしたPMに成果物だけを読ませ、次を確かめる。

- 資料の結論、章の構成、各章の要点を、自分の言葉で説明できる。
- 設計の判断の記録にある却下した案を、再び提案しない。
- 作業を始めるうえで分からない点がない。

#### 説明を書く

担当: PM。

1. 成果物だけを読む。設計セッションに尋ねない。
2. 資料の結論、章の構成、各章の要点の説明を書く。変えたい点と、分からない点があれば、あわせて書く。`work/answers/handover-check.yaml` に置く。
3. 検査セッションが比べた結果を受けて、合否を判定する。食い違いも、分からない点もなければ、合格とする。残ったものの全てに、直さない理由が設計の判断の記録にある場合も、合格とする。

#### 説明を設計の成果物と比べる

担当: 検査セッション。

PMの説明を、主張の骨子、章構成、設計の判断の記録と比べる。

- 結論、章の構成、章の要点が、成果物と違う場合を、食い違いとする。
- 変えたい点が、設計の判断の記録にある却下した案に当たる場合を、食い違いとする。
- 食い違いと、PMが挙げた分からない点を、設計セッションに示す。

#### 成果物を直すかを決める

担当: 設計セッション。

食い違いと、分からない点の1件ごとに、設計の成果物を直すかを決める。

- 直した場合は、新しく起こしたPMで、引き継ぎの検査をやり直す。
- 直さない場合は、理由を設計の判断の記録に書く。

### PM

製造の時期を進めるセッション。引き継ぎの検査に通った後、新しく起こすことを既定とする。承認済みの成果物だけを読んで始める。設計セッションがそのままPMを兼ねる形も許す。兼ねる場合は、設計セッションが書いたもの(型の見本にしたスライド、要約)の受け入れを、ユーザーが行う。どちらの場合も、引き継ぎの検査は行う。PMが止まったときや、文脈が膨らみすぎたときに、新しいセッションに替えられるようにするためである。

- 中身を書かない。読むのは、状態の記録、全体を扱う成果物、検査の合否である。
- 章または節ごとに執筆の子セッションを起こし、検査セッションを起こす。
- 子セッションの成果物を、[工程7](stages/07-slide-spec.md)の合格条件と章の受け入れの条件を全て満たした場合にだけ受け入れる。検査のコマンドは、受け入れる側が自分で実行する。作る者と受け入れる者を分けることで、検査の回避を防ぐ。
- 型の見本にしたスライドの仕様を、該当する章のファイルに入れる。章の執筆のセッションは、そのスライドを書き直さない。
- 子セッションを起こすときは、道具が出す作業票を、最初のメッセージにする。執筆の子セッションには、あわせて章の作業票を渡す。内容を要約して伝えない。
- 設計の見直しが必要になったら、Issueを立てて設計セッションとユーザーに知らせる。自分では設計を直さない。
- 工程8で、読み手の役のセッションの指摘を、1件ずつIssueにする。読み手の役のセッションは、読んで指摘を書くだけである。
- 工程9を進め、ユーザーの承認の後に引き渡す。

節は、工程3で決める。長い章は、節ごとに子セッションを起こしてよい。

### 章の作業票

執筆の子セッションに渡す、章ごとの1つのファイル。上流の成果物から機械的に抜き出して作る。PMが要約したものではない。作業1件の指示である作業票とは別のもので、作業票の入力に当たる。

- ブリーフ
- 章と節の題と要点、その章のスライドの題、要点、役割、限定、出どころ、立証の設計
- 前後の章の、スライドの題と要点
- その章のスライドが使う事実と、仕組みの定義の該当する部分
- その章の前提と到達点
- 表現の対応表、資料の表現規約、その章に関わる語彙
- 該当する型の見本と、そのスライド仕様

素材台帳の全体は渡さない。読み込み量を抑えるためと、立証の設計が割り当てた以外の事実を使わせないためである。

### 完了の報告

執筆の子セッションは、次の書式で報告する。

- 状態(完了、一部、停止)
- 検査のコマンドの結果
- 立てたIssue
- 判断に迷った点

### 上流の問題の戻し方

執筆の子セッションは、上流の成果物を直さない。Issueを立て、該当するスライドを保留にして、ほかのスライドを進める。

| 気づいたこと | 戻す先 |
|---|---|
| 事実が足りない | 調査依頼(収集セッション) |
| 題や要点が証拠と合わない、型に収まらない | 設計セッション |
| 必要な語が語彙表にない | 語の登録の申請([使う語彙](terms.md)) |
| 上流の成果物どうしが矛盾している | 設計セッション |

題と要点の文言は、1文字の変更でも設計セッションを経る。章のブランチが担当外のファイルを変えた場合は、検査のコマンドが失敗する。

### 合格が無効になったスライド

章を並行して書き、途中で上流が直されることがあるため、合格した後に前提が変わるスライドが出る。上流が変わった時点で、PMが該当するスライドを挙げ、章の執筆のセッションに返す。仕組みと、スライド以外の成果物の扱いは、[不合格と修正の手順](rework.md)に定める。

### 子セッション

子セッションは、ユーザーから見え、後から再開できるセッションとする。PMの内部で動いて結果だけを返す、ユーザーから見えない下請けの処理にはしない。

- ユーザーは、どの子セッションの作業も開いて読める。
- ユーザーは、子セッションに直接指示できる。その結果はコミットとIssueに残り、PMはそこから知る。
- 執筆の子セッションは、章や節を担当し続ける。その章への指摘は、同じセッションに渡す。
- 検査セッションは、検査のたびに新しく起こす。前回の検査を覚えていると、見たつもりで見落とすためである。不合格の後の再検査では、新しく起こしたセッションに、前回の指摘だけを渡す([不合格と修正の手順](rework.md))。作業の記録はユーザーから見える形で残す。
- セッションには、資料の名前、担当、役割が分かる名前を付ける。
- 子セッションを起こすときは、作業票を最初のメッセージにする。作業票は、道具 `tools/work_order.py` が工程表から作る。1行目がスキルの名前で、続けて、作業、手順のファイル、対象、入力、読まないもの、成果物を持つ。手順と報告の書式はスキルが持ち、作業票には写さない。
- 入力を限る作業の作業票は、写しを作る指定を付けて出す([限った入力の写し](#限った入力の写し))。
- 子セッションを起こすときの版の指定には、ブランチの名前を使う。短いコミットIDを使わない。対象のコミットは、作業票の対象に書く。

セッションの記憶は正本ではない。正本は成果物のファイルである。上流の成果物が変わったら、担当のセッションに読み直させるか、新しいセッションに替える。どのセッションが止まっても、成果物と状態の記録から別のセッションが引き継げるようにする。

## セッションの分離

| セッション | 読むもの | してはいけないこと |
|---|---|---|
| 収集 | 調査依頼、外部の資料 | 主張、題、要点を書くこと、仮説の一覧を読むこと |
| 執筆 | 承認済みの上流の成果物 | Web検索や資料の直接の読み込み、台帳にない事実の記述 |
| 検査 | 検査対象の成果物と、その上流の成果物 | 検査対象を自分で直すこと |
| 読み手の役 | ブリーフの読み手の情報と、ビルドした実物 | 設計の成果物を読むこと、スライドを直すこと |

読み手の役のセッションは、工程7の章の受け入れと、工程8の結合テストで、PMが起こす。実行のたびに新しく起こす。

検査は、機械の検査を先に行う。検査セッションは、機械の検査に通ったものを検査する。

分ける理由:

- 執筆中のLLMは、文を完成させるために必要な事実を補ってしまう。事実を台帳のIDでしか参照できなくすれば、補う余地がなくなる。
- 生の資料が執筆の文脈に入らないため、読み込み量が抑えられる。
- 書いた本人による検査は、自分の誤りを見逃しやすい。

分離だけでは、収集セッション自身の捏造は防げない。そのため素材台帳に引用箇所を記録させ、検査セッションが出典と突き合わせる。

## 限った入力の写し

入力を限ることが目的の作業(工程表の `restricted: true`)には、元のファイルを渡さない。元のファイルを開くと、見てはいけない項目が見えるためである。機械が、渡してよい部分だけの写しを作り、作業にはその写しだけを渡す。

写しの中身は、工程表の `inputs` の書き方で決まる。

| `inputs` の書き方 | 写しの中身 |
|---|---|
| `ファイル#項目` | その項目だけ。同じファイルの項目を複数挙げた場合は、1つの写しにまとめる |
| `ファイル#-項目` | その項目を除いた残り |
| `ファイル#名前` で、名前が下の表にあるもの | 下の表による |
| 項目のないファイル | 写しを作らず、元のファイルを渡す。まるごと渡してよいと定めた箇所を、工程表の `restricted_by` に書く |

- YAMLのファイルでは、項目は、最上位の項目か、並びの各件の直下の項目を指す。並びの各件には、見分けるために先頭の項目(`id` など)を残す。コメントは写さない。
- Markdownのファイルでは、項目は見出しを指す。
- ディレクトリを挙げた場合は、中のファイルごとに写しを作る。
- 対象の章を指定した場合は、章を持つ件(`chapter`)と、章ごとのファイルのうち、その章のものだけを写す。

名前で指す写しは、次の通り。

| 名前 | 元 | 中身 |
|---|---|---|
| スライドの文 | `07-slides/` | [工程7](stages/07-slide-spec.md)の「スライドの文」に定める |
| そのスライドが使う事実 | `01-sources.yaml` | 対象のスライド仕様の `sources` に挙がる事実 |

写しは、作業票を出す直前に、道具 `tools/work_order.py` が作る。置き場は `work/views/<作業のid>/` で、名前は元のファイルと同じにする。作業票の入力は、写しを指す。

写しを作れない入力は、道具が作業票にそう出す。作業票を出す者は、代わりに元のファイルを渡さない。

写しは成果物ではない。検査と承認の対象にしない。作業票を出すたびに作り直し、作業が終われば消してよい。

## ユーザーとのやり取り

ユーザーの負担を抑えるため、次を守る。

- 一度に求める判断は1つにする。
- 白紙の質問ではなく、推奨と代案を示して選んでもらう。
- 全体の流れを先に見せ、その後は章ごとに進める。
- 検査に通ったものは見せず、判断が要るものだけを出す。
- 承認済みのものを再び聞かない。上流の変更で見直しが要るときは、変わった箇所だけを見せる。
